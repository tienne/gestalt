# 주석 위생 룰북

리뷰 파이프라인이 코드 주석을 검토할 때 쓰는 룰북이다. 룰 원본은 이 문서이며 에이전트 문서에
룰을 복사하지 않는다. 복사해 두면 룰북과 사본이 조용히 갈라진다.

주석은 기본적으로 없는 게 낫다. 코드를 읽거나 `git log`, `git blame`으로 확인되는 내용이면
주석으로 남길 이유가 없고 코드가 바뀔 때 같이 안 고쳐져서 거짓말이 된다.

## 무엇을 대상으로 보는가

판정 범위를 먼저 정한다. 이걸 안 정하면 손대지 않은 기존 주석까지 전부 후보가 되어 리뷰가
노이즈로 덮인다.

- diff에서 **추가되거나 수정된 라인의 주석만** 본다. 손대지 않은 기존 주석은 대상이 아니다
- 예외는 CM-5다. 변경된 함수 안에 있던 주석이 그 변경 때문에 거짓이 됐으면 라인을 직접
  건드리지 않았어도 짚는다. 그 변경이 만든 거짓이라서다
- 파일 전체를 읽어야 하는 상황이면 `git diff`로 변경 라인 번호를 먼저 확보하고 그 범위
  안에서만 판정한다. 파일 목록만 받았다고 파일 전체를 후보로 삼지 않는다

## Do-NOT (검토 제외)

- 라이선스 헤더, 저작권 표기
- 생성 파일 상단의 생성물 표기
- 도구 지시 주석 — `eslint-disable`, `@ts-expect-error`, `prettier-ignore`, `biome-ignore`
- 타입 정의 파일(`.d.ts`)의 설명 주석
- 룰 문서와 템플릿 안의 예시 주석 — 예시로 적힌 나쁜 주석을 실제 위반으로 세지 않는다

## 심각도

리뷰 파이프라인 스키마를 따른다(`critical` | `high` | `warning`). AI-tell 룰북의 S1, S2와는
다른 축이므로 섞지 않는다.

- `high` — 읽는 사람을 잘못된 방향으로 끄는 것
- `warning` — 없어도 되는 것

## A. 지워야 할 주석

| ID | 패턴 | 심각도 | 처방 |
|---|---|---|---|
| CM-1 | 코드를 그대로 옮겨 적은 주석 — `count += 1` 위의 `// 카운트를 1 증가` | warning | 지운다. 코드가 안 읽히는 게 원인이면 이름을 풀어쓰거나 블록을 함수로 뺀다 |
| CM-2 | 시그니처만 반복하는 내부 함수 JSDoc — 파라미터 이름과 타입을 그대로 옮긴 것 | warning | 지운다. 공개 API와 공용 유틸은 CM-K3으로 보존 대상이다 |
| CM-3 | 변경 이력과 작업 메모 — `// 2026-03-12 수정`, `// 기존 로직 제거함`, `// 리뷰 반영` | warning | 지운다. 커밋 메시지가 이미 담는다 |
| CM-4 | 주석 처리된 죽은 코드 | high | 지운다. 되살릴 일이 있으면 히스토리에서 꺼낸다 |
| CM-5 | 코드와 어긋난 주석 — 설명하는 동작이 지금 코드에 없는 것 | high | 코드에 맞게 고치거나 지운다. 어느 쪽인지는 주석이 담은 WHY가 아직 유효한지 보고 정한다 |
| CM-6 | 섹션 배너 — `// ===== helpers =====` | warning | 지운다. 파일이나 함수를 나누라는 신호다 |
| CM-7 | 티켓 번호 없는 TODO, FIXME | warning | 티켓을 만들어 번호를 붙인다(`TODO(WDS-123): ...`). 번호 없이 남기지 않는다 |
| CM-8 | 코드가 무엇을 막거나 보장한다고 단언하는데 그 보장이 깨졌을 때 실패하는 관련 테스트가 없는 주석 — "~를 막는다", "~는 못 만든다", "반드시 ~한다" | high | 그 입력을 실제로 넣어보는 테스트를 먼저 만들고 주석에 남긴다. 테스트를 못 만들 자리면 단언을 빼고 범위로 적는다("~까지가 이 처리의 범위다") |

## B. 남겨야 할 주석 (WHY만)

| ID | 패턴 | 심각도 | 처방 |
|---|---|---|---|
| CM-K1 | 왜 이 방식을 골랐는지, 왜 뻔한 쪽으로 안 갔는지 — 외부 API 버그 우회, 성능 제약, 스펙 요구사항 | 보존 | 지우자는 의견을 내지 않는다 |
| CM-K2 | 겉보기에 틀린 것처럼 보이는 코드가 의도된 것이라는 근거 | 보존 | 같음 |
| CM-K3 | 공개 API와 공용 유틸의 JSDoc, TSDoc | 보존 | 내부 전용 함수의 것은 CM-2 대상이다 |

### CM-8을 판정할 때

단언 동사가 들어갔다고 전부 걸지 않는다. **그 문장이 틀렸을 때 사람이 손해를 보는 자리**만 본다.
방어 코드, 입력 정리, 검사기처럼 "막는다"가 곧 그 코드의 존재 이유인 자리가 대상이다.

관련 테스트가 있는지는 이렇게 가른다.

- 주석이 말한 **그 입력**을 넣어보는 테스트가 있다 → 통과
- 테스트는 있는데 다른 입력만 넣어본다 → CM-8이다. 문장은 A를 막는다는데 테스트는 B만 본다
- 테스트가 그 파일에 여럿 있고 전부 초록불이다 → 그것만으로는 근거가 안 된다

찾은 테스트 이름을 코멘트에 적는다. 리뷰이가 다시 뒤지지 않아도 된다. 잘못 짚었으면 그 자리에서 갈린다.

## C. 처방 원칙

- **지우자고만 하지 않는다.** 대체 표현까지 낸다 — 이름을 풀어쓰거나, 블록을 함수로 빼거나,
  매직 넘버를 이름 붙은 상수로 올리거나, 배경 설명이 길면 README나 ADR로 옮기고 링크만 남기는 식이다
- 주석의 언어는 한글을 우선한다
- WHY가 담긴 주석을 지우자고 할 때는 그 WHY가 갈 자리를 함께 지정한다. 지울 자리만 정하고
  갈 자리를 안 정하면 맥락이 사라진다

## 출력

`category`는 `quality:comments`를 쓰고 `message` 앞에 룰 ID를 적는다.

```
CM-4 주석 처리된 죽은 코드 — 되살릴 일이 있으면 히스토리에서 꺼낼 수 있어요.
```

ID를 안 적으면 리포트에서 어느 룰로 걸렸는지 추적이 끊긴다. 룰을 고쳤을 때 과거 리뷰가
어느 기준으로 나왔는지도 못 가린다.

## 룰을 추가할 때

- 번호는 `CM-` 연번으로 이어 붙인다. AI-tell 룰북의 `A-1`~`J-3` ID와 섞지 않는다 — 어투 룰과
  층위가 다르고 `verify:rules`는 그쪽 ID만 룰북 정합 대상으로 본다
- 추가한 뒤 `pnpm verify:rules`를 돌린다. 이 문서도 `plugin/role-agents/` 아래에 두므로
  금지 표현 검사와 S1 어투 검사를 함께 받는다
- 정규식으로 오탐 없이 잡히는 룰(CM-4, CM-6, CM-7 같은 것)은 `src/humanize/detectors.ts`가
  하는 방식으로 코드에 내리는 걸 함께 검토한다. 코드가 잡으면 프롬프트가 안 닿아도 걸린다
- 판정에 사람 판단이 필요한 룰(CM-1, CM-5)은 모델 쪽에 남긴다. 정규식으로 밀면 오탐이
  리뷰를 덮는다

주 참조자는 `quality-reviewer`다.
