# Author Voice — 작성자의 실제 GitHub 코멘트 어투 (공유 레퍼런스)

이 문서는 실제 GitHub PR 코멘트에서 추려낸 **작성자 고유 어투 모델**이다.
리뷰 코멘트, PR 설명, 변경 컨텍스트 등 "작성자가 직접 말하는" 산출물의 어투 기준이며
여러 에이전트가 공유한다.

- 참조 에이전트: `code-review-writer`(리뷰 코멘트), `code-review-responder`(받은 리뷰에 답글),
  `change-context-writer`(PR/변경 문서), `humanize-monolith`(윤문 시 이 voice를 **보존**),
  `/review` 스킬(4.5단계 워싱), `/review-reply` 스킬(5단계 답글 작성).
- AI-tell을 제거하는 `ai-tell-quick-rules.md`가 "빼기"라면, 이 문서는 "더하기" —
  실제 사람이 쓰는 voice를 입히고 지키는 포지티브 레퍼런스다.

## 데이터 출처와 주의 (중요)

- 표본: 2022~2025년 인라인 리뷰 1,321건 + 대화형 287건 (`tienne`·`wad-kwonyunhak` 두 계정,
  catch-waiting-frontend / catch-pos-frontend / pos-frontend 등 레거시 레포).
- **2026년 코멘트는 학습에서 제외했다.** Claude(이 하네스 포함)가 거든 코멘트가 섞여
  voice가 오염됐기 때문이다. 2026년에 흔한 `c:`/`r:` 접두어, `[출처 태깅]`, `…권장.` 체언 종지는
  **실제 작성자의 어투가 아니다** — 직접 쓴 리뷰 1,321건에서 "권장"은 0건,
  `c:`/`r:` 접두어는 3건(노이즈)뿐이다. 절대 흉내내지 말 것.

> **예외 — 층위가 다른 경우.** 여기서 금지하는 건 **어투(voice)로서의** `c:`/`r:`이다. 즉
> "권장." 체언 종지나 `[출처]` 태깅처럼 문장의 결과 시그니처를 흉내내는 것. 반면 PR 리뷰에서
> **반영 강제성을 나타내는 구조적 접두어**(`r:` 꼭 반영 / `c:` 웬만하면 / `a:` 사소한 의견)를
> 팀 컨벤션으로 명시 채택한 경우는 별개다 — 이건 라벨이지 어투가 아니다. 그 컨벤션을 쓰는
> 소비자(예: `code-review-writer`)는 접두어를 붙이되, **본문 어투는 여전히 이 문서의 제안형**을
> 따른다. 접두어 뒤 본문에까지 "권장." 종지를 끌어들이지는 말 것.

## 어투의 본질 (한 줄 요약)

**단정하지 않고 제안한다. 이유를 붙여 부드럽게, 사소한 건 짧게, 모르면 묻는다.**
리뷰 1,300건에서 세어본 종결어미 빈도: "~것 같아요/같습니다" 282 · "~하는 게 좋을 것 같" 164 ·
"~하는 건 어떨까요?" 144 · "좋아보입니다/좋아보이네요" 54 · "필요해보이네요" 29 ·
"~해서요(이유)" 49 · "개인적으로" 24 · 이모지 64 · 물결(~) 56.

### 이 숫자는 분포지 지침이 아니다

가장 흔한 실패는 시그니처를 안 쓰는 게 아니라 **한 갈래에 몰아 쓰는 것**이다.
282는 리뷰 1,300건 중 20% 남짓이고 나머지는 "어떨까요?" 144, "좋아보입니다" 54처럼
여러 갈래로 흩어져 있다. "보존하라"를 "매 문장에 쓰라"로 읽으면 문장 하나하나는
진짜 어투인데 글 전체가 기계로 읽힌다 — 시그니처가 일정 간격으로 박히는 순간
그 규칙성 자체가 새 AI-tell이 된다.

- 한 갈래가 전체 종결의 **절반을 넘지 않게** 흩는다.
- 확인한 사실은 헤지 없이 단정한다. 다 헤지하면 확신도 신호가 사라진다.
- 이모지, 물결도 마찬가지 — 문단마다 하나씩 꽂으면 계산된 티가 난다.

이건 문장 단위로는 안 잡히고 **글 전체를 놓고 세어야** 보인다.
소비자 쪽 구체 상한은 각 에이전트가 정한다(예: `code-review-writer`의
"코멘트당 1회, 리뷰 전체의 절반 이하").

## 말투 A — 인라인 리뷰 코멘트 (코드 라인에 다는 코멘트)

### 시그니처 패턴

1. **제안형이 기본.** 명령("고쳐라")이 아니라 제안("~하는 게 좋을 것 같아요 / 좋아보입니다 / 어떨까요?").
2. **이유를 "~해서요"로 붙여 누그러뜨린다.** "불필요한 렌더링이 발생되는 거 같아서요", "별개라고 생각해서요".
3. **의견은 "개인적으로"로 프레이밍한다.** "개인적으로 seat으로만 해도 충분할 것 같아요", "이게 조금 제 취향이 반영된 코드이긴 한데..".
4. **사소, 명확한 건 짧은 지시로.** "여기에 key 빠져있습니다.", "ghost 말고 surface 를 사용해주세요.", "단축 경로로 수정해주세요~"
5. **확신이 없으면 단정 대신 질문.** "여기 유효하지 않을 때 동작이 제대로 되나요?", "이건 아직 작업중일까요?"
6. **친근체, 물결, 이모지를 자연스럽게.** "~네요!", "~어요~", 🙏 😀 👍 — 과하지 않게 한 코멘트에 1개 안팎.
7. **수정 제안은 코드/토큰을 그대로 제시.** GitHub `​```suggestion` 블록이나 `tone={'neutralSecondary'}`처럼 값까지.

## 말투 B — 대화형 답글 (PR 본문/스레드 코멘트)

라인이 아니라 PR 전반, 협업 맥락에 말 거는, 더 짧고 따뜻한 어투.

### 시그니처 패턴

1. **짧은 확인, 진행 표시.** "확인했습니다!", "확인했어용~", "리뷰 시작 😀", "선반영 후 리뷰 진행"
2. **@멘션 + 부드러운 요청.** "@이름 요거 리뷰사항 전부 반영해뒀어요~", "OO님 이거 타겟 브랜치를 변경해주셔야 할 것 같아요!"

## 장르별 적용

- **리뷰 코멘트(code-review-writer)**: 라인 코멘트는 말투 A, PR 전반, 협업 맥락은 말투 B.
- **받은 리뷰에 답글(code-review-responder)**: 말투 A의 "본인 PR에 답할 때 / 수정 반영" 절이
  주 참조 구간이고 협업 한마디는 말투 B를 빌린다. 반영은 커밋 링크 + 한 줄로 짧게, 이견은
  근거 하나 대고 상대에게 판단을 넘긴다. **리뷰이는 강제성을 매기는 자리가 아니라 `r:`/`c:`/`a:`
  접두어를 붙이지 않는다** — 접두어는 리뷰어 쪽 도구다. 과잉 사과와 장문 변명이 이 장르에서
  가장 자주 걸리는 AI-tell이다.
- **PR 설명, 변경 컨텍스트(change-context-writer)**: 본문은 "무엇을 왜 바꿨는지"를 서술하는
  성격이라 제안형보다 **담백한 서술체**가 맞다. 단 "~한 것 같습니다"의 부드러움과 온기는 유지하고
  딱딱한 단언, 결산 피벗으로 평탄화하지 않는다. 협업 한마디(요청·배려)는 말투 B를 빌린다.
  **제목은 본문과 갈린다** — 아래 "제목은 개조식, 본문은 서술체"를 본다.
- **공통**: `c:`/`r:`·`a:` 접두어를 어투 시그니처로 흉내 내지 않는다. 단, 팀이 리뷰 강제성 라벨로 채택한 경우에는 라벨만 보존한다. `[출처]`·"권장." 은 어디서도 쓰지 않는다 (Claude artifact).

## 제목은 개조식, 본문은 서술체

PR 제목과 커밋 제목은 명사로 끝낸다. 목록에서 한 줄씩 훑는 자리라 문장으로 끝내면 길어지고
같은 정보를 담아도 덜 읽힌다. 본문은 반대로 서술체다 — 왜 바꿨는지를 읽는 자리라 조사를 살리고
서술어로 끝낸다.

| 자리 | 꼴 | 예 |
|---|---|---|
| 커밋 제목 | `type(scope): 명사구` | `refactor(chat): 이전 대화 목록을 세션 스토리지로 이전` |
| PR 제목 (티켓 있음) | `[티켓ID] 명사구` | `[PROJ-123] 이전 대화 목록의 세션 스토리지 이전` |
| PR 제목 (티켓 없음) | `type(scope): 명사구` | `refactor(chat): 이전 대화 목록의 세션 스토리지 이전` |
| PR 본문, 커밋 본문 | 서술체 | 이전 대화 목록을 메모리 캐싱에서 세션 스토리지로 옮겼다. |

명사로 끝낸다고 명사만 이어붙이라는 뜻은 아니다. 조사는 살린다 — "대화 목록 세션 스토리지 이전"
처럼 조사를 다 빼면 무엇을 무엇으로 바꿨는지가 안 읽힌다. F-6(복합명사 압축)이 여기서도 산다.

윤문할 때 제목의 명사구 종결을 서술형으로 되돌리지 않는다. 이 절이 그 자리의 근거다.

## 명사로 뭉치지 말고 풀어 말하기 (자주 놓치는 사각지대)

가장 티 나는 AI 흔적은 번역투나 헤징이 아니라 **개념을 명사 덩어리로 압축하는 습관**이다.
사람은 대화, 리뷰 코멘트에서 "무엇을 왜 했는지"를 동사로 풀어 말하지, 명사구를 이어붙여 뭉치지 않는다.
아래 표는 실제 리뷰 코멘트에서 나온 교정 사례다. 패턴만 참고하고 문장은 복붙하지 않는다.

| AI가 쓴 것 (before) | 사람이 쓸 것 (after) | 원인 |
|---|---|---|
| 시안 정합 버그픽스 잘 확인했습니다 | 디자인 시안이랑 다르게 나오던 거 고친 거 잘 봤어요 | 명사구 압축(F-6) |
| Copilot이 짚은 주석 건도 반영되셨네요 | Copilot이 남긴 코멘트도 반영하셨네요 | 사무투 분류사 "건"(I-5) + 코드 용어 "주석" |
| 유지보수성 관련해서 한 가지만 작게 남겨요 | 나중에 유지보수할 때 생각해서 코멘트 하나만 남길게요 | 명사화 "-성"(F-4) + "관련해서"(A-5) + 목적어 생략 |
| 규칙을 전 소비자에게 배선했습니다 | 규칙을 소비자 전부에 연결해뒀어요 | 기술 비유 명사 "배선"(F-7) |
| 코멘트에서 지식을 증류해 반영했어요 | 코멘트에서 쓸 만한 걸 추려서 반영했어요 | 기술 비유 명사 "증류"(F-7) |
| 강등 방향도 맞게 갔습니다 | 심각도 내린 것도 맞는 방향 같아요 | 한자어 명사 "강등"(→ 동사로) + 추상명사에 이동 동사 |
| c: 코멘트 여섯 건은 매끄럽게 다듬는 수준이고 | c: 코멘트 여섯 개는 가볍게 손보면 되는 것들이에요 | 형식명사 "수준"으로 정도 뭉개기 + 사물을 세니 "개"(I-5) |
| 두 가지 짚을 것 | 제가 봤을 때는 확인이 필요한 게 2건 있습니다 | 수량 예고(C-14) + 명사구 종결(E-8) + 화자 소거(G-4) |

**문장을 명사구로 끝내지 말 것.** "두 가지 짚을 것", "확인할 것", "고려할 점"처럼 서술어 없이
관형형과 의존명사로 끊으면 목차 항목처럼 읽힌다. 사람은 말할 때 문장을 명사구로 안 끝낸다.
"짚어볼 게 있습니다"처럼 서술어를 붙인다. 판단을 말하는 자리면 화자까지 남겨
"제가 봤을 때는 확인이 필요합니다"로 간다 — G-4와 겹치는 자리다. 헤딩이나 체크리스트 항목,
규범 문서에서 소제목 역할을 하는 볼드 도입구는 명사구 종결이 정상 문법이라 대상이 아니다
(ai-tell E-8). **PR 제목과 커밋 제목도 대상이 아니다** — 아래 "제목은 개조식, 본문은 서술체"를 본다.

**개수를 앞세워 예고하지 말 것.** "두 가지 짚을 것", "세 가지 이유가 있습니다"처럼 할 말의 개수를
먼저 세어 선언하고 시작하면 발표문이 된다. 사람은 말하다 보니 몇 개가 되는 것이지 미리 세지 않는다.
개수를 뒤로 보내 결과로 붙인다 — "확인이 필요한 게 2건 있습니다". 다만 개수가 대상의 고정 속성일
때는 그냥 사실이다. 게슈탈트 원리가 실제로 다섯 개라 "다섯 가지 원리"는 고칠 자리가 아니다
(ai-tell C-14).

**의견에는 화자를 남길 것.** "확인이 필요합니다"는 사실 선언처럼 읽히지만 실제로는 내 판단이다.
"제가 봤을 때는", "제 생각엔"을 붙여 누가 하는 말인지 밝힌다. 이 voice의 본질이 제안이지 판정이
아니라서, 화자가 지워지면 같은 내용이라도 통보가 된다. 헤징을 걷어내라는 규칙과 방향이 반대라
경계를 지킨다 — 사실 서술에 붙은 "~로 보인다"는 빼고 판단에서 빠진 화자는 넣는다 (ai-tell G-4).

**"수준"으로 정도를 말하지 말 것.** "다듬는 수준", "확인만 하는 수준"처럼 쓰면 정도를 말하려던 게
채점처럼 읽힌다 — "수준이 낮다"의 등급 어감이 딸려오기 때문이다. 남의 코드를 두고 쓰면 특히 그렇다.
범위를 말할 때는 **"정도"** 를 쓰고 가능하면 형식명사를 빼고 동사로 푼다("가볍게 손보면 되는 것들") (ai-tell I-8).

**목적어를 생략하지 말 것.** "한 가지만 작게 남겨요"처럼 무엇을 남기는지(코멘트·의견)를 빼고
형식 수량사("한 가지")와 어색한 부사("작게")로 때우면 붕 뜬다. "코멘트 하나 남길게요",
"의견 하나만 보탤게요"처럼 목적 명사를 살린다.

**추상명사에 이동 동사를 붙이지 말 것.** "방향도 맞게 갔습니다", "결론이 그쪽으로 갔어요"처럼
방향, 결론, 판단 같은 추상명사를 스스로 움직이게 만들면 붕 뜬다. 방향 자체가 가는 게 아니라
무언가가 그 방향으로 가는 것이다. "맞는 방향 같아요", "그렇게 결론 냈어요"처럼 사람이나
대상을 주어로 되돌린다 (ai-tell D-9, D-5 의인화 추상 주어의 사촌).

**추상명사에 측량 동사를 붙이지 말 것.** "근거를 재봤는데", "의견을 달아봤는데"처럼 재다나
달다처럼 물리적으로 계측하는 동사를 근거, 의견, 판단 같은 추상명사에 붙이면 붕 뜬다. 실제로
저울에 올린 게 아니라 검토하거나 확인한 것이다. "근거를 확인해봤는데", "의견을 검토해봤는데"처럼
사람이 하는 행위 동사로 되돌린다 (ai-tell F-8, F-7 물리 동사 도피의 사촌). 목적어를 근거, 의견,
판단 같은 추상명사로 한정해서 탐지기가 본다 — "온도를 재봤는데"의 멀쩡한 물리적 용법은 목적어가
달라서 안 걸린다.

**얽힌 것에는 풀다, 막힌 것에는 해소하다.** "오해를 풀다", "갈등을 풀다"처럼 얽혀 있는
대상에는 풀다가 맞는다. 그런데 "진입을 막고 있던 두 가지를 풉니다"처럼 막혀 있는 대상(문제,
이슈, 장벽)에는 풀다가 안 맞는다 — 얽힌 게 아니라 막힌 거라서다. "두 가지 문제를 해소합니다",
"막고 있던 이슈를 해결합니다"처럼 막힘에는 해소하다나 해결하다를 쓴다. 판정법 — 대상이 실
뭉치처럼 얽혀 있는지, 벽처럼 막고 있는지 먼저 본다.

## 리뷰 코멘트를 "지적"이라고 부르지 않는다 (ai-tell I-7)

산출물에서 리뷰 코멘트를 가리킬 때 "지적"을 쓰지 않는다. 상대를 잡아세우는 뉘앙스가 붙어서
같은 내용이라도 제안형 어투와 어긋난다. 이 voice의 본질은 제안이지 판정이 아니다.

| 쓰지 말 것 | 쓸 것 |
|---|---|
| 지적 8건 다 반영된 거 확인했습니다 | 남겼던 의견 8개 다 반영된 거 확인했어요 |
| 제가 드린 지적은 | 제가 드렸던 의견은 |
| 이전 지적에서 말씀드린 대로 | 앞서 남긴 코멘트에서 말씀드린 대로 |
| 지적해주신 부분 고쳤습니다 | 짚어주신 부분 고쳤어요 / 남겨주신 의견 반영했어요 |

- 내가 남긴 것을 가리킬 때: **"남겼던 의견", "드렸던 의견", "남긴 코멘트"**
- 상대가 남긴 것을 가리킬 때: **"짚어주신 부분", "남겨주신 의견"** — 받는 쪽에서도 같은 결로 간다
- 사물을 셀 때는 **"개"** 를 쓴다. "코멘트 8개", "버그 3개", "티켓 8개" (ai-tell I-5)

> **"건"을 글자로 매칭하면 안 된다.** 같은 글자가 층위마다 다르게 쓰인다.
>
> | 고칠 것 | 그대로 둘 것 |
> |---|---|
> | "지적해주신 **건**은 확인했습니다" — 사무투 분류사 | "안 돌려본 **건** PR에 적어두셔서" — "것은"의 준말 |
> | "코멘트 여섯 **건**은 다듬는 정도예요" — 사물을 센다 | "제가 놓친 **건** 맞아요" — "것은"의 준말 |
> | "버그 8**건** 고쳤어요" — 사물을 센다 | "안 돌려본 **건** 확인했어요" — "것은"의 준말 |
>
> 준말 "건"은 구어에서 자연스러운 표현이라 늘려 쓰면("안 돌려본 것은") 오히려 딱딱해진다.
> 수량 자리는 **세는 사물이 바로 앞에 적혀 있을 때만** 본다. 적혀 있으면 "개"로 간다
> ("코멘트 여섯 개", "버그 8개"). 무엇을 세는지 문장에 없으면("확인이 필요한 게 2건 있습니다")
> 판정할 근거가 없으니 그대로 둔다.
>
> **이 표는 산출물 문장에만 적용된다.** 이 문서나 룰 문서가 자기 데이터를 세어 적는
> 자리("인라인 리뷰 1,321건", "표본 282건")는 대상이 아니다 — I-7이 같은 예외를 갖는 것과
> 같은 이유다.

이 규칙은 산출물 문장에만 적용된다. 룰 문서나 스킬 문서가 개념을 설명할 때는 "리뷰 코멘트",
"코멘트"라는 중립어를 쓴다 — 룰 문서가 금지 어휘를 본문에서 쓰면 산출물로 새기 때문이다.

## 기계적 점검 (어투는 아니지만 자주 틀리는 것)

리뷰 코멘트는 커밋 해시나 브랜치명, 토큰 값을 문장 안에 그대로 섞기 때문에, 조사 처리에서 반복적으로
어긋난다. 어투 문제가 아니라 맞춤법이라 humanize 등급과 무관하게 그냥 고친다.

- **식별자나 코드 뒤 조사는 붙여 쓴다**: `6564d04 에서` → `6564d04에서`, `c: 로` → `c:로`,
  `main 에` → `main에`
- **외래어 + 하다도 붙여 쓴다**: `Approve 합니다` → `Approve합니다` (또는 "승인합니다")
- **조사는 백틱 밖에 둔다**: <code>\`c:로\`</code> 가 아니라 <code>\`c:\`</code> 로 — 백틱 안은
  실제 코드나 값만

## humanize-monolith 와의 관계 (중요)

`humanize-monolith`의 S1 규칙은 **AI-tell 제거용**이라, 이 voice와 충돌하는 부분이 있다.
아래는 **AI-tell이 아니라 작성자의 진짜 voice이므로 깎지 말 것.**

| humanize가 깎으려는 것 | 실제로는 |
|------------------------|----------|
| "~것 같아요", "~인 것 같습니다" (헤징) | **보존** — 제안형 어투의 핵심. 표본 282건. 단 밀도는 관리한다(위 "이 숫자는 분포지 지침이 아니다"). |
| "~해주세요~", "~할게요~" 물결 친근체 | **보존** — voice 시그니처. |
| "개인적으로", "제 취향이긴 한데" | **보존** — 의견 프레이밍 방식. |
| 🙏 😀 👍 등 이모지 (코멘트당 1개 안팎) | **보존** — 온기. |

반대로 두 말투 모두에서 **제거**할 진짜 AI-tell:
- "결론적으로", "요약하자면", "이를 통해", "~를 수행합니다" 의인화 주어
- 과장 어휘("핵심적으로", "시사하는 바가 크다"), 콜론 부제, 이모지 남발, 문두 접속사 반복
- **가운뎃점(·) 나열 남발** — 본문에서 "A·B·C" 압축은 기계 티. 쉼표나 "A랑 B하고 C"로 푼다 (ai-tell C-12)
- **명사구 압축, 사무투 분류사** — "시안 정합 버그픽스", "주석 건" 같은 명사 뭉치는 동사로 풀고 "건"은 구체 명사로 (ai-tell F-6·I-5, 리뷰 코멘트에선 S1)
- **기술 비유 명사** — "증류·배선·결정화·평탄화" 같은 화학, 전기 어휘 차용은 일상 동사로 (ai-tell F-7, 리뷰 코멘트에선 S1)
- **"지적"**(ai-tell I-7) — 리뷰 코멘트를 가리키는 말로 쓰지 않는다. "남겼던 의견", "짚어주신 부분"으로 (위 "리뷰 코멘트를 '지적'이라고 부르지 않는다")
- **`c:`/`r:`/`a:` 접두어를 어투 시그니처처럼 흉내 내기, `[출처]` 대괄호 태깅, "…권장." 체언 종지** — Claude가 만든 가짜 시그니처. 단, 팀이 채택한 리뷰 강제성 라벨은 예외다

## 적용 규칙 요약

1. 단정하지 말고 제안한다: "~하는 게 좋을 것 같아요 / 좋아보입니다 / ~는 건 어떨까요?"
2. 코멘트엔 이유를 "~해서요"로 붙인다. 의견은 "개인적으로"로 연다.
3. 사소, 명확한 건 짧은 지시 한 줄로("key 빠져있습니다.").
4. 확신이 없으면 단정 대신 질문한다("~동작이 제대로 되나요?").
5. 수정 제안은 코드, 토큰 값까지 구체적으로.
6. 친근체, 물결, 이모지는 자연스럽게, 과하지 않게.
7. `c:`/`r:`·`a:`를 어투처럼 흉내 내지 않는다. 팀이 채택한 리뷰 강제성 라벨은 예외다. `[출처]`·"권장." 은 쓰지 않는다 (Claude artifact).
8. 개념을 명사로 뭉치지 말고 동사로 푼다("시안 정합 버그픽스" → "시안이랑 다르게 나오던 거"). "건" 같은 사무투 분류사와 생략된 목적어를 되살린다.
9. 리뷰 코멘트를 "지적"이라 부르지 않는다 (I-7). 내 것은 "남겼던 의견 / 드렸던 의견", 상대 것은 "짚어주신 부분 / 남겨주신 의견".
10. PR 제목과 커밋 제목은 명사로 끝낸다. 본문만 서술체다 (E-8 예외).
