# Content Playbook — 슬라이드 유형별 콘텐츠 작성

슬라이드 유형별 콘텐츠 뼈대. 각 유형은 `presentation-designer`의 슬라이드 타입(`presentation-designer/AGENT.md`의 Layout Patterns)과 1:1로 맞물린다. writer가 여기 형식으로 쓰면 designer가 그대로 타입을 배정해 HTML로 옮긴다. 공통 원칙은 AGENT.md의 작성 원칙을 따르고, 한국어 문장 규칙은 `../../_shared/references/style-guide.md`를 공유한다.

## 유형 ↔ designer 슬라이드 타입 매핑

| 콘텐츠 유형 | designer 슬라이드 타입 | 언제 쓰나 |
|------------|----------------------|----------|
| 표지 (cover) | `cover` | 발표 제목, 부제, 발표자·날짜 |
| 목차 (agenda) | `toc` / `agenda` | 발표 흐름 예고 |
| 수치 강조 (stats) | `slide--stats` (3-col) | 핵심 지표 2–3개를 큰 숫자로 |
| 선언 (statement) | `slide--statement` | 발표를 관통하는 한 문장, 또는 도입부 기대치 선언 |
| 비교 (compare) | `slide--compare` / `slide--split` | Before/After, 대안 대조, 익숙한 개념과의 대비 |
| 과정 (process) | `slide--process` / `slide--list` | 단계·순서·프레임워크 |
| 인용 (quote) | `s-quote` | 고객 증언, 인용문 |
| 시나리오 퀴즈 (scenario-quiz) | `slide--compare`(문제) + `slide--statement`(정답) | 교육형 발표에서 판단력을 스스로 검증 |
| 마무리 (closing) | `end` / `closing` | CTA, 다음 행동, 또는 체크리스트형 요약 |

---

## 1. 표지 (cover)

발표의 첫인상. 제목 한 줄로 이 발표가 무엇을 약속하는지 드러낸다.

```
- 제목: [발표가 이루려는 것 — 주제 명사가 아니라 약속으로]
- 부제: [한 줄 보조 설명 — 선택]
- 메타: [발표자, 팀, 날짜]
```

원칙: 제목은 "3분기 리뷰"보다 "3분기에 증명한 것"처럼 청중이 기대할 결론을 살짝 연다.

## 2. 목차 (agenda)

발표 흐름을 예고해 청중이 지도를 갖게 한다.

```
- 섹션 1: [한 구절]
- 섹션 2: [한 구절]
- 섹션 3: [한 구절]
```

원칙: 항목은 3–5개. 명사 나열이 아니라 각 섹션이 답할 질문으로 쓰면 더 좋다.

## 3. 수치 강조 (stats)

핵심 지표를 큰 숫자로 각인시킨다. designer가 3-col stats로 배치한다.

```
- 지표 1: [숫자] / [라벨] / [맥락 한 줄 — 목표 대비, 전기 대비]
- 지표 2: [숫자] / [라벨] / [맥락 한 줄]
- 지표 3: [숫자] / [라벨] / [맥락 한 줄]
```

원칙: 한 슬라이드에 지표 3개까지. 각 숫자 아래 맥락 한 줄을 반드시 붙인다 — 단독 숫자는 청중이 "그래서?"를 메워야 한다.

## 4. 선언 (statement)

발표를 관통하는 한 문장을 전면에 세운다. 텍스트가 적을수록 강하다.

```
- 선언문: [8–12단어 이내의 한 문장]
- 뒷받침 노트: [발표자가 말로 풀 근거 — 슬라이드에는 안 얹음]
```

원칙: 슬라이드에는 문장 하나만. 설명은 발표 노트로 뺀다.

**특수 용도 — 기대치 선언.** 교육형 발표 도입부에서 "무엇이면 성공인지"를 먼저 못박을 때도 이 유형을 쓴다. 실패 조건과 성공 조건을 ❌/✅로 나란히 대비하면 효과적이다.

```
- ❌ 실패 조건: [흔히 하는 착각 — "~을 외웠으면 실패"]
- ✅ 성공 조건: [진짜 목표 — "~을 판단할 수 있으면 성공"]
```

## 5. 비교 (compare)

Before/After나 대안을 나란히 놓아 차이를 보게 한다.

```
- 왼쪽 (Before/안 A): [제목] + 포인트 1–2줄
- 오른쪽 (After/안 B): [제목] + 포인트 1–2줄
- 결론 한 줄: [무엇이 왜 나은가]
```

원칙: 양쪽을 같은 축으로 비교한다. 결론 한 줄로 청중이 어느 쪽인지 알게 한다.

**특수 용도 — 익숙한 개념과의 대비.** 처음 듣는 개념을 설명할 때, 청중이 이미 쓰는 익숙한 대상을 왼쪽에 놓고 새 개념을 오른쪽에 놓아 "뭐가 다른가"로 체감시킨다 (예: `Ctrl+S`로 저장 vs Commit으로 저장).

## 6. 과정 (process)

단계나 프레임워크를 순서대로 보인다. designer가 process/list로 배치한다.

```
- 단계 1: [동사형 제목] + 한 줄 설명
- 단계 2: [동사형 제목] + 한 줄 설명
- 단계 3: [동사형 제목] + 한 줄 설명
```

원칙: 단계는 3–5개. 각 단계 제목은 동사로 시작해 행동이 보이게 한다.

## 7. 인용 (quote)

고객 증언이나 인용으로 신뢰를 더한다.

```
- 인용문: "[실제 발화 그대로]"
- 출처: [이름 / 역할 / 소속]
```

원칙: 인용은 짧게. 지어내지 않는다 — 실제 발화가 없으면 작성자에게 요청한다.

## 8. 시나리오 퀴즈 (scenario-quiz)

교육·트레이닝형 발표에서 정보 전달을 판단력 확인으로 바꾼다. 문제 슬라이드는 designer의 `slide--compare`(상황 설명 + 선택지)로, 정답 슬라이드는 `slide--statement`(정답 강조 + 해설)로 배정한다.

```
[문제]
- 상황: [실제 있을 법한 시나리오 한두 줄]
- 질문: [이게 문제가 될까요? / 뭐가 맞을까요?]
- 선택지: ① ... ② ... ③ ...

[정답]
- 정답: [번호 + 핵심 한 줄]
- 해설: [왜 그런지 — 원리로 연결]
```

원칙: 명령어·정의 암기가 아니라 판단을 묻는다. 도입부에서 선언한 기대치(선언 유형의 "성공 조건")를 실제로 검증하는 문항으로 만든다. 3–5문항이 적당하다 — 그 이상은 지루해진다.

## 9. 마무리 (closing)

발표를 다음 행동으로 닫는다. 보고가 아니라 요청으로 끝낸다.

```
- 마무리 메시지: [청중이 가져갈 마지막 한 문장]
- CTA: [청중이 지금 할 행동 — 결정, 승인, 다음 미팅 등]
```

원칙: 마지막 슬라이드는 "감사합니다"로 낭비하지 않는다. 청중이 방을 나가며 할 일 하나를 남긴다.

**변형 — 체크리스트형 마무리.** 여러 개념을 다룬 교육형 발표는 CTA 대신 개념당 한 줄 정의로 요약해도 된다. ✅ 목록으로 훑으면 발표자 없이 슬라이드만 봐도 절반은 복기된다.

```
- ✅ [개념 A] = [한 줄 정의]
- ✅ [개념 B] = [한 줄 정의]
- ✅ [개념 C] = [한 줄 정의]
```
