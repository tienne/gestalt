# Report Register — 보고서용 한국어 문체

진행현황, 성과 분석, 제안서, 의사결정 메모처럼 읽는 사람이 근거를 대조하고
결정을 내려야 하는 문서에만 적용한다. PR, 슬랙, 지라, 리뷰 코멘트에는 적용하지
않는다. 그 자리에서 보고서식 치환을 쓰면 작성자 어투가 불필요하게 딱딱해진다.

원칙은 간단하다. **글자 수가 아니라 해석의 폭을 줄인다.** 낯선 한자어나
외래어를 늘리는 것이 목적이 아니다. 책임, 시점, 대상의 구분이 더 또렷해질 때만
구체적인 말을 고른다.

## 1. 적용 범위와 어미

- 보고 본문은 평서체 `~한다/~이다`를 기본으로 한다.
- 송부 메일, 협의 요청, 대외 안내는 합니다체로 별도 작성한다.
- 문서 안에서 두 어미를 섞지 않는다. 인용문, 코드, 고유한 고객 문구는 예외다.
- `됐다/했다`처럼 구어로 줄어든 과거형은 본문에서 `되었다/하였다`로 정리한다.
  인용문과 코드 블록은 바꾸지 않는다.

이 기본값은 독자별 voice보다 우선하지 않는다. 경영진이나 타팀에 보내는 본문을
합니다체로 쓰기로 한 경우에는 그 선택을 문서 전체에 일관되게 적용한다. 이때도
송부 메시지와 보고 본문은 섞지 않는다.

## 2. 의미역을 좁히는 치환

아래 표는 기계적 치환표가 아니다. 왼쪽 동사에 서로 다른 목적어를 넣어도 모두
자연스러우면, 목적어가 가리키는 관계에 맞는 오른쪽 동사를 고른다.

| 넓은 표현 | 문맥별 선택 | 구분 기준 |
|---|---|---|
| 다룬다 | 한정한다, 규정한다, 정의한다 | 범위, 규칙, 개념 |
| 맞춘다 | 정합한다, 정렬한다, 보정한다 | 논리, 위치, 값 |
| 바꾼다 | 변환한다, 대체한다, 개정한다 | 형식, 대상, 문서 |
| 넘긴다 | 전달한다, 이관한다, 위임한다 | 데이터, 업무, 권한 |
| 적는다 | 명시한다, 기재한다, 기록한다 | 규정, 항목, 이력 |
| 나온다 | 도출된다, 산출된다, 확정된다 | 결과, 계산, 승인 |
| 넣는다 | 포함한다, 등재한다, 삽입한다 | 범위, 목록, 위치 |
| 고친다 | 수정한다, 보완한다, 개정한다 | 오류, 미비, 문서 |
| 잡는다 | 검출한다, 산정한다, 고정한다 | 이상, 수치, 값 |
| 늘어난다 | 향상된다, 증가한다, 연장된다 | 품질, 수량, 기간 |
| 막는다 | 차단한다, 방지한다 | 경로, 사태 |
| 생긴다 | 발생한다, 형성된다 | 사건, 구조 |

정밀도가 늘지 않으면 바꾸지 않는다. 예를 들어 팀이 실제로 쓰는 용어나 코드의
식별자를 더 격식 있게 보이게 하려고 바꾸지 않는다.

## 3. 서술은 용어와 분리한다

도메인 용어는 그대로 두고 그 용어를 설명하는 동사와 상태만 고친다. 물리 은유와
의인화는 사실 상태로 환원한다.

| 피할 서술 | 보고서 서술 |
|---|---|
| 큐가 밀린다 | 큐에 적체가 발생한다 |
| 값이 튄다 | 값에 이상치가 발생한다 |
| 템플릿이 죽었다 | 템플릿이 비활성 상태다 |
| 로그가 쌓인다 | 로그가 누적된다 |
| 문서가 다룬다 | 문서는 범위를 한정한다, 용어를 정의한다 |

API, enum, 필드명, 제품명, 조직 내부에서 굳어진 개념어는 원문 표기를 보존한다.
영문 표기를 한글 음차나 반대 방향으로 일괄 변환하지 않는다.

## 4. 보고서 프레이밍

문장만 윤문하기 전에 절 단위로 아래를 확인한다.

1. **제목은 주제를 가리킨다.** 자유 서술 절과 표 항목은 명사구로 적고 주장은 본문에 둔다.
2. **결과를 먼저 둔다.** 각 항목은 확인된 수치나 현재 상태를 먼저 제시하고 배경과 원인은 뒤에 둔다.
3. **결함을 숨기지 않고 개선 경로를 드러낸다.** "무엇이 안 됐나"만 나열하지 말고
   어떤 기준이나 경로를 정비할지 함께 적는다.
4. **리스크에는 대응을 붙인다.** 대응이 없는 리스크는 경고가 아니라 불확실성으로 분류하고
   외부 문서에서는 별도 확인이 필요하다고 표시한다.
5. **요청 전에 판단을 낸다.** 상대에게 결정을 넘기기 전에 우리 안, 산정 근거, 조정 가능한
   범위를 먼저 제시한다.
6. **문서 사용법을 본문에서 빼낸다.** 첫 문단은 이 문서를 왜 만들었는지가 아니라,
   독자가 알아야 할 현재 상태와 결정 사항으로 시작한다.

## 5. 수치와 상태

측정값, 구현 상태, 아직 확인하지 못한 값을 같은 무게로 적지 않는다. 주장 바로 옆에
상태를 붙인다.

| 상태 | 사용할 때 |
|---|---|
| 측정됨 | 실제 관측 또는 집계가 끝난 값 |
| 구현됨 | 수단은 존재하지만 해당 조건에서 검증하지 않은 상태 |
| 미측정 | 아직 값을 확인하지 않은 상태 |

조직의 용어가 있으면 그 용어를 쓴다. 상태 표기는 수치에 근거가 없다는 사실을
가리는 장식이 아니라, 다음 검증 대상을 드러내는 정보다.

## 6. 작업 순서

1. 초안에서 사실, 수치, 근거, 요청을 확정한다.
2. 이 레퍼런스로 의미역, 상태, 절 프레이밍을 검토한다.
3. `humanize-monolith`으로 번역투와 AI-tell만 제거한다. 이 단계에서 절 순서와 정보는 바꾸지 않는다.
4. 파일 기반 윤문이면 `gestalt humanize-check --register report`로 어미 혼용과 기존 S1 규칙을 확인한다.
