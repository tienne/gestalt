# 고치기 전에 수정 전 화면을 찍어 둔다

이 문서는 코드를 고친 뒤 `pr` 스킬로 PR을 올리는 스킬이 함께 쓰는 규칙이다. `execute`가 첫 태스크를 실행하기 직전에 이 절차를 돈다. `solve`는 `execute`를 거치므로 따로 부르지 않는다.

컨덕터 워커는 주문 설명이 "원인 파악 → 수정 → 검증" 같은 단계를 직접 적으면 `execute`를 안 거치고 바로 고친다. 그래서 워커 지시서의 규칙 절이 PR을 만드는 체인(ship, pr)마다 이 절차를 따로 시킨다(`src/conductor/launcher.ts`의 `buildWorkerPrompt`). 찍은 기록은 ship이 `pr` 1단계 4번 답으로 넘긴다.

## 왜 미리 찍나

`pr` 스킬 5.5단계는 PR 본문에 수정 전/후 스크린샷을 붙인다. 그런데 PR을 올릴 때는 코드가 이미 바뀌어 있어서 수정 전 화면을 다시 띄우기 어렵다. 배포된 주소가 없으면 base를 체크아웃해서 서버를 따로 띄워야 한다. 고치기 직전에는 로컬에 떠 있는 화면이 곧 수정 전 화면이라 그때 찍어 두면 이런 수고가 없다.

## 언제 찍나

이 절차가 [화면 변경 판정](./screen-change.md)의 첫 확인이다. 계획(ExecutionPlan)의 태스크가 건드릴 파일로 그 문서의 "후보 찾기"를 돈다. 계획 없이 도는 컨덕터 워커는 고치려는 파일을 같은 기준으로 판정한다. 확장자만 보지 않는다. HTML 문자열을 만드는 `.ts`나 화면 문구, 표시 조건, 화면에 찍히는 값을 만드는 계산도 근거가 있으면 후보다.

후보가 없으면 찍지 않고 `manifest.json`에 `"verdict": "none"`과 이유 한 줄만 남긴다. PR 단계의 두 번째 확인이 이 기록을 보고 첫 확인을 했는지 안다.

아래 둘 중 하나면 찍지 않는다. 지금 화면이 이미 수정 전이 아니기 때문이다.

- 이 브랜치에 수정 전 기록(`manifest.json`)에 `pairs`가 이미 있다. Evolve로 다시 돌거나 세션을 이어서 할 때 덮어쓰지 않는다.
- base 대비 후보 파일이 이미 바뀌어 있다. 아래 명령으로 바뀐 파일을 보고 후보 찾기 기준을 댄다.

```bash
# pr-base.md 4절 블록으로 baseRef를 구한 뒤
git diff --name-only "$baseRef" -- .
```

후보가 이미 바뀌어 있으면 찍지 않고 "이미 고친 화면 파일이 있어 수정 전 캡처를 건너뛰었어요"라고 한 줄 남긴다. 그 후보는 `manifest.json`의 `unverified`에 "전 이미지 없음"으로 적는다.

## 어느 화면을 찍나

후보마다 영향받는 화면과 대표 상태를 [화면 변경 판정](./screen-change.md#영향받는-화면과-상태-찾기)대로 정한다. 빈 화면 하나만 찍지 않고 변경이 드러날 상태(진행률이면 시작, 중간, 완료)를 상태마다 찍는다. 레포의 테스트 fixture나 렌더링 테스트로 상태를 만들 수 있으면 그걸 쓴다.

바뀔 화면의 주소를 아래 순서로 찾는다.

1. 사용자가 이번 대화에서 준 주소
2. 스펙, 지라 티켓, handoff 지시서에 적힌 화면 주소
3. 변경 파일에서 라우트가 확실히 드러나는 경우 (Next.js의 `app/<경로>/page.tsx`나 `pages/<경로>.tsx`처럼 파일 위치가 곧 주소인 구조)

주소가 없어도 마크업 함수를 테스트 헬퍼로 HTML 파일에 떨어뜨릴 수 있으면 그 파일을 `$shotTmp` 아래에 두고 `file://` 주소로 찍는다. 이때 `url`에 그 파일 경로를, `state`에 넣은 데이터를 적는다. 수정 후에도 같은 데이터로 다시 만들어야 하기 때문이다.

셋 다 없으면 사람에게 묻는다. 추측한 주소로 찍지 않는다. 엉뚱한 화면을 수정 전이라고 붙이면 리뷰어가 잘못 판단한다.

```
화면이 바뀔 수 있는 작업이라 고치기 전에 수정 전 화면을 찍어 두려고 해요.
찍을 로컬 주소를 알려주세요. (예: http://localhost:3000/list)
없으면 "없음"이라고 해 주세요. 그러면 PR 올릴 때 다시 물어볼게요.
```

## 어떻게 찍나

로컬 서버가 떠 있어야 한다. 주소에 `curl -s -o /dev/null -w '%{http_code}'`를 보내 응답이 없으면 서버를 대신 띄우지 않고 사람에게 알린다. 워크트리 여럿이 같은 포트를 쓰면 다른 워크트리 화면이 찍힐 수 있으므로 띄우는 일은 사람이 한다.

브라우저 도구는 [`pr` 스킬 5.5단계의 업로드](../pr/SKILL.md#업로드)와 같은 순서로 고른다(aside, chrome-devtools). 뷰포트는 모바일 웹이면 390×844, 아니면 1280×800이다. 수정 후 화면도 같은 데이터, 같은 크기, 같은 테마로 찍어야 비교가 되므로 셋을 기록해 둔다.

저장 위치는 `pr` 스킬 5.5단계와 같은 자리다. 레포 작업 트리 밖이라 커밋에 섞이지 않는다.

```bash
shotTmp="$(cd "$(git rev-parse --git-common-dir)" && pwd)/gestalt-pr/shots/$(git rev-parse --abbrev-ref HEAD | tr '/' '_')"
mkdir -p "$shotTmp"
```

화면과 상태마다 `"$shotTmp/<label>-before.png"`로 저장하고 `"$shotTmp/manifest.json"`을 파일 쓰기 도구로 남긴다. 꼴은 [화면 변경 판정의 기록 꼴](./screen-change.md#기록-꼴)이다. `check`는 `before-edit`이고 아직 수정 후가 없으니 후보별 `verdict`는 비워 둔다. 찍지 못한 화면은 `unverified`에 이유와 함께 적는다.

```json
{
  "check": "before-edit",
  "baseRef": "<찍을 때의 baseRef>",
  "headSha": "<찍을 때의 HEAD>",
  "candidates": [
    { "file": "src/list/progress.ts", "evidence": "목록의 진행률 문구를 만든다", "screens": ["목록"], "states": ["시작", "중간", "완료"] }
  ],
  "pairs": [
    {
      "label": "목록-중간",
      "url": "http://localhost:3000/list",
      "state": "중간",
      "viewport": "1280x800",
      "theme": "light",
      "before": "<절대 경로>/목록-중간-before.png"
    }
  ]
}
```

캡처에 실제 고객 정보(이름, 전화번호, 주소)가 보이면 이 자리에서 바로 사람에게 알린다. PR 올릴 때까지 미루지 않는다.

## 사람에게 못 물을 때

컨덕터 워커(`GESTALT_CONDUCTOR_WORKER_ID`가 있는 세션)는 사람에게 묻고 기다리지 않는다. 주소를 위 1~3번에서 못 찾았거나 서버가 안 떠 있으면 찍지 않고 넘어간다. 대신 `manifest.json`에 후보와 이유를 남겨 PR 단계에서 알 수 있게 한다. 못 찍은 후보는 PR에서 "확인 필요"로 시작한다. 화면 변화 없음으로 넘기지 않는다.

```json
{
  "check": "before-edit",
  "candidates": [{ "file": "src/list/progress.ts", "evidence": "목록의 진행률 문구를 만든다", "screens": ["목록"] }],
  "skipped": "주소를 못 찾음",
  "unverified": [{ "screen": "목록", "reason": "주소를 못 찾음" }]
}
```

찍지 못했다고 실행을 멈추지 않는다. 스크린샷은 PR을 읽기 쉽게 하려는 것이지 작업 완료 조건이 아니다.

## PR 단계에서 쓰는 법

`pr` 스킬은 1단계에서 `manifest.json`을 먼저 읽고 최종 diff로 [두 번째 확인](./screen-change.md#언제-판정하나)을 한다. 수정 전 이미지가 있으면 그 화면은 다시 묻지 않고 같은 주소, 상태, 뷰포트, 테마로 수정 후 화면만 찍는다. 자세한 건 `pr` 스킬 5.5단계에 있다.
