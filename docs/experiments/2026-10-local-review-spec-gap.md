# 로컬 PR 리뷰 코멘트 중 요구사항 공백에서 나온 몫

작성 2026-10-02. 분류 원자료는 같은 디렉토리의 [`2026-10-local-review-spec-gap.csv`](./2026-10-local-review-spec-gap.csv)에 스레드 id별로 있다.

## 묻는 것

권윤학님 본인 코드를 로컬 PR(ship, local-pr)로 리뷰받았을 때 나온 코멘트 중에서, 착수 전에 요구사항이 분명했으면 안 나왔을 것이 얼마나 되는가. 많으면 인터뷰와 스펙 단계를 손볼 가치가 있다. 적으면 리뷰 쪽에 계속 투자한다.

## 데이터와 방법

- 출처는 메인 체크아웃의 `.gestalt/reviews.db`다. `sqlite3 .backup`으로 스크래치에 사본을 떠서 그 사본만 열었다.
- 기간은 2026-08-31부터 10-01까지다. 로컬 PR 28개에 `pr.comment.added` 577건이 있다.
- 코멘트를 `threadId`로 묶으면 스레드가 336개다. 리뷰어 에이전트가 연 첫 코멘트가 336건이다. 나머지 241건은 작성자(`human:local`)가 단 대응 답글이다. 분류 단위는 스레드다. 답글은 "고쳤다, 반박했다, 미뤘다"를 판단하는 근거로만 썼다.
- 28개 중 8개는 코멘트가 하나도 없다. 그중 `07e756ea`(13라운드), `ae18cc8c`(10라운드)처럼 라운드는 돌았는데 코멘트가 DB에 안 남은 PR이 있다. 리뷰가 DB 밖 경로로 돌았던 것으로 보인다. 분류할 거리가 없어 집계에서 뺐다. 남은 대상은 PR 20개다.
- 스레드를 PR 단위로 네 묶음으로 나눠 서브에이전트 넷이 같은 기준으로 분류했다. SPEC_GAP 25건과 보조 라벨 SPEC_GAP 37건은 제가 다시 훑어 묶음 간 기준을 맞췄다. 그 과정에서 근거가 맞지 않는 보조 라벨 2건(`a03455bb`, `c5b1e903`)을 지웠다.
- SPEC_GAP은 "올바른 동작을 정하려면 누군가 결정을 내려야 했던 자리"로만 좁게 잡았다. 빠진 엣지 케이스라도 정답이 기존 코드나 규칙에서 바로 나오면 IMPL_DEFECT로 뒀다.

- `~/.gestalt/events.db`에서 같은 기간의 interview와 spec 세션을 전부 확인했다. gestalt 레포 작업은 두 개뿐이다. 9/16 `ruleSources` 설정 문서 절(spec `d6e5d2b8`)과 9/29 하네스 리뷰 강화(spec `261dbfa6`)다.
- 앞의 것은 `8142120f`, `ae18cc8c`(rule-sources)의 문서 한 절만 덮는다. 두 PR 모두 DB에 코멘트가 없다. 뒤의 것은 대응하는 로컬 PR이 없다.
- 그래서 분류한 PR 20개는 전부 interview나 spec을 안 거쳤다. "스펙을 거친 PR과 안 거친 PR"은 비교할 수 없다.
- 대신 10/01에 만든 PR 14개는 대부분 "왜" 절에 문제와 고칠 범위를 적고 시작했다. roadmap 항목 번호나 PR #36 본문의 "테스트를 쓰다 찾은 버그" 번호를 출처로 단 것들이다. 코멘트가 있는 13개의 SPEC_GAP은 스레드 155개 중 7건(4.5%)이다. 9월 PR 7개는 181개 중 18건(9.9%)이다. 9월 쪽에 룰북 PR 넷이 몰려 있어서 그 넷을 빼면 116개 중 8건(6.9%)으로 차이가 줄어든다. 9월 기능 PR이 셋뿐이라 이 차이도 근거로 쓰기는 어렵다.

## 결론

현재 데이터로는 인터뷰와 스펙 단계에 크게 투자할 근거가 약하다. SPEC_GAP은 엄격하게 잡으면 7.4%이고 보조 후보까지 다 넣어도 17.9%다. 코멘트 열에 여덟은 요구사항이 분명한 상태에서 나온 구현 결함(51.5%)과 레포 규칙, 문서 어긋남(36.6%)이다. SPEC_GAP 25건 중 10건은 룰북 PR의 룰 충돌이라 착수 전 인터뷰보다 룰 사이 겹침을 찾아주는 검사가 맞다. 기능 PR에 남는 15건은 "검증을 어디까지 보장하나", "어느 스킬이 게시하나", "실패하면 어떻게 하나" 같은 범위와 계약 질문이 대부분이었다. 이 15건은 인터뷰 전체를 돌리기보다 작업을 시작할 때 범위와 수용 기준 몇 줄을 적게 하는 가벼운 장치로 상당수 막을 수 있어 보인다. 라운드 수는 SPEC_GAP 유무보다 PR 크기를 따라간다(상관계수 0.81 대 0.03). 라운드를 줄이려면 리뷰 쪽, 특히 IMPL_DEFECT와 DOC_DRIFT를 게시 전에 먼저 잡는 쪽에 계속 투자하는 게 낫다. 다만 분류한 PR이 전부 스펙 없이 시작했기 때문에 "스펙을 거치면 줄어드는가"는 이 데이터로 답이 안 나온다. 그걸 보려면 비슷한 크기의 기능 PR 몇 개를 spec을 거쳐 만들고 같은 방식으로 비교해야 한다.
