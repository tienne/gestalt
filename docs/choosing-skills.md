# 스킬 고르기

비슷해 보이는 스킬끼리 언제 무엇을 쓸지 가르는 문서다. [README의 스킬 표](../README.md#skills)는 스킬당 한 줄이라 "interview와 solve가 뭐가 다른지", "review와 review-loop 중 무엇을 부를지" 같은 갈림길은 답하지 못한다. 여기서는 그 갈림길만 다룬다.

스킬은 하는 일의 범위와 멈추는 자리로 갈린다. 어디까지 하고 서는지, 중간에 사람의 승인을 받는지, 내 것인지 남의 것인지가 기준이다. 아래 묶음마다 차이 한 줄, 고르는 기준 표, 같이 쓰는 순서 순으로 적었다. 이름만 헷갈리는 쌍은 [헷갈리기 쉬운 쌍](#헷갈리기-쉬운-쌍)에 따로 모았다.

## 질문으로 고르기

| 지금 상황                                              | 스킬                        |
| ------------------------------------------------------ | --------------------------- |
| 요구사항이 흐릿해서 질문을 받으며 정리하고 싶다        | `interview`                 |
| 문제만 던지고 알아서 끝까지 해결해 주길 바란다         | `solve`                     |
| 스펙이 이미 있고 구현을 시작하려 한다                  | `execute`                   |
| 일을 다른 에이전트나 워크트리에 넘기려 한다            | `handoff`                   |
| 코드를 고치기 전에 어디까지 영향이 가는지 알고 싶다    | `blast-radius`              |
| 고친 뒤 커밋 전에 영향 범위를 보고 싶다                | `diff-radius`               |
| 내 브랜치를 GitHub PR로 올리려 한다                    | `pr`                        |
| 리뷰 통과까지 단계를 이어서 밀어 주길 바란다           | `ship`                      |
| 남의 PR을 한 번 리뷰하려 한다                          | `review`                    |
| 남의 PR을 승인이 날 때까지 따라가려 한다               | `review-loop`               |
| 내 PR에 달린 리뷰에 답하려 한다                        | `review-reply`              |
| 성과 보고서나 제안서, RFC를 쓰려 한다                  | `brief`                     |
| 지라 티켓이나 슬랙 메시지를 만들어 보내려 한다         | `jira-create`, `slack-send` |
| 논문이나 영상, 경쟁 서비스를 읽고 조사하려 한다        | [읽기와 조사](#읽기와-조사) |
| 위에 맞는 스킬이 없고 에이전트 하나에게 바로 묻고 싶다 | `agent`                     |

## 요구사항에서 구현까지

`interview`와 `spec`은 각자 한 단계만 하고 선다. `solve`는 세 단계를 한 루프로 돈다.

| 스킬        | 하는 일                                                                           | 서는 자리                                                     |
| ----------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `interview` | 질문을 주고받아 요구사항을 명확하게 만든다                                        | 해상도 점수가 기준(0.8)에 닿으면 선다. 스펙은 만들지 않는다   |
| `spec`      | 끝난 인터뷰 세션으로 스펙 문서를 만든다                                           | 스펙을 내면 선다. 인터뷰 세션 id가 있어야 한다                |
| `execute`   | 이미 있는 스펙을 검증된 실행 계획으로 바꾸고 태스크 실행, 평가, 개선까지 진행한다 | 스펙이 먼저 있어야 한다                                       |
| `solve`     | 인터뷰, 스펙, 실행을 한 루프로 돈다                                               | 인터뷰는 사람이 직접 답하고 스펙 생성 이후는 AI가 자율로 돈다 |

고르는 기준은 이렇다.

| 이럴 때                                                 | 쓸 것                                               |
| ------------------------------------------------------- | --------------------------------------------------- |
| 단계마다 결과를 보고 확인하며 가고 싶다                 | `interview`, `spec`, `execute`를 차례로 따로 부른다 |
| 날것의 문제에서 시작하고 단계 사이에 멈추지 않아도 된다 | `solve`                                             |
| 스펙이 이미 있다                                        | `execute` (`solve`는 쓰지 않는다)                   |
| 요구사항만 정리하면 되고 구현은 아직이다                | `interview`에서 멈춘다                              |

`solve`는 인터뷰 이후를 자율로 돌지만 사람이 아예 빠지는 건 아니다. 막혔을 때 쓰는 대안 관점(lateral persona)을 다 써서 `awaiting_human`으로 멈췄을 때만 사람에게 묻는다.

같이 쓰는 순서는 `interview`, `spec`, `execute`다. `solve`는 이 셋을 한 번에 묶은 것이라 둘을 섞어 쓸 필요가 없다. `execute`는 끝에서 코드 리뷰까지 이어진다. 자세한 흐름은 [03-execute.md](./03-execute.md)와 [06-code-review.md](./06-code-review.md)에 있다.

## 일을 나눠 맡기기

읽고 끝나는 일은 서브에이전트가 맡는다. 같은 브랜치 안의 병렬 쪼개기는 `execute`의 기본 병렬 경로나 `dispatch`가, 티켓이나 브랜치나 PR 하나로 끝나는 일은 `handoff`가 맡는다.

| 방법                       | 맞는 일                                                                                                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 서브에이전트 (Agent 도구)  | 읽기 전용이고(리뷰, 조사, 분류, 윤문 초안) 15분 안쪽에 끝나며 메인은 결과 텍스트만 필요한 일                                                                                   |
| `execute`의 기본 병렬 경로 | 실행 계획의 `parallelGroups`를 읽어 호스트의 Agent 도구로 병렬 실행한다. 외부 도구가 필요 없다. 같은 파일을 건드리는 태스크는 차례로 돌린다                                    |
| `dispatch`                 | 착수 가능한 태스크를 외부 에이전트 런타임(Orca)의 터미널로 뿌린다. 워커별로 다른 에이전트 CLI를 쓰거나, 진행을 터미널로 들여다보거나, 오래 걸리는 실행을 추적해야 할 때만 쓴다 |
| `handoff`                  | 티켓이나 브랜치나 PR 단위로 끝나는 위임. 15분을 넘기거나 사람이 중간에 들여다봐야 하는 일, 다른 레포 작업, 메인과 파일이 안 겹치는 독립 작업                                   |
| `agent`                    | 전용 스킬이 없는 일을 에이전트 하나에게 이름으로 바로 맡긴다                                                                                                                   |

오르카가 있느냐에 따라 갈리는 부분은 이렇다.

| 상황          | 동작                                                                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 오르카가 있다 | `handoff`는 워크트리 위임에 오르카를 먼저 쓴다. `dispatch`도 오르카가 있어야 돈다                                                                                     |
| 오르카가 없다 | `dispatch`는 그 사실을 밝히고 물러나며 `execute`의 기본 병렬 경로를 권한다. `handoff`는 Agent 도구의 워크트리 격리로 내려가고 어느 경로로 돌았는지 완료 보고에 적는다 |

단지 "병렬로 빠르게 돌리고 싶다"는 요청은 `execute`로 간다. `dispatch`는 "orca로", "codex로", "워커 띄워서"처럼 외부 런타임이나 다른 CLI를 직접 말했을 때만 쓴다.

같은 파일군을 건드리는 병렬은 어느 방법이든 띄우지 않고 차례로 돌린다. 사용자와 주고받아야 하는 일(승인 단계, 인터뷰)은 넘기지 않고 메인에서 직접 한다.

같이 쓰는 순서는 `execute`가 계획을 세우고 태스크를 기본 경로로 돌리는 것이 출발이다. 태스크 하나가 티켓이나 PR만큼 커 보이면 `handoff`의 "맡길 곳 고르기"로 먼저 가른다. 외부 런타임이나 다른 CLI가 필요한 태스크만 `dispatch`로 보낸다.

## 코드 바꾸기 전후 영향 보기

고치기 전에는 `blast-radius`, 고친 뒤 커밋 전에는 `diff-radius`를 쓴다. 둘 다 코드 그래프가 필요하고 그 그래프를 만드는 쪽이 `build-graph`와 `setup`이다.

| 스킬           | 대상                                        | 언제                                                                                           |
| -------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `blast-radius` | 아직 고치지 않은 코드                       | 시그니처나 타입을 바꾸거나 리팩토링하기 전. 수정 범위가 불확실하거나 사이드 이펙트가 걱정될 때 |
| `diff-radius`  | 이미 고친 미커밋 변경과 스테이징 변경       | 작업 중인 코드가 어디까지 영향을 주는지 커밋 전에 확인할 때                                    |
| `build-graph`  | 코드 지식 그래프                            | 그래프만 새로 빌드하거나 다시 빌드할 때                                                        |
| `setup`        | `gestalt.json`, 코드 그래프, post-commit 훅 | 레포를 처음 설정할 때. 레포당 한 번이다                                                        |

고르는 기준은 두 가지다. 코드를 이미 고쳤으면 `diff-radius`, 아직 고치기 전이면 `blast-radius`다. 그래프 DB가 아예 없으면 두 스킬 모두 자동으로 만들지 않는다. 그때만 `build-graph`를 돌린다. 레포를 처음 쓴다면 `build-graph`보다 `setup`이 맞다. `setup`이 그래프 빌드와 훅 설치까지 묶어 해 주기 때문이다.

같이 쓰는 순서는 `setup`(레포당 한 번), `blast-radius`(고치기 전), 코드 수정, `diff-radius`(커밋 전)다. 그래프는 한 번 빌드해 두면 질의할 때마다 작업 트리에 맞춰 갱신되므로 매번 `build-graph`를 부를 일은 없다. 그래프 구조는 [code-graph.md](./code-graph.md)에 있다.

## PR과 리뷰

| 스킬           | 누구의 PR                                    | 어디서                                   | 얼마나                                                                |
| -------------- | -------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------- |
| `pr`           | 내 브랜치                                    | GitHub                                   | 본문을 쓰고 `gh`로 올리는 데까지                                      |
| `local-pr`     | 에이전트끼리                                 | 레포 안 (`gh`와 인증과 원격이 필요 없다) | 만들기부터 리뷰, 머지, ref 정리까지                                   |
| `ship`         | 내 브랜치                                    | 로컬 리뷰 후 GitHub draft PR             | 리뷰가 더 나올 게 없는 상태까지. 외부에 나가는 순간마다 승인을 받는다 |
| `review`       | 누구의 것이든 (PR, 브랜치, 커밋, 로컬 PR id) | GitHub 또는 로컬                         | 한 번 리뷰하고 끝. PR이면 인라인 코멘트를 게시한다                    |
| `review-loop`  | 남의 GitHub PR                               | GitHub                                   | 리뷰, 판정 게시, 대응 확인, 재리뷰를 승인이 날 때까지                 |
| `review-reply` | 내 PR에 달린 리뷰                            | GitHub 또는 로컬                         | 코멘트를 분류하고 고쳐서 답글을 게시한다                              |

고르는 기준은 이렇다.

| 이럴 때                                            | 쓸 것                                                     |
| -------------------------------------------------- | --------------------------------------------------------- |
| PR을 만들어 올리기만 하면 된다                     | `pr`                                                      |
| 사람에게 넘기기 전에 리뷰를 수렴시키고 올리고 싶다 | `ship`                                                    |
| 에이전트끼리 워크트리를 나눠 코드를 주고받는다     | `local-pr`                                                |
| 남의 PR을 한 번만 본다                             | `review`                                                  |
| 남의 PR을 작성자가 고칠 때까지 따라간다            | `review-loop`                                             |
| 내가 받은 리뷰 코멘트에 답한다                     | `review-reply`                                            |
| 보안이나 성능 같은 관점 하나만 빠르게 묻는다       | `security-reviewer` 같은 에이전트를 `agent`로 직접 부른다 |

`pr`은 GitHub 전용이다. 로컬이라고 밝히면 만들지 않고 `local-pr`로 넘긴다. `review`와 `review-reply`는 양쪽을 다 탄다. `--local`을 붙이거나 로컬 PR id를 주면 GitHub 대신 로컬 PR로 간다. 로컬 PR의 상태와 CLI는 [local-pr.md](./local-pr.md#스킬)에 있다.

`review-loop`는 남의 PR이 전제다. GitHub은 내 PR에 승인이나 변경 요청을 못 남기게 하므로 내 PR이면 멈추고 `ship`을 안내한다. 한 번 보고 서고 대응을 기다리며 계속 돌지는 않는다. 다시 부르면 그 라운드부터 이어서 돈다.

`ship`은 단계 사이를 알아서 이어 가지만 무인으로 돌지 않는다. 시작할 때 검증 명령을 확인받는다. 로컬 라운드마다 리뷰 게시와 답글도 확인받는다. GitHub에 올리기 직전과 Copilot 코멘트를 반영할 때마다, ready로 바꾸기 직전에도 승인을 받는다. 승인 자리 사이에 손으로 고치고 싶으면 `pr`, `review`, `review-reply`를 순서대로 따로 부른다.

같이 쓰는 순서는 입장에 따라 다르다.

| 입장                     | 순서                                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 내 PR을 올리는 쪽        | `pr`로 올리고 리뷰를 받으면 `review-reply`로 답한다. `ship`은 로컬 리뷰 수렴부터 GitHub 리뷰 대응까지 이 흐름을 이어서 돌리고 승인 자리에서만 선다 |
| 남의 PR을 보는 쪽        | `review`로 한 번 보거나 `review-loop`로 끝까지 따라간다                                                                                            |
| 에이전트끼리 주고받는 쪽 | `local-pr`로 만들고 `review`로 리뷰하고 `review-reply`로 답한 뒤 머지한다                                                                          |

## 글과 소통 산출물

스킬은 승인 단계와 산출물 처리를 붙인다. 에이전트는 문장만 다듬어 돌려주고 보내거나 등록하지 않는다.

| 스킬           | 만드는 것                                                                    | 승인 단계와 마무리                                                                                        |
| -------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `brief`        | 성과 보고, KPI 회고, 제안서, RFC, 의사결정 메모를 이해관계자 설득용 산문으로 | `impact-writer`가 초안을 쓰고 `humanize-monolith`가 다듬는다. 다시 써 달라는 후속 수정도 이 스킬이 맡는다 |
| `presentation` | Reveal.js 슬라이드                                                           | `presentation-writer`가 콘텐츠를 쓰고 승인 단계를 거친 뒤 `presentation-designer`가 HTML로 조립한다       |
| `explain`      | 개념, 에러, 코드를 지정한 대상에게 맞춘 설명                                 | `explain-check`로 판정하고 걸리면 다시 쓰게 한다                                                          |
| `jira-create`  | 지라 티켓                                                                    | `jira-writer`로 본문을 쓰고 프로젝트와 이슈 타입, 필수 필드를 확정한 뒤 미리보기 승인을 받아 생성한다     |
| `slack-send`   | 슬랙 메시지                                                                  | `slack-messenger`로 초안을 쓰고 채널과 발송 시각을 확인한 뒤 미리보기 승인을 받아 전송하거나 예약한다     |

스킬 대신 에이전트를 직접 부르는 경우는 "문장만 필요할 때"다.

| 이럴 때                                          | 쓸 것                                              |
| ------------------------------------------------ | -------------------------------------------------- |
| 티켓 본문만 다듬고 등록은 내가 한다              | `jira-writer`                                      |
| 슬랙 문구만 다듬고 보내지는 않는다               | `slack-messenger`                                  |
| 설명 문장만 빠르게 필요하고 판정은 필요 없다     | `explainer`                                        |
| README나 API 문서 같은 코드 중심 기술문서를 쓴다 | `technical-writer`                                 |
| 슬라이드의 콘텐츠나 디자인 자문 하나만 필요하다  | `presentation-writer` 또는 `presentation-designer` |

에이전트는 `/agent <이름> "할 일"`로 부른다. 이름을 생략하면 쓸 수 있는 에이전트 목록이 나온다. 전용 스킬이 있는 일(`review`, `pr`, `brief`, `presentation`, `jira-create`, `slack-send`)은 그 스킬로 간다. 승인 단계와 산출물 처리가 스킬에만 있기 때문이다.

이 묶음의 스킬은 서로 이어 붙는 파이프라인이 아니다. 산출물마다 맞는 스킬 하나를 고르면 된다.

## 읽기와 조사

이 묶음은 "자료를 읽고 근거를 붙여 정리하는" 스킬들이다. 상세 가이드는 따로 있다.

| 스킬           | 대상                      | 한 줄 요약                                                                                      | 가이드                                         |
| -------------- | ------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `lens`         | 논문 PDF, 웹 글, 팟캐스트 | 문장마다 원문 출처가 달린 읽기 뷰어를 만든다. 원문 표 숫자와 어긋나는 주장에는 의심 표시를 단다 | [lens.md](./lens.md)                           |
| `video-digest` | 유튜브 주소, 영상 파일    | 문장마다 출처가 달린 요약 뷰어를 만든다. HTML과 마크다운까지 낸다                               | [video-digest.md](./video-digest.md)           |
| `research`     | 경쟁 서비스               | 경쟁사 조사부터 화면 캡처, 비교표, 판단, 열린 질문까지 한 문서로 낸다                           | [research-pipeline.md](./research-pipeline.md) |
| `market-scan`  | 경쟁 서비스               | 서비스 지형을 훑어 레퍼런스 후보를 고른다. 화면 캡처와 분석은 하지 않는다                       | [research-pipeline.md](./research-pipeline.md) |
| `screen-ref`   | 경쟁 서비스               | 화면 지도를 만들고 캡처한다. 개인정보는 가짜 값으로 바꿔 저장하고 해석은 쓰지 않는다            | [research-pipeline.md](./research-pipeline.md) |
| `ux-research`  | 모아 둔 경쟁 화면         | 사용자 관점과 비즈니스 관점으로 와우 포인트와 페인 포인트를 쓴다                                | [research-pipeline.md](./research-pipeline.md) |
| `reverse-plan` | 모아 둔 경쟁 화면         | 화면이 왜 그렇게 만들어졌는지 본업에서 거꾸로 짚고 가져올 것과 안 가져올 것을 가른다            | [research-pipeline.md](./research-pipeline.md) |
| `architecture` | 레포나 문서               | 근거가 있는 연결만 실선으로 긋는 아키텍처 그림을 그린다                                         |                                                |

고르는 기준은 자료의 종류다.

| 자료                                  | 쓸 것                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------ |
| 논문 PDF, 웹 글, 팟캐스트             | `lens`                                                                   |
| 유튜브 영상이나 영상 파일             | `video-digest`                                                           |
| 경쟁 서비스 전체                      | `research`                                                               |
| 경쟁 서비스의 한 단계만               | 단계별 스킬 (`market-scan`, `screen-ref`, `ux-research`, `reverse-plan`) |
| 레포나 문서를 근거로 그리는 구조 그림 | `architecture`                                                           |

`research`의 하위 네 스킬은 같은 조사 문서의 단계를 하나씩 맡는다. 같이 쓰는 순서는 `market-scan`으로 후보를 고르고 `screen-ref`로 화면을 모은 다음 `ux-research`와 `reverse-plan`으로 읽는 것이다. `ux-research`와 `reverse-plan`은 캡처가 있는 조사 문서에서 각자 한 섹션만 채운다. 캡처가 없으면 먼저 모으자고 말한다. 이 전체를 한 번에 돌리는 것이 `research`다.

`architecture`는 코드나 문서의 근거를 따라 그림을 그린다. 근거 없이 mermaid만 원하면 이 스킬이 아니다. 설계 리뷰는 `architect` 에이전트가, 파일 단위 의존성과 영향 범위는 `build-graph`와 `blast-radius`가 맡는다.

## 헷갈리기 쉬운 쌍

| 쌍                                      | 구분                                                                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `interview` / `solve`                   | 요구사항 정리만 하고 싶으면 `interview`, 정리부터 구현까지 한 루프로 맡기려면 `solve`                                            |
| `solve` / `execute`                     | 문제 설명만 있으면 `solve`, 스펙이 이미 있으면 `execute`                                                                         |
| `spec` / `execute`                      | 스펙 문서를 만들려면 `spec`, 만들어진 스펙으로 구현하려면 `execute`                                                              |
| `dispatch` / `handoff`                  | 같은 브랜치 안에서 태스크를 병렬로 쪼개 터미널로 뿌리려면 `dispatch`, 티켓이나 브랜치나 PR 단위로 끝나는 위임이면 `handoff`      |
| `dispatch` / `execute`의 기본 병렬 경로 | 외부 런타임이 필요 없으면 `execute`, Orca 터미널이나 다른 에이전트 CLI를 직접 쓰려면 `dispatch`                                  |
| `agent` / 전용 스킬                     | 전용 스킬이 있는 일은 그 스킬, 없는 일을 에이전트 하나에게 바로 맡기려면 `agent`                                                 |
| `blast-radius` / `diff-radius`          | 고치기 전이면 `blast-radius`, 고친 뒤 커밋 전이면 `diff-radius`                                                                  |
| `build-graph` / `setup`                 | 그래프만 다시 빌드하면 `build-graph`, 레포를 처음 설정하면 `setup`                                                               |
| `pr` / `local-pr`                       | 사람에게 넘길 PR은 `pr`, 에이전트끼리 레포 안에서 주고받는 PR은 `local-pr`                                                       |
| `pr` / `ship`                           | PR을 만들기만 하면 `pr`, 리뷰 통과까지 밀어 올리려면 `ship`                                                                      |
| `review` / `review-loop`                | 한 번만 보려면 `review`, 승인이 날 때까지 따라가려면 `review-loop`                                                               |
| `review-loop` / `ship`                  | 남의 PR을 통과시키는 쪽은 `review-loop`, 내 PR을 통과시키는 쪽은 `ship`                                                          |
| `review` / `review-reply`               | 남의 PR에 코멘트를 달면 `review`, 내 PR에 달린 코멘트에 답하면 `review-reply`                                                    |
| `review` / `doubt`                      | PR 단위 검토는 `review`, 만드는 중에 내린 결정 하나(되돌리기 어려운 작업이나 낯선 분기 로직)를 의심해 보려면 `doubt`             |
| `explain` / `explainer`                 | 판정과 재시도까지 받으려면 `explain`, 설명 문장만 필요하면 `explainer`                                                           |
| `jira-create` / `jira-writer`           | 티켓 생성까지 하려면 `jira-create`, 본문만 다듬으려면 `jira-writer`                                                              |
| `slack-send` / `slack-messenger`        | 전송이나 예약까지 하려면 `slack-send`, 문구만 다듬으려면 `slack-messenger`                                                       |

## 스킬이 안 뜰 때

클라이언트마다 스킬을 부르는 방식이 다르다. [README](../README.md#skills)는 이렇게 설명한다.

> Each skill is a slash command in Claude Code. In Codex the same skill is `gestalt:<name>`, and Codex picks it from your description of the task.

Claude Code에서는 스킬이 슬래시 명령이라 `/review`처럼 직접 부른다. Codex에서는 같은 스킬이 `gestalt:<이름>`이다. 하려는 일을 말로 설명하면 Codex가 알맞은 스킬을 고른다.

다른 레포에 같은 이름의 스킬이 있어 헷갈리면 `gestalt:pr`처럼 접두어를 붙여 부른다. `pr` 스킬이 이 경우를 따로 안내한다.

스킬이 `ges_*` 도구를 못 찾거나 호출이 실패하면 흉내 내서 진행하지 않고 무엇이 왜 안 되는지 말하고 멈춘다. 이때는 MCP 서버가 연결돼 있는지부터 확인한다.
