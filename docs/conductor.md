# 컨덕터

컨덕터 세션 하나가 여러 레포의 주문을 받아 워커에 나눠 주고 주문 범위가 정한 끝 자리(기본은 머지)까지 끌고 간다. 처음 쓴다면 [시작하기](#시작하기)부터 본다. 그 뒤 절은 밑에서 도는 동작을 적는다. 컨덕터 세션이 따르는 절차는 `plugin/skills/conductor/SKILL.md`에 있다.

```
주문 (말, 지라, 외부 큐, PR 감시)
   │
   ▼
gestalt conductor tick ──► 저장소 (~/.gestalt/conductor)
   │                       events.jsonl, inbox/, prompts/, deploy/, slack/
   ▼
hostActions ──► 컨덕터 호스트 세션이 실행 (서브에이전트, 세션 열기, 메시지, 지라, 슬랙)
   │
   ▼
워커 (subagent, orca-worktree, git-worktree)
   └─ solve → ship 같은 기존 스킬 체인
   └─ gestalt conductor checkpoint save / worker report
```

구조는 컨덕터와 워커 2계층이다. 워커는 다른 워커를 띄우지 못하고 다음 주문을 스스로 집지 않는다. 워커가 하위 워커를 원하면 보고에 `spawnRequest`를 싣고 컨덕터가 새 주문으로 받는다. 주문 하나에서 생기는 하위 주문은 세 개까지고 한 단계뿐이다. 하위 주문의 워커가 다시 요청하거나 세 개를 넘기면 만들지 않고 그 워커에 이유를 보낸다.

## 시작하기

### 첫 사용 흐름

1. 평소 쓰는 에이전트 세션을 연다. 오르카 안에서 열면 워커 진행을 오르카 화면에서 본다.
2. `/gestalt:conductor`를 치거나 "컨덕터 세션 시작하자"라고 말한다. 이 세션이 컨덕터가 된다.
3. 할 일을 말한다. 예를 들어 "acme/app 배너 문구 고치는 거 머지까지 끌고 가 줘. 지라 APP-101, APP-102도 넣어 줘"라고 하면 세션이 주문 세 개를 넣는다.
4. 세션이 첫 tick을 돌린 뒤 반복을 직접 건다. Claude Code에서는 따로 `/loop`을 칠 필요가 없다. 한 번만 돌려 보려면 "한 번만"이나 `--once`를 붙인다.
5. 세션이 머지 승인처럼 사람이 답할 자리를 물으면 답한다. 나머지는 세션과 워커가 이어 간다.

아래는 단계마다 알아 둘 것이다.

### 세션 열기

컨덕터를 띄우는 명령은 따로 없다. 평소 쓰는 에이전트 세션에서 `/gestalt:conductor`를 치거나 그렇게 해 달라고 말하면 그 세션이 컨덕터가 된다. 스킬은 "컨덕터 세션", "컨덕터", "주문 큐 처리해줘", "티켓들 머지까지 끌고 가", "여러 레포 주문 처리", "워커들 감시해줘" 같은 말에 불린다.

컨덕터 세션은 하나만 둔다. tick은 처음 등록하는 세션이면 다른 컨덕터 세션이 최근에 tick을 돌렸는지 먼저 본다. 기한은 `staleAfterSec`의 두 배(기본 1시간)다. 반복이 한가할 때 깨우는 간격이 `staleAfterSec` 근처까지 늘어나서 그 두 배로 잡았다. 그 안에 돈 세션이 있으면 이 세션을 등록하지 않고 거절한다. 그래서 다른 탭에서 주문을 넣으려고 스킬을 불러도 그 탭은 `order add`까지만 하고 끝나며 주문은 떠 있는 컨덕터가 다음 tick에 받는다. 인계한 세션(`handoff.json`이 있는 세션)은 이 검사에서 빠져서 인계받은 새 세션은 막히지 않는다.

처음 등록에 성공한 세션은 인계 안 한 나머지 세션에 `sessions/<세션 id>/superseded.json`을 적는다. 그 세션의 tick과 wait는 이 파일을 보고 거절해서 오래 쉬던 세션이 다시 깨어나도 컨덕터가 둘이 되지 않는다. 떠 있던 세션이 닫힌 게 확실한데 기한이 안 지났으면 `tick --take-over`(wait도 같다)로 넘겨받는다. 넘겨받힌 세션에서 다시 돌릴 때도 `--take-over`를 쓴다. 세션마다 마지막 tick 시각은 `sessions/<세션 id>/last-tick`에 남는다.

오르카 안에서 열면 첫 tick이 그 탭 이름을 `🤴 지휘자 세션 🤴`로 바꾼다. 탭 여러 개 사이에서 컨덕터를 바로 찾으려는 것이다. 자세한 건 [탭 이름](#탭-이름)에 있다.

### 탭 이름

tick이 세션을 상태 저장소에 처음 등록하는 자리([세션 인계](#세션-인계)의 1번)에서 한 번만 탭 이름을 바꾼다. 스킬로 연 세션도, `handoff`가 오르카로 띄운 새 세션도 첫 tick을 돌므로 둘 다 이름이 붙는다. 이미 등록된 세션의 tick은 다시 안 바꿔서 사람이 나중에 바꾼 이름을 덮지 않는다.

- 터미널 탭이면 `orca terminal rename --terminal="$ORCA_TERMINAL_HANDLE" --title "🤴 지휘자 세션 🤴"`를 부른다.
- 채팅 탭(`ORCA_STRUCTURED_SESSION=1`)이면 `orca chat rename --name "🤴 지휘자 세션 🤴"`를 부른다. 지금 채팅이 기본 대상이다.
- 둘 다 아니면 오르카 밖이라 아무것도 안 한다. 오르카 CLI는 `ORCA_CLI_COMMAND`, PATH 순서로 찾는다.
- 부르다 실패하면 stderr에 한 줄만 남기고 tick은 그대로 돈다. 다음 tick에 다시 시도하지 않는다.

tick은 `GESTALT_CONDUCTOR_WORKER_ID`가 있는 세션이나 살아 있는 워커의 워크트리 안에서 거절되니 보통 워커 탭에는 안 붙는다. 오르카 워커는 환경 변수로 컨덕터와 구분이 안 돼 작업 디렉토리로만 가르므로 워커가 워크트리 밖에서 tick을 부르면 그 탭 이름도 바뀐다. 세션 id가 필요해서 Claude Code에서만 돈다. 인계할 때는 `handoff` 명령이 두 탭 이름을 바로 바꾼다([세션 인계](#세션-인계)의 4번).

### 미리 할 설정

설정은 두 파일에 나눠 적는다.

| 파일                                      | 적는 칸                                                                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `~/.gestalt/conductor.json` (사용자 전역) | `defaultScope`, `defaultAgent`, `repoAgents`, `accounts`, `repoPaths`, `prWatchRepos`. 상태 저장소를 옮기려면 `stateDir`도 |
| 레포의 `gestalt.json`                     | `maxConcurrentWorkers`, `pollIntervalSec` 같은 조율 값만                                                                   |

칸별 뜻과 예시는 [설정 레퍼런스의 컨덕터 절](./configuration.md#컨덕터-conductor)에 있다.

### 어디서 열지

오르카 안에서 열면 코드를 고치는 주문이 `orca-worktree` 워커로 뜬다. 진행은 오르카 화면에서 본다. 오르카 밖에서 열면 같은 주문이 `git-worktree` 워커로 뜬다. 이때는 `repoPaths`에 그 레포의 로컬 경로가 있어야 한다. 경로가 없는 레포의 주문은 띄우지 못하고 `repoPaths`에 적어 달라고 알린다. 읽기만 하는 주문은 어느 쪽이든 서브에이전트로 돈다([워커 종류 고르기](#워커-종류-고르기)).

상태 저장소는 레포 안이 아니라 `~/.gestalt/conductor`(`stateDir`로 바꿀 수 있다)에 있다. 그래서 어느 디렉토리에서 세션을 열어도 같은 상태를 본다. 다만 살아 있는 워커의 워크트리 안이거나 `GESTALT_CONDUCTOR_WORKER_ID`가 잡힌 세션에서는 `tick`, `order add`, `order remove`, `order take-over`, `order cancel`, `order mark-merged`, `queue add`, `gate resolve`, `deploy report`, `wait`, `archive`가 거절된다. 컨덕터 세션은 워커 밖에서 연다.

### 주문 넣기

| 출처    | 넣는 법                                                                                                                                                                                                        |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 말      | 할 일을 말하면 세션이 `gestalt conductor order add`를 대신 부른다. 출처는 `spoken`으로 남는다                                                                                                                  |
| 지라    | "이 티켓들 넣어줘"라고 하면 세션이 Atlassian MCP로 티켓을 읽고 `--source jira --source-ref jira:<KEY> --issue-key <KEY>`를 붙여 넣는다                                                                         |
| PR 감시 | `prWatchRepos`에 적은 레포는 tick마다 열린 PR을 보고 주문을 만든다. 내 PR에 새 코멘트가 달리면 `review-reply`, 내가 리뷰한 PR의 head가 바뀌면 `review-loop` 주문이다. 자세한 조건은 [PR 감시](#pr-감시)에 있다 |
| 외부 큐 | 다른 시스템이 상태 저장소의 `queue/`에 JSON 파일을 두거나 `gestalt conductor queue add`로 넣으면 다음 tick이 주문으로 받는다. 파일 꼴은 [외부 큐](#외부-큐)에 있다                                             |

범위를 말로 정해 주면 그 값으로 넣고 말하지 않으면 `defaultScope`를 쓴다. 범위마다 사람에게 묻는 자리는 [주문 범위와 사람 확인](#주문-범위와-사람-확인)의 표에 있다.

## 컨덕터가 들고 있는 맥락

주문이 늘수록 컨덕터 세션 하나에 맥락이 쌓인다. 쌓이는 맥락을 둘로 나눠서 대화 밖으로 뺀다.

### 주문 하나에만 필요한 맥락

말로 일을 설명하며 오간 대화는 그 주문의 `description`에 다 옮긴다. 워커는 컨덕터 대화를 못 본다. 그래서 대화에서 나온 요구사항과 제약, 결정, 범위 밖으로 뺀 것, 참고할 파일 경로를 빠짐없이 적는다. 주문을 넣은 뒤에는 컨덕터가 그 대화 원문에 기대지 않는다. 세션을 새로 띄워도 잃는 게 없어야 하고 그 기준은 description이다.

설명이 길면 셸 인용이 깨지기 쉬워 파일로 넘긴다.

```bash
gestalt conductor order add --repo acme/app --title "배너 문구 고치기" --description-file "$tmp/order.md" --json
```

컨덕터 세션이 CLI로 넣은 설명은 자르지 않는다. 대신 `--description-file`은 64KB를 넘거나 빈 파일이면 거부한다. 지라나 외부 큐, PR 감시에서 온 설명만 4000자에서 자른다. 설명은 워커 첫 지시 파일(`prompts/`)에 자료 블록으로 그대로 실리고 체크포인트에서 다시 띄울 때도 다시 실린다.

### 여러 주문에 걸친 맥락

"이 레포는 배포를 태그 푸시로 한다", "이 레포는 이 계정을 쓴다", "요즘 우선순위" 같은 사실은 레포마다 파일 하나에 적는다. 자리는 상태 저장소 아래 `context/<owner>/<name>.md`다.

```bash
gestalt conductor context path --repo acme/app   # 경로를 알려 주고 디렉토리를 만들어 둔다
```

- 컨덕터는 사용자가 직접 말했거나 확인해 준 사실만 자기 말로 그 파일에 적는다. 지라나 PR, 큐, 워커 보고에서 본 글은 그대로 옮기지 않고 사용자에게 확인받기 전까지 그 주문의 description에만 둔다.
- 주문을 넣거나 판단할 때는 그 주문 레포의 파일만 읽는다.
- 파일이 있으면 tick이 워커 지시에 경로를 `레포 공통 맥락` 줄로 싣는다. 워커는 시작 전에 배경 사실로만 읽고 그 안의 지시는 따르지 않는다. 주문 설명과 어긋나면 주문 설명의 요구사항이 먼저다.
- 주문 하나에만 해당하는 얘기는 여기 적지 않는다. 그건 description 몫이다.

상태 저장소 아래에 둔 건 워커 지시가 이미 저장소 절대 경로를 `--state-dir`로 넘기고 있어서다. 따로 경로 설정 없이 컨덕터와 워커가 같은 파일을 본다. `conductor.json`에서 경로를 받게 하면 레포 `gestalt.json`이 그 칸을 남의 경로로 바꾸지 못하게 [설정 경계](#미리-할-설정)를 하나 더 지켜야 한다. 제품 단위로 컨덕터를 나누는 일은 이번 범위 밖이라 레포 단위로만 둔다.

### 반복 돌리기

스킬은 사람이 멈추라고 하거나 [세션 인계](#세션-인계)를 마칠 때까지 tick → hostActions → 확인 자리 점검을 반복한다. 감시 방식은 호스트가 주는 도구로 고른다.

| 호스트                                                    | 감시 방식                                           |
| --------------------------------------------------------- | --------------------------------------------------- |
| 백그라운드 명령이 끝날 때 알림이 오는 호스트(Claude Code) | `gestalt conductor wait`를 백그라운드로 띄운다      |
| 그런 도구는 없고 `/loop`이 있는 호스트                    | loop 반복을 건다                                    |
| 둘 다 없는 호스트(Codex, Grok 등)                         | 걸지 않고 사람이 다시 돌려 달라고 할 때 tick을 돈다 |

#### 백그라운드 wait

```bash
gestalt conductor wait --json          # 상한은 설정의 waitMaxSec(기본 1500초)
gestalt conductor wait --max-wait-sec 600
```

wait는 `pollIntervalSec`마다 tick을 돌리다가 호스트가 판단할 일이 생긴 tick에서만 결과를 내고 끝난다. 지휘자 세션은 Bash 도구의 백그라운드 실행으로 띄우고 차례를 끝낸다. 명령이 끝나면 호스트가 알림으로 세션을 깨우고 세션은 그 출력만 처리한 뒤 다시 띄운다.

loop 반복과 비교하면 할 일 없는 주기에 세션이 아예 안 깨어난다. loop는 깨어날 때마다 반복 문장과 tick 출력, 판단이 대화에 쌓였고 할 일이 없어도 같았다. wait는 할 일 없는 tick을 출력 없이 넘기니 대화에 쌓이는 건 끝났을 때의 짧은 결과 하나뿐이다. `tests/unit/conductor/cli.test.ts`의 wait 테스트가 할 일 없는 tick 동안 출력이 한 줄도 없다는 걸 확인한다.

끝나는 이유는 `reason`에 실린다.

| reason       | 뜻                                                                                                                                                                               | 세션이 할 일                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `attention`  | 호스트 할 일이나 새 게이트가 생겼거나 사람이 맡은 PR에 변화가 생겼다. 처음 보는 오류나 경고, 인계할 때, 이전 탭을 닫은 결과도 여기 든다. 어떤 이유로 끝났는지는 `reasons`에 있다 | `tick`(tick JSON과 같은 꼴)을 처리하고 다시 띄운다 |
| `timeout`    | 상한 동안 할 일이 없었다. 세션이 살아 있는지 확인할 기회를 준다                                                                                                                  | 보고 없이 다시 띄운다                              |
| `superseded` | 더 나중에 띄운 wait가 이어받았다                                                                                                                                                 | 다시 띄우지 않는다                                 |

- 출력은 호스트가 바로 처리할 만큼만 싣는다. tick 결과가 6000자를 넘으면 `tick`을 빼고 `reportFile`(상태 저장소의 `wait-last.json`) 경로만 싣는다. 크기가 큰 넘김 결과는 다음 wait가 공용 사본을 바꿔도 읽을 수 있게 `wait-reports/` 아래 별도 경로를 알린다. 공용 사본 `wait-last.json`은 `attention`으로 끝날 때만 덮어쓴다. `superseded`로 끝난 앞선 wait가 이어받은 wait의 보고서를 덮지 않게 하려는 것이다.
- 접수 단계(지라, 큐, PR 감시)가 연 게이트는 tick의 `escalated`에 안 실린다. wait는 띄울 때 열려 있던 게이트 수보다 늘었으면 `gatesOpened`로 끝난다.
- 이미 보여 준 경고와 오류, 이전 탭을 닫은 결과는 상태 저장소의 `wait-seen.json`에 남긴다. 고쳐지지 않는 오류 하나 때문에 wait가 띄우자마자 끝나는 일을 막는다. 다른 이유로 끝나면 그 오류도 함께 실린다. wait 하나가 끝날 때 그동안 건너뛰지 않은 tick에서 한 번도 안 나온 문장은 목록에서 뺀다. 고쳐졌다가 같은 문장으로 다시 나면 그다음 wait에서 호스트를 깨운다. 한 wait 안에서 풀렸다가 다시 난 문장은 그 wait에서는 못 알아본다. PR 상태 확인 실패처럼 `humanOwnedPollSec` 간격으로만 실리는 오류가 tick 사이에 빠졌다고 매번 깨우지 않게 하려는 것이다. 다만 이 오류는 wait가 그 간격보다 오래 돌아 확인 tick을 지나야 목록에 남는다. 일찍 끝난 wait나 `humanOwnedPollSec`이 `waitMaxSec`보다 길 때는 목록에서 빠져 다음 확인 tick에서 다시 깨운다.
- 세션 한도 대기(`rateLimited`)는 풀릴 때까지 tick마다 실려서 이유로 안 친다. 오래가면 tick이 게이트로 올린다.
- tick은 기존 잠금(`tick.lock`)을 그대로 쓴다. wait가 도는 중에 사람이 시켜 `tick --force`를 돌려도 둘이 겹쳐 돌지 않는다. 간격은 wait가 직접 재고 tick은 `--force`로 부른다. 시계 하한에 맡기면 호스트가 방금 돌린 tick 때문에 첫 주기를 통째로 건너뛴다.
- wait는 뜰 때 상태 저장소의 `wait.owner`에 자기 표식과 세션 id를 쓴다. 세션 id가 없는 wait는 최근에 tick을 돌린 컨덕터가 있으면 시작을 거절한다. 컴팩트 뒤 중복으로 띄웠거나 닫힌 세션에 wait가 남아 있어도 tick 앞뒤에서 표식이 바뀐 걸 확인해 `superseded`로 끝난다. 닫힌 세션에 남은 wait가 tick을 계속 돌리면 hostActions를 아무도 못 받기 때문이다.
- tick이 도는 동안 소유권을 넘기면 끝난 tick의 전달할 결과를 `wait-carry/`에 남긴다. 새 wait는 다음 결과를 낼 때 또는 시작할 때 남은 파일을 오래된 순서대로 한 번만 가져간다. 다른 세션의 인계 판단은 `carriedHandoffs`에 기록으로 싣는다. 아직 가져가지 않은 결과는 다음 wait가 이어받는다. 파일을 가져간 프로세스가 강제 종료되면 실행 요청의 중복을 막기 위해 그 파일을 자동으로 다시 전달하지 않는다.
- 상한은 기본값이자 최댓값이 1500초다. 스킬은 `timeout: 1800000`(30분)으로 띄우는데 상한이 지난 뒤에도 마지막 tick이 끝나야 wait가 끝난다. 그 tick까지 30분 안에 마치려고 상한을 1500초로 막았다. 설정이나 `--max-wait-sec`로 이보다 크게 주면 거절한다. 레포 `gestalt.json`에서 더 짧게 바꿀 수 있다.
- tick이 감시 간격보다 오래 걸리면 다음 tick까지 10초만 쉰다. 간격은 tick이 시작한 때부터 잰다.
- 인계한 세션의 wait는 다음 tick이 거절돼 실패로 끝난다.

#### loop 반복

백그라운드 알림이 없는 호스트에서는 첫 tick을 돌린 뒤 세션이 loop 스킬을 직접 불러 아래와 같은 반복을 간격 없이 건다. 간격을 비우면 세션이 간격을 스스로 정한다.

```text
/loop 컨덕터 tick: 맥락에 있는 gestalt:conductor 스킬의 깨어날 때마다 절차대로 gestalt conductor tick --json 돌리고 hostActions 처리, 반복은 다시 걸지 않음
```

반복 문장에 슬래시 명령을 쓰지 않는 건 컨텍스트 때문이다. `/loop /gestalt:conductor …`로 걸면 깨어날 때마다 스킬을 다시 불러 SKILL.md 본문(약 12k자)이 tick마다 한 벌씩 더 쌓인다. 2026-11-13 컨덕터 세션에서 tick 한 번에 약 10.4k 토큰이 늘었고 tick 출력과 응답은 그중 1k도 안 됐다. 그래서 컨텍스트가 금방 차서 할 일이 없어도 1시간마다 인계했다. 본문은 첫 호출 때 맥락에 들어오고 컴팩트 때도 Claude Code가 불렀던 스킬 본문을 요약 뒤에 다시 붙인다([스킬 문서의 Skill content lifecycle](https://code.claude.com/docs/en/skills)). 그래서 반복 문장은 그 절차를 따르라는 일반 문장이면 된다.

할 일이 없으면 간격을 늘린다. tick JSON의 `idleTicks`는 상태가 안 바뀐 tick이 연달아 몇 번 왔는지 센다. 새 주문과 띄운 워커, 올린 확인 자리, 호스트 할 일, 오류가 없고 앞 tick 뒤로 상태 저장소에 이벤트가 하나도 안 쌓였으면 `idleTicks`가 1 오른다. 사람이 넘겨받은 주문의 PR을 확인만 하고 상태가 그대로인 기록은 이벤트로 세지 않는다. 하나라도 있으면 0으로 돌아간다. 간격 하한이나 잠금에 막혀 건너뛴 tick은 마지막 값을 그대로 싣는다. 세션은 `idleTicks`가 2 이상이면 다음 깨우기를 20~30분 뒤로 잡고 상태가 바뀌거나 사람이 답하면 다시 짧은 간격으로 돌아온다. 텍스트 출력에는 `변화 없는 tick N번째` 줄로 찍힌다.

반복이 두 겹으로 걸리지 않게 아래 경우에는 다시 걸지 않는다.

- 입력이 `/loop`으로 시작하거나 자율 반복 표식(`<<autonomous-loop-dynamic>>` 등)이 붙어 들어온 실행. 사람이 반복 프롬프트 문장을 직접 쳤으면 여기 들지 않는다
- 같은 세션에서 이미 loop 스킬을 불렀거나 `ScheduleWakeup`, 크론이 걸려 있는 상태. 압축이나 재개로 세션이 이걸 기억 못 하면 나머지 기준으로만 판단하고 사람에게 묻지 않는다. 기억이 없어 두 겹으로 걸려도 tick이 늘어날 뿐 상태는 안 깨진다. 동시에 도는 tick은 잠금에 막히고 `pollIntervalSec` 안에 다시 부른 tick은 간격 하한에 막혀 `skipped: true`로 끝난다
- 컨덕터 실행을 두고 "한 번만", `--once`처럼 이번 실행만 원한다고 말한 경우. 이때는 보고 끝에 위 명령을 알려 준다. 위 두 경우로 반복이 이미 걸려 있으면 안내를 생략하고 그 반복도 끄지 않는다

직접 `/loop`으로 시작해도 된다. 그때는 스킬이 반복을 더 걸지 않는다. `pollIntervalSec` 안에 다시 부른 tick은 `skipped: true`로 바로 끝나서 자주 불러도 토큰이 거의 안 든다. 멈추려면 멈추라고 말한다. 세션에 남은 `ScheduleWakeup`과 컨덕터 크론을 함께 끈다.

`/loop`도 백그라운드 알림도 없는 호스트(Codex, Grok 등)에서는 감시를 걸지 않고 안내만 한다. 다시 돌려 달라고 그때그때 말하거나 그 호스트의 반복 기능을 쓴다. 호스트마다 반복 기능이 어떻게 동작하는지는 아직 확인하지 않았다.

### Orca 봇 운영과 인계

운영자 터미널에서 Orca 봇과 채팅을 확인하고 상태 저장소의 운영권을 등록한다. 등록하기 전에 기존 컨덕터의 마지막 tick과 `hostActions`를 마친다.

```sh
orca bot list --json
orca bot chats --bot Conductor --json
gestalt conductor bot bind --bot Conductor --chat <채팅-ID>
gestalt conductor status --json
```

`conductor.botOwner`에 봇과 채팅 ID가 표시된다. 등록된 채팅만 같은 저장소의 tick과 wait를 돌릴 수 있다. 운영을 넘기려면 인계 메모를 받은 새 채팅이 준비됐는지 확인한 뒤 터미널에서 `gestalt conductor bot bind --bot Conductor --chat <새-ID> --from-chat <기존-ID>`를 호출한다. 대상 확인, tick 잠금 또는 기존 ID 비교에서 실패하면 운영권은 그대로다. 성공하면 기존 채팅의 감시를 끈다. 터미널 운영으로 복귀하려면 `gestalt conductor bot release --from-chat <현재-ID>`로 등록을 해제한다.

Orca의 `bot new-chat`은 기존 홈을 닫는다. 운영을 이어가면서 홈을 교체하려면 별도 채팅으로 먼저 운영권을 넘긴다. 새 홈이 열려 준비된 뒤 별도 채팅에서 다시 운영권을 넘긴다.

#### 정기 자동화와 운영권을 함께 인계

운영자 터미널에서 `orca bot chats --bot <봇> --json`, `orca automations list --json`, `orca automations show <자동화-ID> --json`으로 두 채팅과 기존 정기 자동화를 찾는다. 새 채팅이 인계 메모를 받았는지 확인한 뒤 기존 채팅의 마지막 tick과 후속 작업을 마친다. 다음 명령에 정기 점검의 기존 ID를 지정하고 미리보기에 나온 현재 책임 채팅, 자동화 대상, 주기와 다음 실행을 확인한다.

```sh
gestalt conductor bot handoff --bot Conductor --from-chat <기존-ID> --chat <새-ID> \
  --automation <자동화-ID> --request <고유-요청-ID>
```

인계하려면 같은 명령에 미리보기의 `--approve <승인값>`을 한 번 붙인다. 승인은 상태 저장소, 운영권 리비전, 두 채팅, 자동화 ID와 설정에 묶인다. 다른 저장소나 설정이면 새 미리보기가 필요하다. 완료 결과에 책임 채팅과 자동화 대상, Orca가 보고한 다음 정기 실행 시각이 나온다. 실제 예약 실행은 예정 시각 이후 `orca automations runs --id <자동화-ID> --json`에서 확인한다. `--json` 출력과 `gestalt conductor status --json`의 `conductor.botHandoff`에서 같은 요청을 추적할 수 있다.

- Orca 1.4.269의 공개 CLI는 명시적으로 채팅 ID가 지정된 활성 봇 일정에 `orca automations edit <자동화-ID> --runs-in chat:<새-ID>`를 지원한다. 이 명령은 같은 ID와 실행 이력을 보존한다. 설정은 `show`로 변경 전후를 대조한다. 기존 자동화를 조회하고 편집할 수 있는 해당 로컬 Orca의 운영자 권한이 필요하다. 설치된 플러그인 호스트 API의 `automation.update`는 대상 채팅 변경을 지원하지 않아 운영자 터미널에서 인계한다.
- 진행 중인 요청은 기존 운영 채팅에 책임을 둔다. Orca 쪽만 이동한 상태라면 다음 정기 실행이 새 채팅에서 tick을 시도해도 완료 전에는 거절된다. 현재 책임 채팅에서 수동 점검을 이어간다. 결과에 나온 재개 단계를 확인한 뒤 같은 요청 ID와 승인값으로 다시 실행한다. 먼저 옮겨진 자동화를 이어받을 때도 운영권을 기록하기 직전에 새 채팅이 열려 있는지 다시 확인한다.
- Orca 호출 전에 중단되면 같은 요청과 승인값으로 이어간다. `--cancel`은 기존 책임 채팅이 메일을 받을 수 있는지 다시 확인한 뒤 실제 자동화 대상과 승인된 설정을 재조회한다. 운영권과 일정이 일치할 때 취소를 확정한다. 편집을 맡은 로컬 프로세스는 명령을 실행한 쪽이 종료되어도 Orca 응답을 기록한다.
- 호출을 시작한 뒤 이 편집의 Orca 응답을 받지 못하면 `reconcile-edit` 상태에 남는다. 다른 편집이나 늦게 반영된 편집이 같은 대상을 가리킬 수 있다. 응답을 확인할 때까지 운영권 이전, 재편집, 취소 확정은 보류된다. `automations show`는 현재 설정, `automations runs`는 일정 실행 이력을 조회한다. Orca 1.4.269의 공개 명령과 플러그인 API에는 설정 편집의 잃어버린 응답을 회수할 조회가 없다. Gestalt 편집 시도 ID는 로컬 기록을 찾을 때 쓴다.
- 응답이 계속 없으면 Orca 운영자와 [Orca 공식 지원 채널](https://github.com/stablyai/orca#community--support)에 조사에 필요한 정보를 전달한다. Orca 버전, 자동화 ID, 요청 ID, 편집 시도 ID, 요청 UTC 시각, 현재 책임 채팅과 조회된 자동화 대상이 필요하다. 요청 시각은 `conductor status --json`의 `botHandoff.editDispatchedAt`에 실린다.
- Orca 응답이 확인된 요청을 복구하려면 수동 변경 전에 승인 명령에 `--cancel`을 붙여 현재 상태를 확인한다. 자동화가 새 채팅에 있고 기존 채팅이 메일을 받을 수 있으면 운영자 터미널에서 `orca automations edit <자동화-ID> --runs-in chat:<기존-ID>`를 실행한다. `show`로 대상과 설정이 돌아왔는지 확인한 뒤 같은 `--cancel` 명령으로 취소를 확정한다.
- 같은 OS 계정에서 로컬 Orca를 쓰는 저장소들은 사용자 홈의 `.gestalt/orca-handoffs`에서 자동화별 잠금과 담당 저장소 기록을 공유한다. 다른 저장소가 먼저 맡은 자동화라면 `coordinate` 단계에 저장소 경로와 요청 ID가 나온다. 해당 저장소의 요청을 이어서 처리한다. 첫 인계를 취소하면 담당 기록도 비워진다.
- 대상 없는 홈 채팅 설정, 새 대화에서 실행되는 자동화, 닫힌 대상, 일시 중지 또는 편집 권한이 없는 경우에는 Orca에서 해당 조건을 확인한다. Orca CLI는 조건부 편집이나 두 저장소의 공통 트랜잭션을 제공하지 않는다. 인계 중에는 Orca 화면에서 같은 자동화를 편집하거나 두 채팅을 닫는 작업을 피한다.

#### 봇 채팅에서 게이트 승인

봇 채팅에서 닫을 수 있는 게이트는 머지 승인(`merge`), 파일 중첩(`file-overlap`), 리뷰 수동 전환(`review-manual-switch`) 셋이다. 승인과 거절이 워커에 주는 뜻은 패널이나 `gate resolve`로 닫을 때와 같다. 다른 게이트와 배포 결정은 운영자 터미널이나 패널에서 처리한다.

`gestalt conductor bot gate <게이트-ID>`는 게이트 유형, 레포, 사유와 refs, 승인과 거절에 서명할 문자열(`messages`), Orca 항목 질문에 실을 줄(`orcaItem.binding`)을 반환한다. 머지 게이트면 PR 주소와 GitHub에서 확인한 HEAD, 검사 결과도 싣는다. 승인자는 본인 기기에서 해당 문자열에 서명한다.

```sh
gestalt conductor bot decide <게이트-ID> --decision approved --signer <승인자-ID> --signature <base64>
```

상태 저장소의 `bot-policy.json`에 레포별 Ed25519 공개키를 PEM SPKI 형식으로 등록한다. 머지 승인자는 `mergeApprovers`, 파일 중첩과 리뷰 수동 전환 승인자는 `gateApprovers`에 둔다. 두 칸의 모양은 같다. 개인키는 승인자가 보관한다. OpenSSL 3에서 `openssl genpkey -algorithm Ed25519 -out approver.key`와 `openssl pkey -in approver.key -pubout`으로 키를 만들 수 있다. 승인 또는 거절에 해당하는 문자열을 개행 없이 파일에 저장해 서명한다.

```sh
jq -jr .messages.approved gate.json > decision.txt
openssl pkeyutl -sign -rawin -inkey approver.key -in decision.txt | openssl base64 -A
```

거절할 때는 `messages.rejected`와 `--decision rejected`를 사용한다. 머지 문자열은 이전과 같은 `gestalt/merge-approval/v1`이다. 다른 게이트 문자열은 `gestalt/gate-approval/v1`에 게이트 유형과 레포를 넣어서 한 게이트에 한 서명을 다른 게이트에 옮겨 쓸 수 없다. 게이트 내용이나 PR HEAD가 바뀌면 새 문자열에 서명한다. 머지는 잠금을 잡은 뒤 GitHub HEAD를 한 번 더 읽어 서명한 HEAD와 다르면 닫지 않는다. 승인된 HEAD는 워커에게 전달된다. 패널에서 먼저 처리했거나 답을 다시 보냈으면 이미 기록된 결정을 보여 준다. 결정과 별도로 전달 상태가 표시된다. `pending`은 다음 tick에 전달 대기, `delivered`는 런처 전송 성공, `failed`는 전송 실패, `host-action`은 호스트에 전달 위임, `no-worker`는 전달할 워커 없음, `unknown`은 과거 기록에 전달 결과가 없다는 뜻이다. 전송이 실패해 다시 시도하는 중이면 `failedAttempts`가 붙는다. `itemReport`는 이 둘을 `판단:`과 `워커 전달:` 두 줄로 나눠 적은 글이라 운영 봇이 Orca 항목에 그대로 남긴다.

#### Orca 항목 답으로 게이트 승인

운영 봇은 게이트를 Orca 항목 질문으로 올릴 수 있다. 질문 본문에 `bot gate`가 준 사유와 근거, 서명할 문자열, `orcaItem.binding` 한 줄을 그대로 싣고 `승인`, `거절` 선택지를 단다. 운영자는 항목에 두 줄로 답한다.

```text
승인
서명 <승인자-ID> <base64>
```

Orca가 답을 알려 주면 봇은 메일에 적힌 항목 번호와 질문, 답 이벤트 ID로 아래 명령을 부른다.

```sh
gestalt conductor bot item-decide <게이트-ID> --item <항목-번호> --question <질문-이벤트> --answer <답-이벤트>
```

Gestalt는 봇이 옮겨 적은 말 대신 `orca bot item show`로 Orca가 저장한 항목을 직접 읽는다. 항목이 등록된 운영 봇과 채팅의 것인지, 질문이 그 봇이 쓴 것이고 지금 게이트의 `binding` 줄(게이트 ID, 유형, 연 시각, 레포, 머지면 PR과 HEAD)을 담았는지, 답이 질문 뒤에 사람(`owner`)이 단 것인지, 사이에 더 새 게이트 질문이 없는지 본다. 그다음 `bot decide`와 같은 승인자 서명 검사를 거쳐 게이트를 닫고 항목, 질문, 답 이벤트를 `decisionSource`로 남긴다. 같은 답이 다시 오면 `alreadyResolved`와 `sameAnswer: true`로 기존 결정을 돌려준다. 다른 경로로 먼저 닫혔으면 `sameAnswer: false`다.

서명 줄이 없는 답(선택지 클릭만)은 게이트를 그대로 두고 실패로 끝난다. Orca 1.4.269의 항목 이벤트는 답한 쪽을 `owner` 하나로만 적는다. 사람마다 다른 식별자, 레포별 권한, Orca 밖에서 확인할 서명이 없어서 같은 계정으로 도는 봇 에이전트가 만든 기록과 사람의 답을 가를 수 없다. 서명 없는 답을 받으려면 Orca가 승인자 식별자와 레포별 권한 확인 결과, 항목과 질문, 답, 결정을 묶은 서명을 줘야 한다. 이 계약이 생기기 전까지는 서명이 승인 근거다.

#### GitHub 팀 주문

Orca GitHub 커넥터가 연결된 팀 접수 봇은 운영 봇과 별도로 둔다. 운영자가 상태 저장소에 `bot-policy.json`을 작성한다. 레포 키는 소문자로 적는다. 팀 접수 권한은 GitHub 사용자 숫자 ID를 등록한다.

```json
{
  "githubIntakeBotId": "<팀 접수 봇 ID>",
  "githubRepositories": { "acme/app": [12345678] },
  "mergeApprovers": {
    "acme/app": {
      "release-owner": "-----BEGIN PUBLIC KEY-----\n<공개키>\n-----END PUBLIC KEY-----\n"
    }
  },
  "gateApprovers": {
    "acme/app": {
      "review-owner": "-----BEGIN PUBLIC KEY-----\n<공개키>\n-----END PUBLIC KEY-----\n"
    }
  }
}
```

팀원은 GitHub 이슈나 PR의 일반 댓글 첫 줄에 Orca의 호출 멘션을 단독으로 적는다. 다음 줄에 `gestalt order <제목>` 또는 `gestalt status`를 적는다. 주문 설명은 제목 아래에 쓴다. 접수 봇은 `gestalt conductor bot github <원본-댓글-URL>`을 호출한다. Gestalt가 GitHub API에서 스레드와 작성자 ID를 확인하고 기존 큐에 `solve → ship`, `approval` 범위로 넣는다. 같은 댓글을 다시 받으면 기존 주문을 돌려준다. 봇은 반환된 스레드와 자신을 깨운 스레드가 같을 때 Orca 최종 응답으로 결과를 남긴다. 팀원은 이후 같은 스레드에서 `gestalt status`로 주문 상태와 PR을 확인한다.

팀 접수 봇의 도구는 GitHub 조회와 허용된 큐 동작으로 한정한다. 운영자와 같은 계정의 범용 셸, 컨덕터 상태와 정책 쓰기, 승인자 키와 머지와 배포 자격 증명을 팀 요청 경로에 열면 CLI 검사를 우회할 수 있다. Orca의 Who can ask는 채널 접수 범위를 좁히는 설정이다. 설치된 CLI에서 채팅 답변의 승인자나 GitHub에서 실행을 깨운 요청자의 신원을 직접 읽는 공개 인터페이스는 확인하지 못했다. 게이트 승인은 채팅이나 Orca 항목으로 받은 서명으로, 팀 주문은 GitHub API의 원본 댓글로 검사한다.

[Orca 봇](https://orca.dev/docs/bots), [커넥터](https://orca.dev/docs/bots/connectors), [보안](https://orca.dev/docs/bots/security).

### 세션 인계

컨덕터 세션은 컴팩트를 한 번까지만 허용한다. 두 번째 컴팩트가 오기 전에 새 세션을 띄워 대화에만 있던 맥락을 넘기고 기존 세션은 감시(wait나 반복)를 멈춘다. 진행 상태는 이미 저장소에 들어 있으니 다시 쓰지 않는다.

1. **세션 등록.** Claude Code에서 `gestalt conductor tick`을 부르면 Bash 환경의 `CLAUDE_CODE_SESSION_ID`로 이 세션을 상태 저장소의 `sessions/<세션 id>/`에 등록한다. 이 디렉토리가 있는 세션만 컨덕터 세션으로 본다.
2. **컴팩트 세기.** 플러그인 훅 `scripts/conductor-compact-hook.sh`가 `SessionStart`의 `compact` 시작(자동과 수동 둘 다)에 걸린다. 등록된 세션이면 `sessions/<세션 id>/compactions`의 횟수를 하나 올리고 훅 입력의 `transcript_path`를 같이 적는다. 그리고 컴팩트 뒤 맥락에 "컨덕터 세션이고 N번째 컴팩트"라는 한 줄을 붙인다. 등록 안 된 세션은 아무것도 안 쓰고 끝난다. 훅은 bash와 cat, mv로만 돌고 Node를 띄우지 않는다.
3. **판정.** tick은 매번 이 세션의 `handoff`를 JSON 출력에 싣는다. 훅 입력에는 컨텍스트 사용량이 없어서 트랜스크립트 끝의 마지막 메인 응답 usage(input, cache 생성, cache 읽기의 합)를 창 크기로 나눠 사용량을 낸다. 창 크기는 `contextWindowTokens` 설정이 먼저다. 비어 있으면 Claude settings의 `autoCompactWindow`를 쓰고 그것도 없으면 모델 창을 쓴다. 모델 창은 모델 id에 `[1m]`이 있거나 사용량이 200k를 넘을 때 1M, 아니면 200k로 본다. `autoCompactWindow`는 Claude Code와 같은 순서로 관리 설정, 프로젝트의 `.claude/settings.local.json`, `.claude/settings.json`, 사용자 settings.json(`CLAUDE_CONFIG_DIR`가 있으면 그 아래, 없으면 `~/.claude`) 가운데 먼저 적힌 값을 읽고 모델 창보다 크면 모델 창을 쓴다. 1M 모델을 `autoCompactWindow: 250000`으로 쓰는데 창을 1M으로 세면 220k를 써도 22%라 인계 전에 컴팩트가 먼저 온다.
   - 컴팩트 전이면 `due: false`
   - 한 번 컴팩트했고 사용량이 `handoffContextPercent`(기본 70%) 이상이면 `due: true`
   - 두 번째 컴팩트가 이미 왔으면 사용량과 상관없이 `due: true`
   - 사용량을 못 읽으면 `due: false`와 이유. 세션은 그 이유를 사용자에게 한 번 전하고 두 번째 컴팩트가 오면 넘긴다. 텍스트 출력에는 `인계 판정 못 함: <이유>` 줄로 찍힌다
4. **인계.** `due: true`를 본 세션은 그 tick에서 hostActions를 처리하고 확인 자리를 점검하는 일까지 마친 뒤 넘긴다. tick 도중이나 사람에게 확인 자리를 묻고 답을 처리하는 도중에는 넘기지 않는다. 넘길 것은 대화에만 있는 값이다.
   - `/loop` 프롬프트 원문. wait로 감시했으면 반복 문장이 없으니 `--loop-prompt`를 뺀다
   - 사용자가 대화로 정한 규칙(특정 티켓 제외, tick 플래그 같은 것)
   - 사람에게 물어 두고 답을 기다리는 질문
   - 워커 reply id처럼 대화에만 있는 값

   세션이 이걸 마크다운 파일로 쓰고 아래 명령을 부른다. `--loop-prompt`는 `컨덕터 tick: `으로 시작하는 한 줄(앞에 `5m ` 같은 간격 하나는 붙어도 된다, 500자 이하)만 받는다. 이미 떠 있는 세션이 옛 꼴로 반복을 걸었을 수 있어 `/gestalt:conductor`로 시작하는 한 줄도 받는다. 새 세션이 인계 파일의 값을 그대로 반복에 걸기 때문에 명령은 간격 접두만 남기고 본문을 지금 반복 문장으로 바꿔 싣는다. 옛 꼴로 걸린 세션도 인계 뒤에는 새 문장으로 돈다. 꼴이 다르면 인계 파일을 쓰기 전에 거절하니 `--loop-prompt`를 빼고 다시 넘기고 사용자에게 알린다.

   ```bash
   gestalt conductor handoff --notes-file "$tmp/handoff-notes.md" \
     --loop-prompt "컨덕터 tick: 맥락에 있는 gestalt:conductor 스킬의 깨어날 때마다 절차대로 gestalt conductor tick --json 돌리고 hostActions 처리, 반복은 다시 걸지 않음" --json
   ```

   명령은 상태 저장소의 `handoffs/`에 인계 파일을 쓴다. 파일은 이어받은 세션이 할 일, 반복 프롬프트 원문, 메모 순서이고 메모는 펜스로 감싸 앞의 고정 절과 섞이지 않게 한다. 그다음 띄우기 전에 거절 기록(`handoff.json`)을 남기고 오르카가 있으면 `orca agent launch --agent claude --worktree path:<지금 작업 디렉토리> --model <모델> --effort <handoffEffort> --prompt "/gestalt:conductor … 인계 파일: <경로>"`로 같은 워크스페이스에 새 세션을 띄운다. 오르카가 없거나 띄우기가 실패하면 파일만 남기고 `launched: false`와 사람에게 전할 문장을 돌려준다. 세션은 그 문장을 사람에게 전한다. 그 문장에도 `/effort <handoffEffort>`로 추론 수준을 맞추라는 말이 들어 있다.

   새 지휘자 세션은 추론 수준 `handoffEffort`(기본 `high`)로 띄운다. 오르카는 `--effort`를 `--model` 없이 받지 않아서 모델을 같이 싣는다. 모델은 `handoffModel` 설정이 먼저고 비어 있으면 이전 세션 트랜스크립트에서 메인 대화가 마지막으로 응답할 때 쓴 모델을 그대로 잇는다. 트랜스크립트의 모델 id에는 1M 창 표시가 없으므로 모델 창을 1M으로 봤으면 `[1m]`을 붙인다. 사용량을 잰 창과는 따로 본다. `autoCompactWindow`로 250k에서 재더라도 1M 모델이면 새 지휘자도 1M 모델로 뜬다. 설정값에는 이걸 안 붙이므로 1M 창이 필요하면 `opus[1m]`처럼 설정에 직접 적는다. 트랜스크립트 모델이 설정과 같은 허용 꼴이 아니면 모델을 모르는 경우로 다룬다. 컴팩트 전에 손으로 넘겨 트랜스크립트를 못 읽는 등 모델을 모르면 두 플래그를 다 빼고 띄운 뒤 결과 문장에 새 세션에서 `/effort <handoffEffort>`로 맞추라고 적는다. 두 플래그는 새 세션 에이전트가 claude일 때만 싣는다. 두 칸 모두 사용자 전역 `~/.gestalt/conductor.json`에서만 바꾼다([설정](./configuration.md)). 띄운 뒤 결과를 `handoff.json`에 못 덮어쓰면 stderr에 `인계 기록 갱신 실패` 한 줄을 내고 결과에 `recordError`를 싣는다. 이때 기록에는 "띄우는 중"이 남지만 tick 거절은 그대로 걸린다.

   오르카로 띄웠으면(`launched: true`) 명령이 두 탭 이름도 바꾼다. 넘긴 세션 탭은 `지휘자 세션 (인계 완료, MM/DD)`, 새로 띄운 탭은 `🤴 지휘자 세션 🤴`이 돼서 어느 탭이 지금 도는 컨덕터인지 바로 보인다. 새 탭은 `agent launch` 응답의 채팅 세션 id(`chat rename --session`)나 터미널 핸들(`terminal rename`)로 가리킨다. 응답에서 새 탭을 못 읽었으면 넘긴 탭만 바꾸고 `renameErrors`에 한 줄 남긴다. 새 탭은 첫 tick에서 이름이 붙는다. 이름 바꾸기가 실패해도 인계는 성공으로 두고 결과의 `renameErrors`와 stderr로 알린다. `--json`이어도 stderr에 남긴다. 오르카로 띄우지 않았으면 탭 이름을 건드리지 않는다.

5. **기존 세션 멈추기.** 넘긴 세션은 떠 있는 wait를 끄고 `ScheduleWakeup`을 `stop: true`로 부르고 컨덕터 크론도 지운다. 그래도 wait나 반복이 남아 tick이 다시 돌면 `sessions/<세션 id>/handoff.json`이 있어서 거절한다. 새 세션이 닫혀 반복이 끊긴 걸 사람에게 확인한 뒤에만 이 파일을 지우고 그 세션에서 이어 돌린다.
6. **이전 탭 닫기.** 오르카로 띄웠으면(`launched: true`) 명령이 넘긴 세션의 탭을 `handoff.json`의 `previousTab`에 적는다. 터미널 탭이면 `ORCA_TERMINAL_HANDLE`의 핸들을, 채팅 탭(`ORCA_STRUCTURED_SESSION=1`)이면 종류만 적는다. 그 뒤 tick마다 지금 도는 컨덕터 세션이 저장소의 `sessions/*/handoff.json`을 훑고 인계 시각부터 `handoffCloseAfterSec`(기본 600초)가 지난 기록을 처리한다.
   - 인계 시각부터 기한 안에 등록된 다른 세션이 있으면 `orca terminal close --terminal=<핸들> --tab --json`으로 이전 탭을 닫는다. 등록은 첫 tick에서 일어나므로 새 세션이 살아서 tick을 돌렸다는 근거가 된다
   - 기한 안에 등록된 세션이 없으면 닫지 않고 남긴다. 새 세션이 첫 tick을 못 돌렸다면 이전 탭이 사람이 이어 돌릴 자리라서다
   - 채팅 탭은 닫지 않는다. 오르카 CLI(1.4.256에서 확인)에 채팅 탭을 닫는 명령이 없고 `terminal close`는 채팅 세션을 받지 않는다
   - 오르카가 없거나 닫기가 실패해도 인계와 tick은 그대로 두고 경고만 남긴다

   결과는 `handoff.json`의 `close`(`closed`, `skipped`, `failed`)에 적고 tick JSON의 `handoffClose`에 한 번 싣는다. 아래의 close-claim을 못 만든 `failed`만 예외로 고쳐질 때까지 tick마다 다시 실린다. 텍스트 출력에는 닫았으면 알림 한 줄, 아니면 `경고:` 줄로 찍힌다. `close`가 적힌 기록은 다시 보지 않는다. 오르카가 없거나 채팅 탭이라 `skipped`로 남은 기록, 닫다 실패한 `failed` 기록도 그대로 두고 다시 시도하지 않는다. 탭은 사람이 닫는다. 닫을 탭이 지금 tick을 돌리는 탭과 같거나 기록된 탭 정보가 터미널 핸들 꼴이 아니면 닫지 않고 `skipped`로 남긴다. tick 둘이 같은 기록을 함께 닫지 않게 세션 디렉토리에 `close-claim`을 먼저 만든다. 이 파일에는 잡은 세션과 시각을 적어 둔다. 같은 세션이 다시 인계하면 `handoff` 명령이 새 기록을 쓰기 전에 지운다. 파일을 못 만들면 `failed`를 알리고 기록은 안 남겨 다음 tick이 다시 시도한다. 파일을 잡은 tick이 닫기 도중 끊기면 `close` 없이 파일만 남아 그 기록은 더 안 본다. 이때는 `close-claim`의 시각을 보고 탭을 직접 닫는다. `launched: false`였거나 `previousTab`이 없는 기록, `handoffCloseAfterSec`가 0이면 아무것도 안 한다. 닫히는 시점은 기한이 지난 뒤 첫 tick이라 반복 간격만큼 늦을 수 있다.

   타이머를 이전 세션에 두지 않은 건 그 세션이 이미 반복을 멈췄고 탭이 닫히면 프로세스도 같이 사라져서다. 오르카에는 시간을 두고 탭을 닫는 기능이 없어서 새 세션의 tick이 기한을 확인한다. 이렇게 하면 닫는 쪽이 늘 살아 있는 컨덕터라 컨덕터가 둘 다 사라지는 일이 없다. 이전 세션의 tick은 이미 거절되니 둘 다 도는 일도 없다.

새 세션은 인계 파일을 읽고 규칙을 이어 지킨다. 기다리던 질문은 사람에게 다시 묻고 tick을 한 번 돌린 뒤 감시를 다시 건다. 인계 파일에 반복 문장이 있으면 그 문장으로 반복을 건다. 없으면 [반복 돌리기](#반복-돌리기)대로 감시를 고른다. 백그라운드 명령이 끝날 때 알림이 오는 호스트면 wait를 띄운다. 새 세션은 세션 id가 달라서 컴팩트 횟수를 0부터 센다.

감시는 새 세션 안의 백그라운드 wait나 크론, `ScheduleWakeup`이라 그 세션 프로세스와 함께 사라진다. 탭을 닫으면 감시도 끊기고 이전 세션의 tick은 거절된 채로 남는다. 그래서 새 세션은 첫 보고에 이 탭을 닫지 말아 달라고 알리고 질문은 대화창 도구 말고 일반 텍스트로 묻는다. 대화창이 열려 있는 동안에는 차례가 끝나지 않아 반복이 돌지 못한다. 끊긴 걸 알아채는 장치는 tick 경고다. 앞 tick과 이번 tick 사이가 `staleAfterSec`(기본 1800초)보다 길면 tick이 공백 길이를 `warnings`에 남기고 `gestalt conductor status`도 마지막 tick이 그보다 오래됐으면 지난 시간을 경고로 붙인다. 경고는 반복이 끊겼을 수 있다는 신호다. 한 번만 돌린 세션이나 반복을 안 거는 호스트, 간격이 기준보다 긴 반복에서도 뜬다. wait로 감시하던 세션이면 wait를 다시 띄운다. 반복이었으면 다시 걸지를 대화 기억 말고 반복 표식과 크론 목록으로 정한다. 이전 세션에서 이어 돌리려면 먼저 새 탭이 닫혔는지 사람에게 묻고 답을 받는다. status의 마지막 tick이 기준보다 오래됐는지는 참고로만 본다. 간격이 긴 반복에서도 오래돼 보여서다. 새 세션이 살아 있는데 지우면 컨덕터 둘이 같은 저장소를 돌린다. 닫힌 게 맞으면 `handoff.json`을 지우고 감시(wait나 반복)를 다시 건다.

이 흐름은 Claude Code 전용이다. 세션 id와 컴팩트 훅이 없는 호스트에서는 `handoff`가 출력에 안 실린다. `--state-dir`로 다른 저장소를 쓰면 훅이 그 자리를 몰라 횟수를 못 센다. 훅은 `GESTALT_CONDUCTOR_STATE_DIR`, `~/.gestalt/conductor.json`의 `stateDir`(절대 경로만), 기본값 순서로 저장소를 찾는다.

### 사람이 답할 자리

사람에게 오는 자리는 머지 승인, 슬랙 게시, 인터뷰 답, 리뷰 수동 전환, 파일 겹침 확인이다. 파일 겹침 확인은 같은 레포 워커 둘이 같은 파일을 많이 고칠 때 뒤에 뜬 주문에 열린다([tick 한 번](#tick-한-번)). 승인하면 그 워커가 이어서 진행하고 거절하면 멈추고 `--status done`으로 끝낸다. 대화 중이면 세션이 그 자리의 이유와 참조를 보여 주고 묻는다. 답하면 세션이 확인 자리를 종료하고 결정이 그 워커에 전해진다.

터미널에서 보거나 직접 종료하려면 아래 명령을 쓴다.

```bash
gestalt conductor gate list
gestalt conductor gate resolve <gateId> --approve
gestalt conductor gate resolve <gateId> --approve --answer "보존 기간은 30일"
gestalt conductor gate resolve <gateId> --reject
gestalt conductor gate resolve <gateId> --take-over --answer "머지는 내가 할게"
```

`gate resolve` 응답에 `hostActions`가 실리면 컨덕터 세션이 그걸 실행해야 결정이 워커에 닿는다. 그래서 대화에서 답하는 쪽이 기본이다.

답은 셋 중 하나다. `--answer`는 어느 답에나 붙일 수 있고 워커에는 고정 문구보다 먼저 따르라는 말과 함께 전해진다.

| 답            | 워커가 받는 지시                                                                                                           | 주문                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `--approve`   | 머지 확인 자리면 머지하고 보고한다. 답이 있으면 답이 먼저다                                                                | `running`으로 돌아간다                             |
| `--reject`    | 머지하지 않는다. 답이 있으면 답대로 처리하고 없으면 PR을 그대로 둔다. 어느 쪽이든 기다리지 말고 `--status done`으로 끝낸다 | `running`으로 돌아갔다가 워커 보고로 `done`이 된다 |
| `--take-over` | 사람이 넘겨받았으니 아무것도 하지 말고 종료한다                                                                            | `human-owned`가 되고 tick이 PR 머지를 지켜본다     |

머지를 직접 하겠다면 `--reject`가 아니라 `--take-over`를 쓴다. 거절은 워커가 할 일을 정리하고 끝내는 답이라 주문이 `done`으로 닫히고 사람이 나중에 머지해도 컨덕터가 모른다. 넘겨받기는 주문을 열어 둔 채 머지를 기다리므로 머지 뒤 지라 전환과 배포 처리가 그대로 이어진다.

확인 자리가 없는 주문도 넘겨받거나 취소할 수 있다.

```bash
gestalt conductor order take-over <orderId>
gestalt conductor order cancel <orderId> --reason "요구사항 바뀜"
gestalt conductor order mark-merged <orderId>
```

- `order take-over`는 `gate resolve --take-over`와 같다. 열린 확인 자리를 같이 종료하고 워커에 종료를 전한 뒤 거둔다. 오르카 터미널은 정리하지만 워크트리와 브랜치는 남겨 사람이 그 자리에서 이어 손볼 수 있다.
- `order cancel`은 주문을 `cancelled`로 바꾼다. 살아 있는 워커에 멈추라고 전하고 거두며 정리는 [워커 정리](#워커-정리) 규칙을 따른다. 열린 확인 자리도 같이 종료한다. 머지된 주문은 머지 뒤 처리가 남아 있어 취소하지 않는다.
- `order mark-merged`는 `human-owned`, `parked` 주문과 컨덕터가 쥔 `running`, `waiting-gate`, `escalated` 주문을 받는다. gh로 PR을 한 번 확인해 MERGED일 때만 `merged`로 넘기고 머지 뒤 처리를 태운다. 컨덕터가 쥔 주문이면 넘기기 전에 열린 확인 자리를 종료하고 워커에 종료를 전한다. 워커는 다음 tick의 [워커 정리](#워커-정리)가 거둔다. 아니면 이유를 출력하고 거절한다. 배포 실패로 올라온 `escalated` 주문은 이미 머지돼 있어 받지 않는다.

### 진행 보기와 재개

`gestalt conductor status`가 주문과 워커 상태를 보여 준다. 끝난 주문까지 보려면 `--all`을 붙인다. 컨덕터 세션이 압축되거나 끊겨도 상태는 저장소에 남아 있다. 새 세션에서 스킬을 다시 부르면 status를 읽고 이어 간다.

주문 하나의 결과는 아래 명령으로 읽는다. 주문 제목과 레포, 범위, 상태, 설명, 스킬 체인을 보여준다. 모든 워커의 종류와 에이전트, 상태도 나온다. 보고 이력에는 시각과 상태, 요약이 남고 refs 경로와 PR, gate, bypass도 함께 읽는다. 저장소로 복사한 refs는 보고마다 `사본:` 줄로 나온다. `--json`은 같은 내용을 구조화해 돌려준다.

```bash
gestalt conductor order show <id>
gestalt conductor order show <id> --json
```

`status --all`은 끝난 주문 줄에 마지막 보고 요약을 100자까지 붙인다. `status --all --json`의 `lastSummary`에는 요약 전문이 실린다. 이전 진행 보고는 `order show`로 읽는다. 새 컨덕터 세션에서도 같은 결과를 볼 수 있다. 보고 본문을 저장하지 않던 옛 로그는 복원할 수 없어 빈 이력으로 보인다.

끝난 주문(done, failed, cancelled, parked)이 쌓여 보기 번거로우면 `gestalt conductor order remove <주문 id...> [--json]`으로 지운다. 저장소에 `order-removed` 이벤트를 덧붙이는 방식이라 로그 기록은 남지만 status와 `order show`에서는 더 못 본다. 주문의 워커와 체크포인트, 게이트, bypass 기록도 같이 빠진다. 열린 게이트가 있거나 워커가 아직 돌거나 멈춘 워커가 남은 주문은 거절한다. 멈춘 워커는 워크트리가 남아 있을 수 있어서 기록을 지우면 그 워크트리에서 컨덕터 명령을 막던 가드가 풀린다. 끝난 주문의 멈춘 워커는 tick 정리가 거두니 거절당하면 tick을 한 번 돌린 뒤 다시 부른다. 정리에 실패한 워커는 정리 실패 게이트를 처리해야 지울 수 있다. `parked` 주문의 멈춘 워커는 사람이 워크트리를 쥐고 있을 수 있어 tick이 거두지 않는다. 멈춘 워커가 남은 `parked` 주문은 먼저 취소하고 tick을 돌린 뒤 지운다. tick과 같은 잠금을 잡고 지우니 tick이 도는 중이면 잠시 뒤 다시 부른다. 지운 주문의 출처(지라 티켓, PR, 큐 메시지)는 따로 기억해 두고 다음 tick이 같은 주문을 다시 만들지 않는다. 지운 하위 주문도 상위 주문의 하위 주문 상한에 그대로 센다. 주문의 [refs 사본](#refs-사본)(`refs/<주문 id>/`)도 같은 잠금 안에서 지운다. `refs/`가 심링크면 저장소 밖을 지우게 되고 주문 디렉토리가 심링크면 누가 사본 자리를 바꿔 둔 것이라 둘 다 지우지 않고 경고만 낸다(`--json`의 `warnings`). 사본을 못 지워도 주문 삭제는 되돌리지 않는다. 워크트리와 브랜치는 건드리지 않으니 필요하면 따로 정리한다. 여러 id를 넘기면 지울 수 있는 것만 지우고 나머지는 이유와 함께 알려 준다. 하나도 못 지우면 exit 1이다.

효과를 재려면 `gestalt conductor metrics --since <날짜>`를 쓴다. 무엇을 비교하는지는 [효과 재기](#효과-재기)에 있다.

#### 오르카 플러그인

오르카를 쓰면 레포의 `orca-plugin/`을 개발 폴더로 불러 사이드바 패널과 상태 표시줄에서 진행을 볼 수 있다. 패널은 레포마다 타일을 그린 지도로 시작하고 타일을 누르면 그 레포의 게이트와 주문 위계, 상태별 주문, bypass 사후 보고가 나온다. 탭 바의 + 메뉴에서 "컨덕터 보드"를 고르면 같은 내용을 에디터 탭에 넓게 펼쳐 본다. 상태 표시줄은 `주문 N · 확인 대기 M`을 띄운다. 새 게이트가 열리면 데스크톱 알림을 한 번 띄운다.

탭 바의 + 메뉴에 있는 "컨덕터 터미널"은 어느 워커가 어떤 스킬의 어느 단계에 있는지를 터미널 대시보드처럼 보여 준다. 끝나지 않은 주문마다 카드가 하나씩 뜨고 스킬 체인과 지금 단계, 라운드, 진행 막대, 대기 사유나 rate-limit, 다음 할 일이 붙는다. 이 화면을 위해 `status --json`의 주문마다 `skillChain`과 `checkpoint`(ref와 shipDir는 뺀다), `waiting`, `account`, `rateLimitedAt`, `rateLimitResetsAt`을 싣고 최상위에 `conductor`(감시 주기, 슬롯, 대기 주문, PR 감시 레포, 컴팩트 횟수, 끊긴 워커)와 `recentEvents`(기본 50개)를 싣는다. 최근 이벤트를 읽는 동안 저장소가 계속 바뀌어 못 읽으면 `recentEvents`를 빈 배열로 두고 `recentEventsError`에 이유를 싣는다. 이 필드들은 `--all` 없이도 `--json`이면 늘 실린다. `--all`은 끝난 주문을 함께 싣는 데만 쓴다. 값이 없는 필드는 아예 안 싣는다. 컴팩트 횟수는 지금 도는 컨덕터 세션을 찾았을 때만 들어간다. 대기 이벤트의 기한은 문장에 넣지 않고 `until`에 ISO로 따로 실어서 화면이 카드와 같은 로컬 시각으로 적는다. 카드를 두 번 누르면 워커 터미널로 이동한다. 카드의 "상세"를 펼치면 체크포인트와 그 주문의 최근 이벤트가 나오고 데스크톱에서는 워커 에이전트 상태와 터미널 마지막 줄까지 읽어 온다. 이 때문에 플러그인이 `agent:read`와 `terminal:read` 권한을 받는다. 같은 화면이 사이드바 패널로도 있어서 좁은 폭에서는 세로로 쌓아 보여 준다.

컨덕터 터미널은 워커가 지금 뭘 하는지도 보여 준다. 플러그인이 `status --json --with-activity`를 불러 주문마다 아래 필드를 받는다. 이 플래그는 `--json`과 같이 쓰고 플래그 없는 `status`와 tick 출력에는 이 필드들이 안 실린다. 플래그를 모르는 옛 CLI면 플래그 없이 한 번 더 부르고 작업 내용 칸만 비운다. `running` 주문에 작업 내용이 실려 있으면 저장소가 안 바뀌어도 10초마다 다시 부른다.

| 필드           | 내용                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------- |
| `activity`     | 마지막 tool 이름과 시각. 파일을 고치는 tool이면 대상 경로(`file`)도 싣는다                |
| `changedFiles` | 기준 브랜치와 갈라진 뒤 워크트리에서 고친 파일. 커밋 안 한 변경과 추적 안 한 새 파일 포함 |
| `tasks`        | 워커 에이전트의 todo 제목과 상태, 끝난 개수와 전체 개수                                   |
| `subagents`    | 띄운 서브에이전트 이름과 시작 시각, 상태                                                  |
| `recentTools`  | 최근 tool 호출 8개. 명령이나 설명은 앞부분만 싣는다                                       |
| `history`      | 트랜스크립트를 처음부터 읽었으면 `full`, 앞부분을 건너뛰었으면 `partial`                  |
| `overlapFiles` | 같은 레포 다른 주문과 겹친 파일. 겹친 게 있을 때만 싣는다                                 |

읽지 못한 값은 `null`이다. 트랜스크립트는 Claude 워커만 읽어서 다른 에이전트 워커는 `changedFiles`만 찬다. 카드에는 지금 tool과 고친 파일 수, todo 진행, 서브에이전트 수를 그리고 겹친 파일 옆에 ⚠를 붙인다. 데스크톱 상세는 todo 제목과 서브에이전트, 최근 tool, 터미널 마지막 줄까지 펼치고 "전체 보기"를 누르면 [`browse`](#결과-찾아보기)의 작업 내용 탭(`#order/<id>/work`)을 브라우저로 연다. 플러그인 워커가 `browse --no-open --port 0`을 한 번 띄워 두고 같은 서버를 다시 쓴다. 폰용 페이지는 개수만 싣고 이 링크도 없다.

```bash
orca plugin dev load ./orca-plugin --json
```

처음 부르면 `approval_required`와 함께 받을 권한 목록과 `--approve <fingerprint>`를 붙인 명령이 나온다. 권한을 읽어 보고 그 명령을 직접 다시 부르면 켜진다. 승인은 사람이 한다.

설정의 `gestaltPath`는 오르카가 셸 PATH를 못 물려받을 때 gestalt 절대 경로를 적는 자리다. `stateDir`은 status JSON에 `stateDir`을 안 싣는 옛 CLI를 쓰면서 저장소를 기본 위치 밖에 뒀을 때만 적는다. 둘 다 비워 두면 PATH의 gestalt와 status JSON이 알려 준 저장소를 쓴다. 워커는 `gestalt conductor exec-path --json`으로 실제 bin 경로를 한 번 받아 두고 이후엔 런처를 거치지 않고 node로 바로 부른다. 다시 받는 조건은 [`orca-plugin/README.md`](../orca-plugin/README.md#설정)에 있다.

오르카 모바일은 플러그인 패널을 못 그린다. 폰에서 보려면 설정의 `mobilePort`에 포트를 적는다. 그러면 워커가 그 포트로 이 맥의 루프백에만 보기 전용 페이지를 연다. `tailscale serve`로 그 포트를 테일넷에 이어 폰에서 연다. 게이트와 주문 위계를 보여 주기만 하고 승인과 거절, 지우기는 데스크톱에서 한다. 같은 주소에 `?view=terminal`을 붙이면 컨덕터 터미널 화면을 보기 전용으로 본다. 에디터와 같은 마크업을 쓰고 폭이 좁으면 사이드바처럼 세로로 쌓는다. 상세는 펼칠 수 있지만 워커 터미널 출력은 싣지 않는다. 워커가 직접 쓴 다음 할 일과 대기 사유, bypass 내용, 보고 요약과 계정 이름도 뺀다. 이벤트 로그의 그런 줄은 시각과 유형, 주문 id만 남긴다. 명령과 보안 경계는 [`orca-plugin/README.md`](../orca-plugin/README.md#폰에서-보기)에 있다.

패널의 승인과 거절은 한 번 더 눌러야 확정되고 `gate resolve --defer-delivery`를 부른다. 오르카 워커에는 결정을 그 자리에서 전한다. 플러그인 쪽에 오르카가 안 잡히거나 전하다 실패하면 게이트에 전달 대기를 남기고 다음 tick이 직접 다시 전한다. 전하다 또 실패하면 대기를 그대로 두고 세 번 못 전하면 대기를 걷고 tick 보고의 `errors`에 직접 전해 달라고 남긴다. 컨덕터 세션에도 오르카 런처가 없으면 그 tick에서 대기를 걷고 `errors`에 런처가 없어 못 전했다는 줄만 남긴다. git-worktree와 서브에이전트 워커는 컨덕터 세션만 결정을 전할 수 있어서 게이트에 전달 대기를 남기고 다음 tick이 `hostActions`의 `send`로 내보낸다. 그사이 워커가 끝났으면 결정은 버리고 대기만 걷는다. 이 플래그를 모르는 옛 CLI면 플래그 없이 한 번 더 부르고 돌아온 `hostActions`를 "컨덕터 세션에서 처리할 일"로 보여 주기만 한다. 주문을 맡은 오르카 워크트리를 찾으면 그 주문을 눌러 워크트리로 바로 이동한다. 끝난 주문은 패널과 보드에서 하나씩 또는 레포 단위로 지울 수 있고 이것도 한 번 더 눌러야 `order remove`를 부른다. 자세한 동작은 [`orca-plugin/README.md`](../orca-plugin/README.md)에 있다.

### 결과 찾아보기

워커가 남긴 보고와 refs 파일은 쌓일수록 어느 주문에 뭐가 있었는지 찾기 어려워진다. 세션 중간에 꺼내 볼 때는 터미널 명령을 쓰고 둘러보며 찾을 때는 웹 뷰어를 띄운다. 둘 다 저장소를 읽기만 하고 tick 잠금을 잡지 않아서 컨덕터가 도는 중에도 부를 수 있다. 저장소 위치는 다른 컨덕터 명령과 같은 순서로 정하고 `--state-dir`도 받는다. 지운 주문은 나오지 않는다.

```bash
gestalt conductor results list [--repo <owner/name>] [--status <s>] [--since <날짜>] [--limit N] [--json]
gestalt conductor results search <키워드> [--repo] [--status] [--since] [--limit N] [--no-body] [--json]
gestalt conductor results show <주문 id> [--report <n>] [--no-body] [--json]
gestalt conductor browse [--port N] [--no-open]
```

- `results list`는 끝난 주문까지 최근 갱신순으로 30개를 보여 준다. 한 줄에 주문 id와 상태, 레포, 날짜, 보고 수, 참조 수, 제목이 들어간다.
- `results search`는 주문 제목과 보고 요약, 읽을 수 있는 refs 본문, 저장소의 결과 파일에서 대소문자를 가리지 않고 찾는다. 결과마다 주문과 보고 시각, 맞은 자리(요약 번호나 파일 경로와 줄 번호)를 붙이고 앞뒤 80자를 잘라 보여 준다. 파일 하나에서는 세 건까지만 내고 그 파일에 더 맞은 줄이 있으면 몇 건 더 있는지 붙인다. 머리 줄의 전체 건수는 파일당 상한 때문에 결과로 안 낸 줄까지 센 수라 "전체 N건 중 M건만 보여요"로 찍힌다. 1MB가 넘어 앞 256KB만 읽은 파일은 읽은 부분에서만 찾는다. 이렇게 앞부분만 읽은 파일이 하나라도 있으면 맞은 줄이 없어도 한 줄 안내를 붙인다. `--since`에 날짜만 적으면 로컬 날짜의 자정부터 센다. `--no-body`를 붙이면 제목과 요약만 찾는다. 개행이 든 검색어는 제목과 요약에서만 찾는다. `--repo`나 `--status`를 걸면 주문에 안 묶인 파일은 뺀다. 웹 뷰어에서 지라 키로 걸러도 마찬가지다.
- `results show`는 주문 머리(제목, 레포, 상태, 지라 키, PR)를 먼저 찍고 보고 타임라인과 사람 확인, bypass, 참조 목록을 이어 찍은 뒤 읽을 수 있는 refs 본문을 원문 그대로 붙인다. 주문 id는 앞부분만 적어도 하나로 정해지면 받는다. 여럿이 걸리면 후보를 보여 주고 exit 1이다. `--report <n>`은 그 보고 하나와 그 보고가 적은 refs만 보여 준다.
- `--json`은 에이전트가 읽을 구조를 그대로 돌려준다. search 결과의 `matchStart`와 `matchLength`는 발췌 안에서 맞은 자리다. 바로 읽을 수 있게 실제 경로(`absPath`)도 싣는데 저장소 파일 결과에만 있다. refs 결과의 `where`는 워커가 적은 원문 경로고 디렉토리 항목이면 그 경로 뒤에 파일 이름을 붙인다. 디렉토리 ref는 앞 50개 파일만 싣고 `entriesTotal`에 자르기 전 파일 수를 적는다. search 결과에 `partialFiles`가 있으면 크기 때문에 앞부분만 찾은 파일 수다. 0건이어도 맞는 줄이 그 파일 뒷부분에 있을 수 있다. 그럴 땐 없다고 단정하지 말고 큰 파일은 앞 256KB만 찾았다고 밝힌다.

`browse`는 127.0.0.1에만 붙는 로컬 서버를 띄우고 브라우저를 연다. 포트는 7894부터 빈 곳을 찾는다. 왼쪽은 레포, 상태, 날짜, 지라 키로 거르는 주문 목록이다. 목록은 레포별로 묶어 보여 주고 티켓이나 PR, 날짜, 상태별로 바꿔 묶거나 묶음을 풀 수 있다. 고른 묶는 방식은 브라우저에 남는다. 오른쪽은 고른 주문의 설명과 보고 타임라인, PR 링크, 사람 확인, bypass, refs 카드다. 설명과 보고 요약도 마크다운으로 그리고 설명은 보고가 있으면 접어 둔다. refs 카드를 펼치면 마크다운 본문을 그려서 보여 주고 원문도 함께 펼쳐 볼 수 있다. 512KB가 넘거나 한 줄이 1만 자를 넘는 마크다운과 마크다운이 아닌 파일은 원문 그대로 보여 준다. 위쪽 검색창은 `results search`와 같은 검색을 돌리고 결과를 누르면 그 보고나 refs 자리로 바로 간다. 주소 해시(`#order/<id>`)에 위치가 남아서 새로고침해도 같은 자리를 연다. 서버가 떠 있는 동안 `events.jsonl`이 바뀌면 다음 요청에서 다시 읽는다. 파일 본문은 따로 캐시하는데 파일이 바뀌면(수정 시각이나 크기가 달라지면) `events.jsonl`이 그대로여도 다음 요청에서 다시 읽는다. 이 캐시는 `events.jsonl`이 바뀌어 다시 읽을 때도 이어 쓴다. 검색은 캐시에 있으면 쓰지만 캐시를 채우지 않는다. 주문 없는 파일 목록은 `events.jsonl`이 바뀔 때만 다시 모은다. Ctrl+C로 멈춘다.

주문 상세의 "작업 내용" 탭(`#order/<id>/work`)은 워커가 실제로 한 일을 재개 회차별로 묶어 보여 준다. 회차마다 tool 호출 타임라인과 assistant가 쓴 글을 시간순으로 섞어 그리고 todo와 서브에이전트, 고친 파일 목록을 붙인다. tool 결과 본문은 보여 주지 않는다. 아직 도는 워커가 있으면 5초마다 이어서 읽는다. 서버가 회차마다 읽던 자리를 메모리에 들고 있어서 새 줄만 읽는다. 회차마다 어디서 그렸는지가 붙는다. 트랜스크립트를 읽었으면 `transcript`, 트랜스크립트가 지워졌거나 다른 머신으로 옮겨져서 저장해 둔 [타임라인 요약](#상태-저장소)으로 그렸으면 `summary`, 둘 다 없으면 `none`이다. 요약으로 그린 회차에는 assistant 글이 없다. 트랜스크립트 앞부분을 건너뛰고 읽었으면 그렇다고 표시한다. 트랜스크립트 파일은 요청이 정하지 않는다. API(`/api/orders/<id>/work`)는 주문 id만 받고 서버가 그 주문 워커의 기록으로 파일을 찾는다. 응답에 파일 경로는 싣지 않고 다른 API와 같은 Host와 Origin 검사를 거친다.

refs는 워커가 적은 값이라 아무 파일이나 읽지 않는다. 본문을 읽는 건 아래 자리 안의 파일뿐이다.

- 상태 저장소 디렉토리
- `~/.gestalt/conductor.json`의 `repoPaths`에 적은 레포 경로 (레포의 gestalt.json 값은 안 받는다)
- 그 주문 워커의 워크트리. git 워크트리 워커는 저장소에 남은 경로를 쓰고 오르카 워커는 `<주문 id>-<회차>` 디렉토리 이름으로 알아본다. 오르카 쪽은 위치를 따로 묻지 않아서 상위 경로 어디든 그 이름의 디렉토리가 있으면 그 아래를 허용한다

경로는 심링크를 푼 실제 경로로 비교해서 `..`나 심링크로 밖에 나가는 경로를 막는다. 확장자는 md, markdown, txt, log, json, diff, patch만 읽고 1MB가 넘으면 앞 256KB만 보여 준다. 임시 디렉토리처럼 이 자리 밖을 가리키는 refs는 경로만 보이고 본문은 안 읽는다. 이미 없는 파일은 없음으로, 상대 경로나 커밋 SHA는 참조 글자로 보인다. 링크는 http와 https만 건다.

어느 주문 refs에도 안 걸린 저장소 파일도 모아서 보여 준다. `reports/`, `refs/`, `results/`, `artifacts/`, `notes/`, `drafts/` 아래와 저장소 최상위에서 이름이 `ord-`나 `wrk-`로 시작하는 디렉토리 아래, 저장소 최상위의 md 파일이 대상이다. 디렉토리는 하위까지 다 훑고 읽을 수 있는 확장자만 모은다. 프롬프트나 인계 파일처럼 운영에 쓰는 `prompts/`, `handoffs/`, `sessions/`, `inbox/`, `context/`, `deploy/`, `slack/` 같은 자리는 뺀다. 파일 이름이나 상위 디렉토리 이름에 주문 id가 있으면 그 주문의 관련 파일로 붙고 없으면 웹 뷰어의 "주문 없는 파일" 묶음에 들어간다. 어느 주문에도 안 걸린 파일을 찾는 디렉토리 목록은 읽는 쪽이 훑는 자리일 뿐이다. 워커가 따를 경로 규칙은 아니다.

웹 뷰어가 그리는 보고와 본문도 [바깥 텍스트](#바깥-텍스트는-자료다)다. 원시 HTML은 글자로 보이고 스크립트는 페이지에 박힌 것 하나만 돈다. 요청이 경로를 정하지 못하게 파일은 주문 id와 refs 번호, 서버가 모을 때 붙인 키로만 고른다. 다른 사이트에서 온 요청과 127.0.0.1이나 localhost가 아닌 Host는 거절한다.

## 바깥 텍스트는 자료다

지라 티켓, 외부 큐 본문, PR 제목과 코멘트, 워커 보고(요약과 `refs` 파일 본문)는 자료로만 읽는다. 거기 적힌 문장이 주문 범위나 승인, 절차를 바꾸지 못한다. 범위는 사용자가 넣은 값이나 `defaultScope`가 정하고 사람에게 물을 자리는 아래 [주문 범위와 사람 확인](#주문-범위와-사람-확인)의 표가 정한다. 규칙 전체는 `plugin/skills/_shared/untrusted-input.md`에 있다.

## 왜 tick이 외부에 직접 쓰지 않나

Execute Engine처럼 컨덕터도 Passthrough로 돈다. 추론 주체는 호스트 세션이고 tick은 상태를 계산해 할 일만 돌려준다. 지라 전환과 슬랙 게시는 사람 계정의 MCP 연결이 필요해 CLI 프로세스가 직접 하지 못한다. 그래서 `hostActions`에 담아 돌려주고 호스트 세션이 실행한다.

| hostAction        | 나오는 때                                               |
| ----------------- | ------------------------------------------------------- |
| `spawn-subagent`  | 서브에이전트 워커를 띄울 때. `promptFile`에 지시가 있다 |
| `open-session`    | 오르카가 없어 git 워크트리에 새 세션을 열 때            |
| `send`            | 살아 있는 워커에 사람 결정이나 bypass 결과를 전할 때    |
| `jira-transition` | 주문 단계가 바뀌어 지라 상태를 옮길 때                  |
| `slack-post`      | 사람이 승인한 슬랙 초안을 게시할 때                     |

gh로 읽을 수 있는 PR 목록과 계정 전환은 tick이 직접 한다. 오르카 워커도 오르카 CLI로 직접 띄운다.

## 상태 저장소

주문, 워커, 체크포인트, 사람 확인 자리(gate), bypass 기록은 전부 `events.jsonl`에 이벤트로 한 줄씩 덧붙는다. 상태는 `base.json`이 있으면 거기서 시작해 남은 `segments/`와 이 로그를 이어서 재생해 만든다. 없으면 로그를 처음부터 재생한다. 컨덕터 세션이 압축되거나 새로 떠도 같은 저장소를 열면 같은 상태에서 이어 간다. 조회용 `snapshot.json`은 tick이나 `order remove`, `archive`가 끝날 때 들여쓰기 없이 쓴다. 상태 안 워커와 게이트를 주문 id로 찾을 때는 상태가 바뀔 때마다 한 번 만든 주문 id별 인덱스를 쓴다.

`events.jsonl`을 떼어 내 `base.json`에 반영하는 일은 [끝난 주문 보관](#끝난-주문-보관)(`archive` 명령)이 함께 한다. tick은 아직 부르지 않는다. 설계는 [`proposals/conductor-archive.md`](./proposals/conductor-archive.md)에 있다.

- 워커가 잠금 없이 덧붙이므로 로그를 다시 쓰지 않고 이름만 바꿔 `segments/`로 옮긴다. 이름을 바꾸기 직전에 연 쪽이 옛 파일에 쓰는 줄은 크기가 멈출 때까지 기다렸다 읽는다.
- 그보다 늦게 붙는 줄도 잃지 않게 반영한 segment를 바로 지우지 않는다. `base.json`의 `foldedSegments`에 이름과 반영한 길이를 적고 읽는 쪽은 그 길이 뒤만 재생한다. 다음 반영이 남은 꼬리를 마저 반영하고 지운다. 그 사이 줄이 또 붙었으면 한 번 더 미룬다. 한 주기가 지나도 끝나지 않은 반쪽 줄은 쓰다 죽은 흔적이라 로그를 남기고 버린다. 줄바꿈 없이 끝났어도 JSON으로 읽히는 마지막 줄은 재생이 적용하는 줄이라 반영 길이에 넣는다.
- segment 이름은 순번 10자리로 시작한다. 시계가 뒤로 가도 이름 순서가 떼어 낸 순서다.
- tick과 같은 `tick.lock`을 잡는다. 못 잡으면 이번엔 넘긴다.
- 어느 단계에서 죽어도 다시 열면 같은 상태가 나온다. `base.json`을 쓰기 전이면 남은 segment를 처음부터 재생한다. `base.json`은 fsync한 뒤에만 segment를 지운다.
- 잠금 없이 읽는 쪽은 재생 앞뒤로 `base.json`과 segment 목록을 비교해 바뀌었으면 다시 읽는다. 다섯 번 읽어도 계속 바뀌면 어긋난 상태를 돌려주지 않고 에러를 낸다. 최근 이벤트를 읽을 때도 같다.
- 결과 보기(`results`, 웹 뷰어)와 최근 이벤트도 같은 순서로 읽는다. 최근 이벤트는 `events.jsonl`에서 모자라면 남은 segment 끝을 이어서 읽는다. 웹 뷰어는 `base.json`과 segment마다의 크기, `events.jsonl`이 바뀌었을 때만 다시 읽는다.
- 떼어 낸 뒤에는 `base.json`을 모르는 0.153.0 전 gestalt가 이 저장소를 열면 `events.jsonl`만 재생해 상태를 잘못 만든다. 0.153.0도 `archivedOrders`를 몰라서 보관한 주문의 출처를 다시 받고 PR 감시가 주문을 다시 만든다. `archive`를 처음 부르기 전에 컨덕터 세션과 워커가 쓰는 gestalt를 `archive` 명령이 들어간 버전으로 맞춘다.
- 반영하면서 이벤트를 주문별로 `order-logs/<주문 id>.jsonl`에 덧붙여 둔다. segment는 다음 반영 때 지워지므로 나중에 그 주문을 보관할 때 이 파일로 이벤트를 모은다. 덧붙이기 전에 줄이 닿은 주문의 파일 크기와 이번 반영 id를 `order-logs/.staging.json`에 적고 `base.json`에도 같은 id(`orderLogsFold`)를 적는다. 두 id가 다르면 지난 반영이 덧붙인 뒤 `base.json`을 못 쓰고 죽은 것이라 다음 반영이 적어 둔 크기로 되돌리고 그 범위를 다시 읽어 덧붙인다. 파일 끝에 끝나지 않은 줄이 있으면 덧붙이기 전에 잘라 낸다. fsync는 반영 한 번에 줄이 닿은 주문 수 + 4번(기록 파일과 그 rename, 새 파일 엔트리, `order-logs/`를 새로 만든 경우 저장소 디렉토리)이다. 끝나지 않은 줄을 자르거나 죽은 반영을 되돌린 파일은 한 번씩 더 든다. 0.158.0은 반영 범위마다 `order-logs/<주문 id>/<segment>.<시작 바이트>.jsonl`을 따로 썼다. 그 파일이 남아 있으면 보관할 때 이름 순서로 앞에 잇고 단일 파일을 뒤에 잇는다. 주문을 찾는 규칙은 제안서의 [이벤트를 주문에 붙이는 규칙](./proposals/conductor-archive.md#이벤트를-주문에-붙이는-규칙)과 같다. tick과 `tail-repaired`, 주문 없는 게이트, `report` 없이 이름만 있는 옛 `report-applied` 줄은 모으지 않는다. 마지막 것은 `appliedReports`에만 쓰이고 그건 `base.json`에 들어간다. 첫 반영 전 로그는 첫 반영이 처음부터 재생하며 모은다.

| 경로                           | 쓰는 쪽         | 내용                                                                                                                                                                                                                                                                      |
| ------------------------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events.jsonl`                 | tick, CLI 명령  | 상태 이벤트와 실제 워커 에이전트, 보고 이력. `report-applied`에 workerId, status, summary, refs, skill, prRef, merged, stopReason, need, refCopies를 보존하며 진행 보고도 포함한다. 하위 주문 요청(`spawnRequest`)은 주문 이벤트로 옮겨지므로 보고에는 다시 남기지 않는다 |

| `segments/`                    | 떼어 내기       | `events.jsonl`에서 떼어 낸 로그. 반영한 뒤에도 다음 반영 때까지 남겨 두고 그때 지운다                                                                                                                                                                                     |

### refs 사본

워커는 결과 원문을 `/tmp`나 자기 워크트리에 두고 경로만 보낸다. 그 파일은 워커를 거두거나 재부팅하면 사라지므로 tick이 보고를 적용할 때 저장소 밖 텍스트 파일을 `refs/<주문 id>/<해시>-<파일 이름>`으로 복사한다.

- 절대 경로와 `~/` 경로만 본다. 상대 경로는 워커 작업 디렉토리 기준이라 컨덕터가 풀 수 없어 건너뛴다. 무엇을 가리키는지 컨덕터가 판정하지 못했으니 컨덕터 스킬은 내용을 읽으려는 상대 경로 ref를 `denied`와 같게 다룬다.
- 확장자가 md, markdown, txt, log, json, diff, patch인 일반 파일만 복사한다. 주소, 디렉토리, 없는 파일, 앞 8KB에 NUL이 있는 파일은 그대로 둔다.
- 마지막 칸이 심링크인 경로, `..`이 들어간 경로, 이미 저장소 안에 있는 파일은 복사하지 않는다. `..` 경로는 `/`나 `\`로 나눈 칸 하나가 `..`인 경로다(`a..b.diff` 같은 이름은 아니다). 이런 경로는 풀어 본 자리가 아래 거부 대상이면 `denied`로 남긴다. 기록이 없어도 컨덕터 스킬은 `..` 경로 ref를 `denied`와 같게 다룬다. 저장소 안이어도 `worktrees/` 아래 git 워커 워크트리는 워커를 거둘 때 지워지므로 복사한다. 기본 저장소가 `~/.gestalt` 아래라 실제 경로가 워크트리 안인 파일은 아래 자리 판정을 건너뛰고 이름 판정만 받는다. 워크트리 안의 심링크가 밖을 가리키면 실제 경로가 워크트리 밖이라 자리 판정을 그대로 받는다. 중간 디렉토리 심링크는 풀어서 실제 위치로 판정한다. macOS의 `/tmp`와 `/var`가 `/private` 아래로 가는 심링크라 막으면 워커 결과를 두는 주된 자리가 다 빠진다. `refs/`나 주문 디렉토리가 심링크로 바뀌어 있어도 쓰지 않는다. 다른 경로로 같은 파일을 가리키는 ref끼리는 사본 하나를 같이 쓴다.
- 비밀 값이 있을 만한 자리는 복사하지 않는다. 홈 바로 아래 점 디렉토리(`~/.claude`, `~/.config` 같은 곳)와 `~/Library`가 그렇다. `~/Library` 중 오르카 첨부 자리(`Application Support/orca/agent-session-attachments/`, `Application Support/orca/chat-scratch/`)는 복사한다. 레포 안 `.git/`처럼 홈에서 깊은 점 디렉토리도 복사한다. 자리는 워커가 적은 경로와 심링크를 푼 실제 경로를 둘 다 보고 대소문자는 가리지 않는다. `~/.docker`가 다른 디렉토리로 가는 심링크여도, `~/library`나 홈 앞부분처럼 대소문자만 바꿔 적어도 막힌다. 이름에 credential, secret, token이 들어간 파일은 어디 있든 막는다. 부분 일치라 `design-tokens.json`처럼 비밀이 아닌 파일도 막히는데 놓치는 쪽보다 덜 복사하는 쪽을 골랐다. 확장자를 뗀 이름의 끝 낱말이 password, passwords, passwd, apikey, auth, kubeconfig이거나(auth는 md와 markdown 파일이면 `login-auth.md` 같은 문서로 보고 복사한다), 이름이 api key, private key, service account(-key)로 끝나거나, 낱말에 adminsdk가 있어도 막는다. `.env`, `.env.local`, `prod.env`, `.envrc` 같은 환경 변수 파일도 막고 `.env.example`, `.env.sample`, `.env.template`은 둔다. 비밀 자리나 이름이면 복사 대상 확장자가 아니어도(`~/.ssh/id_rsa`, `~/.aws/credentials`), 마지막 칸이 심링크여서 복사하지 않는 ref여도 실제 경로로 판정해 `denied`로 남긴다. 기록이 없으면 컨덕터 스킬이 원래 경로를 읽기 때문이다. `password-reset-flow.md`처럼 그 말로 시작하는 문서는 복사한다. 이름만으로는 비밀 파일을 다 가려내지 못한다.
- 사본 디렉토리는 0700, 사본 파일은 0600으로 만든다. 원본이 소유자만 읽는 파일이어도 사본에서 권한이 풀리지 않는다.
- 파일 하나는 256KB까지 남기고 넘으면 앞부분만 남긴다. 보고 하나의 합계는 1MB까지이고 남은 양에 못 들어가는 파일은 읽지 않고 건너뛴다. 그 뒤의 작은 파일은 남은 양 안에서 계속 복사한다. 같은 ref가 두 번 오면 한 번만 복사한다. 2026-11-20 저장소에 남아 있던 refs 파일 154개가 최대 111KB, 보고 하나에 실린 절대 경로가 많아야 3개였던 것을 보고 정했다.
- 복사가 실패해도 보고 적용과 기록은 그대로 간다. 적용 뒤 기록만 실패한 보고는 다음 tick이 기록할 때 다시 복사한다. 그 사이 원본이 사라졌으면 `refCopies`가 비고 앞서 쓴 사본은 이벤트가 가리키지 않는 파일로 남는다.

이벤트의 `refs`는 워커가 보낸 값 그대로 두고 사본 결과는 `refCopies`에 따로 남긴다. 항목마다 원래 값(`ref`)과 저장소 기준 사본 경로(`path`)가 있고 앞부분만 남겼으면 `truncated`와 원래 크기(`size`), 복사하지 않았으면 `skipped`(`report-limit`, `denied`, `error` 중 하나)가 붙는다. 복사 대상이 아닌 ref는 비밀 자리나 이름으로 거부한 경우만 `refCopies`에 `denied`로 있다. 컨덕터 스킬은 값의 꼴이 아니라 하는 일로 가른다. 사본이 없는 ref로 파일 본문을 읽으려는데 상대 경로이거나 `..` 칸이 있으면 기록과 상관없이 `denied`처럼 다룬다. 커밋 SHA나 브랜치 이름 ref로는 메타데이터만 보고 본문이나 diff(`git show`, `git diff`, `git log -p`)를 읽는 일은 `denied`처럼 다룬다. 주소, PR 약칭, 지라 키는 그 서비스에서 상태를 보는 데만 쓴다. `path`는 저장소 기준이라 `order show --json`의 `stateDir` 아래에 붙여 읽는다. 컨덕터 스킬은 사본이 있으면 원래 경로보다 사본을 먼저 읽는다. 같은 PR에 리뷰 주문이 두 번 생기면 워커가 같은 경로에 결과를 덮어써서 원래 경로가 뒤 주문의 본문을 가리킬 수 있어서다. `truncated`면 원래 파일 크기가 `size`와 같을 때만 나머지를 원래 경로에서 읽는다. `skipped`가 `denied`인 ref는 원래 경로를 바로 읽지 않고 사용자에게 알린 뒤 사용자가 지시할 때만 읽는다. 컨덕터 세션의 작업 디렉토리는 저장소가 아니다. 이 칸이 없는 옛 이벤트도 그대로 재생된다.

위치는 `--state-dir`, `GESTALT_CONDUCTOR_STATE_DIR`, `~/.gestalt/conductor.json`의 `stateDir`, 기본값 `~/.gestalt/conductor` 순서로 정한다. 워커는 다른 레포에서 돌아 그쪽 `gestalt.json`을 읽기 때문에 워커 지시에는 저장소 절대 경로를 `--state-dir`로 박아 둔다.

### 끝난 주문 보관

`gestalt conductor archive [--older-than <일>] [--dry-run] [--json]`은 끝나고(`updatedAt` 기준) 기간이 지난 주문을 `archive/<YYYY-MM>/<주문 id>/`로 옮기고 상태에서 뺀다. 기간은 기본 14일이고 `YYYY-MM`은 주문이 끝난 달이다. tick이 하루 한 번 같은 일을 하고(아래 [tick이 하루 한 번 보관](#tick이-하루-한-번-보관)) 사람도 언제든 부를 수 있다.

- `events.jsonl`을 떼어 반영하는 일과 한 번에 돈다. tick과 같은 잠금을 잡고 못 잡으면 exit 1로 끝난다. `--dry-run`은 잠금 없이 옮길 주문만 보여 준다.
- 옮기는 주문은 `order remove`가 받아 주는 주문과 같다. 끝난 주문(done, failed, cancelled, parked) 중 열린 게이트나 멈춘 워커가 남은 주문은 옮기지 않고 이유를 `blocked`에 남긴다. 여기에 tick이 아직 할 일이 남은 주문도 막는다. 워커가 finished나 failed로 남아 아직 안 거둔 주문, 그 주문 워커의 정리 실패 게이트가 열려 있는 주문, 승인했지만 아직 슬랙에 안 올린 `slack-post`가 있는 주문이다. 옮기면 tick이 그 일을 할 근거가 상태에서 사라진다.
- 주문 디렉토리에는 넷을 둔다. `events.jsonl`은 `order-logs/`에 모아 둔 그 주문의 이벤트 줄을 원래 값 그대로 이은 것이다. `order.json`은 `order show --json`과 같은 꼴에 `stateDir` 대신 보관한 시각(`archivedAt`)을 둔다. `refs/`는 `refs/<주문 id>/`를 복사한 것이고 `order.json`의 `refCopies[].path`는 옮긴 자리(`archive/<YYYY-MM>/<주문 id>/refs/...`)로 바꿔 적는다. `workers/<워커 id>.summary.json`은 그 주문 워커의 타임라인 요약(`activity/<워커 id>.summary.json`)을 복사한 것이다. 모아 둔 이벤트가 없으면(손으로 `order-logs/`를 지운 경우) 빈 `events.jsonl`을 쓰고 `warnings`에 남긴다.
- 상태에서는 `order remove`와 같은 규칙으로 주문과 워커, 체크포인트, 게이트, bypass, 지라 전이, 보고를 빼고 `archivedOrders`에 출처(`sourceRef`), 상위 주문, 보관 시각과 달을 남긴다. 지운 주문처럼 같은 출처를 다시 받지 않는다. 상위 주문이 하위 주문을 몇 개 만들었는지 셀 때도 넣는다. parked 주문이면 사람에게 넘긴 PR을 `humanPr`로 남겨 PR 감시가 그 PR로 주문을 새로 만들지 않는다.
- `order remove`로 지운 주문은 지운 시각에서 같은 기간이 지나면 모아 둔 이벤트만 `archive/<지운 달>/<주문 id>/events.jsonl`로 옮기고 `removedOrders`의 그 주문에 옮긴 달(`archived`)을 적는다. 모아 둔 이벤트가 없으면 달만 적는다. 한 번 옮긴 지운 주문은 다시 옮기지 않는다.
- 주문에 안 붙는 컨덕터 게이트는 닫히고 같은 기간이 지나면 상태에서 버린다. 다만 그 게이트가 있어야 도는 일이 남았으면 둔다. 승인했지만 후속 재리뷰 주문(`<sourceRef>:approved`)이 아직 없는 `review-manual-switch`, 승인했지만 아직 슬랙에 안 올린 `slack-post`, 승인했지만 워커가 아직 released가 아닌 정리 실패 게이트가 그렇다. 버리는 게이트에 `sourceRef`가 있으면 `askedSourceRefs`에 출처와 닫힌 시각만 남긴다. PR 감시의 `review-manual-switch`와 접수의 `no-procedure`가 같은 질문을 다시 안 여는 근거라서 두 곳 다 `gates`와 이 색인을 함께 본다. 승인한 `review-manual-switch`는 후속 주문이 생긴 뒤에만 옮기므로 tick이 승인 게이트를 훑어 후속 주문을 만드는 자리는 상태에 남은 게이트만 봐도 된다. 색인은 `removedOrders`처럼 늘기만 한다.
- 보관 파일과 refs 사본, 새로 만든 보관 디렉토리와 `base.json`을 다 쓰고 fsync한 뒤에 `order-logs/<주문 id>.jsonl`(0.158.0이 남긴 `order-logs/<주문 id>/`가 있으면 그것도)과 `refs/<주문 id>/`를 지운다. 지운 주문도 같다. `base.json`을 쓰기 전에 죽으면 모아 둔 이벤트가 그대로라 다시 불렀을 때 같은 자리에 같은 내용을 덮어쓴다. `base.json`까지 쓰고 죽어 남은 파일은 다음 보관이 보관 기록(`archivedOrders`, `removedOrders`의 `archived`)을 보고 지운다.
- 옮긴 뒤에 그 주문으로 붙는 줄은 모으지 않고 버린다. 재생할 때도 지우거나 옮긴 주문에 워커, 체크포인트, 게이트, bypass, 지라 전이를 다시 붙이지 않는다. 없는 게이트에 온 `slack-posted`도 버린다. 끝나고 기간이 지났고 도는 워커와 열린 게이트가 없는 주문만 옮기므로 그런 줄은 옮기는 순간에 늦게 쓴 경우뿐이다.
- `results show`에 보관한 주문 id를 주면 보관소 자리를 알려 준다. 묶은 달이면 `archive/<YYYY-MM>.tar.gz` 안의 자리를, `archive prune`으로 지운 달이면 지웠다는 사실을 알려 준다. 결과 뷰어가 보관소를 읽는 일은 뒤에 따로 한다.

#### 운영 파일 정리

보관할 때 결과를 읽는 데 필요 없는 운영 파일도 지운다. 보관 결과의 `swept`에 지운 개수가 나온다.

- `prompts/<워커 id>.md`와 `activity/<워커 id>.*`는 그 워커가 상태에 없고 하루 넘게 안 바뀐 파일만 지운다. 워커는 주문을 보관하거나 `order remove`로 지울 때 상태에서 빠진다. 보관하는 순간에는 그 주문의 워커가 아직 상태에 있으므로 다음 보관 때 지운다. 워커 요약은 주문을 보관할 때 보관소의 `workers/`로 복사해 둔다. `order remove`로 지운 주문은 이벤트만 옮기므로 그 워커의 요약은 복사하지 않고 같이 지운다.
- `handoffs/`는 보관 기간(`--older-than`, 기본 14일)보다 오래된 인계 파일(`<시각>-<세션 id>.md`)을 지운다. 인계 파일은 주문이 아니라 컨덕터 세션에 붙어 있어서다. `--older-than 0`이어도 하루 안 된 파일은 새 세션이 아직 안 읽었을 수 있어 둔다. 그 꼴이 아닌 파일은 사람이 둔 것으로 보고 안 지운다.
- `prompts/`는 `.md` 파일만 본다. 심링크나 디렉토리는 건드리지 않는다. `inbox/failed/`는 사람이 볼 자리라 그대로 둔다.

#### 지난 달 묶기와 지우기

끝나고 한 달이 지난 달의 `archive/<YYYY-MM>/`은 `archive/<YYYY-MM>.tar.gz`로 묶고 디렉토리를 지운다. 11월 23일이면 9월까지가 대상이다. `archive` 명령과 tick이 보관을 마쳐 잠금을 놓은 뒤 다시 잡고 묶는다.

- 끝난 지 오래된 주문은 게이트나 워커가 풀린 뒤에야 보관된다. 그 주문이 끝난 달을 이미 묶었으면 디렉토리가 다시 생긴다. 다음 묶기가 묶음을 풀어 합치고 다시 묶는다. 같은 파일이 양쪽에 있으면 디렉토리 쪽이 나중에 쓴 것이라 그쪽을 남긴다.
- 새 묶음을 임시 이름으로 쓰고 fsync한 뒤 이름을 바꾸고 그다음에 디렉토리를 지운다. 어디서 죽어도 다시 부르면 끝까지 간다.
- 시스템 `tar`를 부른다. 풀기 전에 묶음 안 이름이 전부 그 달 디렉토리 아래인지 보고 링크 항목은 대상도 본다. 심링크 대상이 절대 경로거나 `..`를 거치면, 하드링크 대상이 그 달 밖이면 풀지 않는다. 새 묶음은 디렉토리의 항목이 다 들어갔는지 확인한 뒤에 이름을 바꾼다. 못 묶은 달은 `warnings`에 tar의 오류 앞 몇 줄과 함께 남기고 다음 달로 넘어간다.
- 한 번에 오래된 달부터 두 달까지만 묶는다. 잠금을 잡고 1시간이 지났으면 새 달을 시작하지 않는다. 남은 달은 다음 보관 때 이어서 묶고 `warnings`에 몇 달 남았는지 적는다. 밀린 달은 tick 기준으로 하루에 두 달씩 줄어든다. 못 묶은 달은 이 두 달에 안 센다.
- 묶다 죽어 남은 임시 파일(`<YYYY-MM>.tar.gz.tmp`, `.<YYYY-MM>.merge`)은 다음 묶기가 치운다. `archive prune`도 지우는 달의 임시 파일을 같이 지운다.

지우기는 자동으로 하지 않는다. `gestalt conductor archive prune --before <YYYY-MM> [--dry-run] [--json]`이 그 달보다 앞선 `archive/<YYYY-MM>/`과 `archive/<YYYY-MM>.tar.gz`를 지운다. 끝나고 한 달이 안 지난 달은 받지 않는다(11월이면 `--before`는 `2026-10`까지). 상태의 `archivedOrders` 기록은 남기므로 지운 주문의 출처를 다시 받지 않는다.

#### tick이 하루 한 번 보관

tick은 잠금을 놓은 뒤 하루에 한 번 보관과 운영 파일 정리, 지난 달 묶기를 차례로 한다. 마지막으로 돌린 시각은 `archive/last-run.json`에 남긴다. 잠금을 못 잡으면 시각을 안 남겨서 다음 tick이 다시 해 본다. 보관이 오류로 멈추면 실패 시각(`failedAt`)을 남기고 한 시간 뒤에 다시 해 본다. 같은 실패가 tick마다 되풀이되지 않게 하려는 것이다. 시계가 뒤로 가서 남은 시각이 지금보다 미래면 없는 값으로 보고 바로 돈다. 감시 간격 안이라 건너뛴 tick은 보관을 안 부른다.

- 돈 tick의 응답에는 `archive`(옮긴 주문, 지운 주문, 버린 게이트 수, 못 옮긴 주문과 이유, 묶은 달, 지운 운영 파일 수)가 붙는다. 보관 경고는 `보관:`을 붙여 `warnings`에 싣고 못 옮긴 주문이 있으면 개수와 앞쪽 id 다섯 개를 한 줄로 남긴다. 이유는 `archive --dry-run`으로 본다.
- 보관이 실패해도 tick 결과는 그대로 두고 `errors`에 `보관 실패:`로 남긴다.
- 끄려면 `~/.gestalt/conductor.json`에 `"archive": { "enabled": false }`를 적는다. 파일을 지우는 일이라 레포 `gestalt.json`의 값은 받지 않는다. 기간은 14일로 고정이고 다르게 하려면 끄고 `archive --older-than`을 사람이 부른다.

### 워커 트랜스크립트

워커가 무엇을 하는지는 Claude Code가 쓰는 트랜스크립트로 본다. 워커 보고를 기다리지 않고 지금 tool과 todo, 서브에이전트를 읽어서 생존 판단과 작업 내용 표시에 쓴다. 트랜스크립트는 문서화되지 않은 형식이라 보조 신호로만 쓴다. 못 읽으면 필드를 비우고 컨덕터는 리더가 없을 때처럼 돈다.

- 위치는 `<설정 디렉토리>/projects/<슬러그>/<세션 id>.jsonl`이다. 설정 디렉토리는 `CLAUDE_CONFIG_DIR`을 먼저 보고 `~/.claude`도 본다. 슬러그는 워크트리 절대 경로에서 영문, 숫자, `-`가 아닌 글자를 전부 `-`로 바꾼 값이다.
- 한 워크트리에 세션이 여럿이면 워커 시작 시각 앞뒤 창 안에서 시작한 세션을 고른다. 재개한 회차는 다음 회차가 시작한 시각부터의 세션을 빼서 앞 회차가 뒤 회차 세션을 가져가지 않는다.
- 서브에이전트는 자기 트랜스크립트를 `<세션 id>/subagents/agent-<id>.jsonl`에 쓰고 옆에 `agent-<id>.meta.json`을 둔다. 리더는 이 파일들을 읽지 않고 부모 세션에서 서브에이전트를 띄운 tool 호출과 그 결과만 본다.
- 한 번에 파일 끝에서 2MB까지만 읽고 읽은 위치를 커서에 남겨 다음엔 새 줄만 읽는다. 처음 읽을 때 앞부분을 건너뛰면 `partial`이다.
- 리더가 알아보는 tool 이름(서브에이전트, todo, 파일 쓰기, 셸)은 [`src/conductor/transcript-tools.ts`](../src/conductor/transcript-tools.ts) 한 곳에 표로 있다. Claude Code가 tool 이름을 바꾸면 여기만 고친다.

저장소의 `activity/` 아래 파일은 전부 0700 디렉토리에 0600으로 쓴다.

| 파일                        | 내용                                                                                                                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<워커 id>.json`            | 워크트리 경로, 고친 파일, 다른 주문과 겹친 파일, gate 멈춤을 알린 시각, 요약용 트랜스크립트를 못 찾은 시각과 횟수                                                                        |
| `<워커 id>.transcript.json` | 트랜스크립트 커서(파일, 읽은 위치)와 요약 상태(지금 tool, todo, 서브에이전트, 최근 tool)                                                                                                 |
| `<워커 id>.summary.json`    | 끝난 워커의 타임라인 요약. tool 이름과 시각, 명령이나 설명 앞 60자, 성공 여부, todo, 서브에이전트, 고친 파일만 싣는다. 프롬프트와 답변, 파일 내용, tool 결과는 싣지 않는다. 한 번만 쓴다 |

## tick 한 번

1. **결과 반영**: `inbox/`의 워커 보고를 읽어 상태를 옮긴다. 요약이 `resultMaxChars`를 넘거나 diff, 스택 트레이스가 섞이면 받지 않고 요약을 다시 달라고 돌려보낸다. 적용한 보고 파일은 이름을 기록해 두므로 지우기에 실패해 다음 tick에 다시 보여도 두 번 적용하지 않는다.
2. **접수**: 지라 소스와 외부 큐, PR 감시에서 새 주문을 받는다. 출처 키(`sourceRef`)가 같으면 한 번만 받는다. 결과 반영보다 뒤에 도는 건 PR 감시가 워커가 방금 보고한 PR 주소를 알아야 같은 PR에 주문을 또 만들지 않기 때문이다.
3. **작업 내용**: 도는 워커마다 워크트리에서 고친 파일을 모으고 [트랜스크립트](#워커-트랜스크립트)를 새 줄까지 읽는다. 백그라운드로 gate를 띄우고 턴을 끝낸 채 `gateStallAfterSec`(기본 900초)를 넘긴 워커에는 포그라운드로 다시 돌리라는 말을 워커당 한 번 보낸다. 같은 레포에서 도는 워커 둘씩 고친 파일의 교집합을 보고 겹치면 `warnings`에 한 줄로 남긴다. 겹친 파일이 `overlapGateFiles`(기본 5개)를 넘으면 뒤에 뜬 주문에 파일 겹침 확인 게이트를 연다. 같은 상대와는 한 번만 열고 상대가 여럿이면 열린 게이트의 답을 받은 뒤 다음 상대를 묻는다. 누구와 물었는지는 저장소의 게이트 기록으로 가린다. 끝 상태가 된 워커는 타임라인 요약을 `activity/<워커 id>.summary.json`에 한 번 남긴다. tick 응답에는 숫자와 할 일만 싣고 tool 이름이나 파일 목록은 싣지 않는다.
4. **재개**: `staleAfterSec`(기본 1800초) 동안 보고도 체크포인트도 없는 워커와 `stopped`로 보고한 워커를 마지막 체크포인트부터 다시 띄운다. 사람 결정을 기다리는 `waiting-gate` 주문의 워커와 `--status waiting`으로 대기를 알린 워커는 오래 조용해도 끊긴 것으로 보지 않는다. 대기가 `waitingEscalateAfterSec`(기본 6시간)을 넘거나 워커가 적은 기한(`--wait-until`)이 지나고 `staleAfterSec`만큼 더 소식이 없으면 게이트로 사람에게 올린다. 대기 중인 오르카 워커도 `staleAfterSec`마다 터미널이 살아 있는지 보고 사라졌으면 대기를 지우고 재개한다. 게이트 답을 기다린다고 알린 대기는 게이트를 종료할 때 함께 지운다. 끊김 판단 순서는 트랜스크립트 리더, 터미널 probe, 끊김이다. 리더가 `staleAfterSec` 안에 활동을 봤으면 보고가 없어도 살아 있는 것으로 보고 마지막으로 본 시각을 그 활동 시각으로 당긴다. 리더가 못 봤으면 오르카 워커는 끊김으로 바꾸기 전에 터미널부터 확인하고 세션 한도에 걸린 워커는 재개하지 않는다. 규칙은 [오르카 워커의 세션 한도](#오르카-워커의-세션-한도)에 있다.
5. **결정 전달**: 전달 대기로 남은 게이트 결정을 내보낸다. git-worktree와 서브에이전트 워커에는 `hostActions`의 `send`로 내보내고 오르카 워커에는 직접 다시 전한다. 오르카 워커에 전하다 실패하면 대기를 남겨 다음 tick에 또 하고 세 번 못 전하면 그만둔다. 컨덕터 세션에 그 워커의 런처가 없으면 그 tick에서 그만둔다.
6. **띄우기**: 빈 슬롯만큼 큐의 주문을 띄운다. 띄우기 전에 그 레포의 계정을 맞춘다.
7. **사람이 넘겨받은 PR**: `human-owned` 주문의 PR을 주문마다 `humanOwnedPollSec` 간격으로 gh로 본다. 규칙은 [주문 상태](#주문-상태)에 있다.
8. **머지 뒤 처리**: 지라 상태를 옮기고 배포 결과를 확인한다.
9. **슬랙**: 승인된 초안을 `slack-post`로 넘긴다.
10. **정리**: 끝난 워커와 끝난 주문에 남은 멈춘 워커를 거둔다. git 워커는 워크트리를 지우고 오르카 워커는 터미널만 거둔다. `removeMergedOrcaWorktrees`를 켜면 머지된 주문의 오르카 워크트리까지 지우고 `removeDoneOrcaWorktrees`를 켜면 머지 없이 끝난 `done` 주문의 워크트리도 지운다. 규칙은 [워커 정리](#워커-정리)에 있다.
11. **보관**: 잠금을 놓은 뒤 하루 한 번 끝난 주문을 보관하고 운영 파일을 정리한다. 규칙은 [tick이 하루 한 번 보관](#tick이-하루-한-번-보관)에 있다.

`pollIntervalSec` 안에 다시 부르면 `skipped: true`로 바로 끝나서 상태를 자주 물어도 토큰이 늘지 않는다. 응답에는 숫자와 할 일만 담는다. 감시 주기마다 tick을 돌리고 할 일이 생겼을 때만 깨우는 건 [`wait`](#백그라운드-wait)가 한다.

| 체인이 전부 읽기만 하는 스킬(review, blast-radius, diff-radius, explain) | `subagent`                                                | `subagent`     |
| 그 밖의 체인(solve, ship, review-loop, review-reply, local-pr 등)        | `orca-worktree`                                           | `git-worktree` |
| 체인에 [레포 스킬](#레포-스킬)(`repo:<이름>`)이 하나라도 있음            | `orca-worktree`                                           | `git-worktree` |
| `--worker-kind`로 고정                                                   | 그 값. `orca-worktree`인데 오르카가 없으면 `git-worktree` |                |

기준은 `handoff` 스킬의 "맡길 곳 고르기" 표를 따른다. 레포 스킬 체인은 `--worker-kind subagent`를 접수에서 거절한다. 서브에이전트는 컨덕터 자리에서 돌아 대상 레포 워크트리의 스킬 문서를 못 읽기 때문이다.

### 워커 에이전트 고르기

사용자 전역 `~/.gestalt/conductor.json`에 기본값과 레포별 값을 적는다. 레포마다 쓰는 에이전트가 다를 수 있어 `repoPaths`처럼 레포(`owner/name`)를 키로 하는 맵을 둔다. 레포 안의 `gestalt.json`에서는 이 값을 받지 않는다.

```json
{
  "defaultAgent": "claude",
  "repoAgents": { "acme/app": "codex" }
}
```

주문 하나만 다르게 띄우려면 다음처럼 넣는다.

```bash
gestalt conductor order add --repo acme/app --title "배너 문구 고치기" --agent cursor
```

첫 실행의 우선순위는 주문의 `--agent` > `repoAgents[레포]` > `defaultAgent` > `claude`다. ID는 영문자나 숫자로 시작하고 영문자, 숫자, `.`, `_`, `:`, `-`만 쓴 64자 이하여야 한다. `-`로 시작하는 값은 오르카 CLI가 옵션으로 읽으므로 받지 않는다. 지원 여부는 오르카가 판단한다. `claude`, `codex`, `cursor`, `opencode` 외의 ID도 받는다. 주문의 선택은 주문 이벤트에, 실제 실행값은 워커 이벤트에 남는다. 재개할 때는 앞 워커의 에이전트를 유지하므로 설정을 바꿔도 실행 도중 에이전트가 바뀌지 않는다. 에이전트 기록이 없는 옛 오르카 워커는 기존 동작인 `claude`로 재개한다.

이 선택은 `orca-worktree`에만 적용한다. `subagent`는 호스트 세션 안에서 뜨므로 agent를 무시한다. `git-worktree`의 `open-session`도 agent를 싣지 않고 호스트의 세션 여는 방식을 따른다. 호스트마다 에이전트 CLI 실행법이 달라 컨덕터가 특정 실행법을 가정하지 않기 때문이다.

### 지라 주문의 브랜치와 참조

주문에 지라 키(`issueKey`)가 있으면 워커 브랜치 이름을 컨덕터가 정한다.

| 이슈 타입                                       | 브랜치           |
| ----------------------------------------------- | ---------------- |
| `bug`, `sub-bug`                                | `fix/<지라 키>`  |
| `story`, `task`, `sub-task`, `other`, 타입 없음 | `feat/<지라 키>` |

- 처음 띄울 때 같은 이름이 로컬이나 `origin`에 이미 있으면 이어받지 않고 `-2`, `-3`을 붙여 비어 있는 이름을 쓴다. `-20`까지 다 차 있으면 멈춘다. 사람이 만든 브랜치나 예전 주문이 남긴 브랜치 위에 얹지 않으려는 것이다. 로컬은 하위 워크트리면 부모 워크트리에서, 아니면 `repoPaths`의 경로에서, 그것도 없으면 `orca repo show`가 알려 준 레포 경로에서 본다. 로컬 브랜치를 못 읽거나 `git remote`가 실패하면 멈춘다. `origin`이 없는 레포는 로컬만 본다. `origin`을 못 읽으면 로컬만 보고 띄운 뒤 tick 보고 `warnings`에 남긴다. `origin` 목록은 레포마다 tick에 한 번 읽는다. 경로가 달라도 git 공용 디렉토리가 같으면 같은 레포로 본다. 못 읽은 결과도 그 tick 안에서는 다시 묻지 않는다. ssh 명령을 따로 정해 두지 않았으면 `ls-remote`에 `BatchMode`를 걸어 암호나 호스트 키 확인을 기다리며 멈추지 않게 한다.
- 고른 브랜치는 워커 기록(`worker-started` 이벤트의 `branch`)에 남는다. 재개로 새 워커를 띄울 때 이 값을 앞 브랜치로 넘겨서 앞 워커가 커밋해 둔 작업을 그대로 이어 간다. 기록된 값이 ref 이름 꼴이 아니거나 기준 브랜치, 레포 기본 브랜치면 새 브랜치로 넘어가지 않고 멈춘다. git 워크트리 워커가 앞 워크트리를 다시 쓸 때 그 워크트리가 기준 브랜치나 기본 브랜치를 체크아웃하고 있으면 브랜치를 기록하지 않고 `warnings`에 남긴다. git 워크트리 워커는 기록된 앞 브랜치가 로컬에 없어도 멈춘다. `origin`에만 있으면 로컬로 가져온 뒤 다시 돌린다.
- 브랜치 기록이 없는 옛 워커를 재개할 때는 앞 워커가 실제로 쓰던 브랜치를 먼저 찾는다. 오르카 워커는 앞 워크트리가 체크아웃한 브랜치를 읽어 이 주문 몫이면 이어받는다. 이 주문 몫으로 보는 건 기본 이름과 거기에 `-2`부터 `-20`까지 붙인 이름, 예전 이름 `conductor/<주문 id>`, 마지막 조각이 오르카 워크트리 이름(`<주문 id>-<시도>`)인 브랜치다. 기준 브랜치나 레포 기본 브랜치(`origin/HEAD`, 못 읽으면 `main`과 `master`)에 있으면 조용히 넘어가고 그 밖의 브랜치면 이어받지 않았다고 `warnings`에 남긴다. 워커가 남의 브랜치에 커밋하지 않게 하려는 것이다. git 워크트리 워커는 예전 이름 `conductor/<주문 id>`가 남아 있으면 그걸 이어받는다. 둘 다 못 찾으면 기본 이름(`feat/<지라 키>`, `fix/<지라 키>`) 브랜치가 로컬에 있을 때 그걸 이어받고 tick 보고 `warnings`에 확인해 달라고 남긴다. 사람이 같은 이름으로 만든 브랜치일 수도 있어서다. 기본 이름도 없으면 처음 띄울 때처럼 비어 있는 이름을 고른다.
- 지라 키가 없는 주문은 지금처럼 오르카 기본 이름이나 `conductor/<주문 id>`를 쓴다. 주문에 PR(`--pr`)이 붙어 있으면 그 PR 브랜치에서 일하므로 새 이름을 짓지 않는다. PR 감시가 만드는 `review-reply`, `review-loop` 주문은 지라 키가 없어 띄우는 방식이 그대로다. 앞 워커가 브랜치를 기록해 둔 주문(하위 워크트리로 띄운 주문 등)이 지라 키도 PR도 없이 오르카로 재개되면 앞 브랜치를 이어받지 않고 새 워크트리로 띄운 뒤 `warnings`에 남긴다.

오르카 워크트리에는 지라 키를 참조로 붙이고 주문에 PR이 있으면 GitHub PR 주소도 같이 붙인다. 워크트리를 만든 뒤 `orca reference add`로 하나씩 붙인다. `worktree create --reference`로 한 번에 붙이면 지라 사이트 연결이 없을 때 워크트리 만들기까지 실패해서다. 참조를 못 붙여도 워커는 띄우고 tick 보고 `warnings`에 한 줄만 남긴다. git 워크트리 워커는 참조를 붙일 자리가 없어 브랜치 이름만 따른다.

지라 주문의 오르카 워커는 두 단계로 띄운다. `orca worktree create --branch <이름>`으로 워크트리를 먼저 만들고 `worker-start --worktree <그 워크트리>`로 워커를 붙인다. `worker-start`에는 `--branch`가 없어서다. 부모가 없으면 `--no-parent`를 붙인다. 안 붙이면 오르카가 컨덕터 워크트리를 부모로 잡는다. 워크트리를 만든 뒤 돌리는 셋업 스크립트 정책은 한 번에 띄우던 길과 같다. 재개는 앞 워커가 커밋한 브랜치에서 만들어서 말로 받은 주문이 아니면 기준 브랜치가 없어도 셋업을 건너뛴다. 워커 붙이기가 실패했을 때 워크트리를 남기거나 지우는 기준도 [부모 워크트리](#부모-워크트리와-기준-브랜치)와 같다.

재개 때 오르카는 이미 있는 브랜치를 `--branch`로 붙이지 못한다(이름이 겹치면 숫자를 붙여 새로 만든다). 그래서 앞 브랜치에서 갈라 새 워크트리를 만든 뒤 그 브랜치로 바꾼다.

1. `orca worktree create --base-branch <앞 브랜치>`로 같은 커밋에서 새 워크트리를 만든다.
2. 앞 워크트리는 재개해도 지우지 않아 그 브랜치를 체크아웃한 채로 남아 있다. `git switch --detach`로 앞 워크트리를 그 자리 커밋에서 detach해 브랜치 체크아웃을 해제한다. 커밋 안 한 변경은 앞 워크트리에 그대로 남는다. 브랜치를 체크아웃한 곳이 앞 워커의 워크트리(`orca worktree show`로 찾은 경로)가 아니면 detach하지 않고 멈춘다. 사람이 쓰는 메인 체크아웃을 건드리지 않으려는 것이다. 앞 워커의 워크트리 디렉토리만 지워지고 git 등록이 남아 있으면 `git worktree remove --force`로 그 등록만 지운다. 레포 전체를 `prune`하면 다른 워크트리 등록까지 지워서다(git 워크트리 워커는 지금도 다시 붙이기 전에 레포 전체를 `prune`한다). git이 prunable로 알려도 그사이 디렉토리가 다시 보이면 지우지 않고 멈춘다. `--force`가 안의 변경까지 지워서다.
3. 새 워크트리를 `git switch <앞 브랜치>`로 바꾼다.
4. 오르카가 만든 임시 브랜치를 `git branch -d`로 지운다. 임시 브랜치 이름을 못 읽었으면 지우지 않고 `warnings`에 확인할 경로를 남긴다.

2나 3이 실패하면 워커를 안 띄우고 남은 워크트리와 `orca worktree rm` 명령을 실패 사유에 붙여 확인 자리로 올린다. 2에서 detach한 뒤 3이 실패하면 앞 워크트리를 다시 그 브랜치로 돌려 둔다. 돌리지 못하면 되돌릴 명령을 실패 사유에 붙인다. 4가 실패하면 워커는 띄우고 tick 보고 `warnings`에 남긴다.

재개한 워커를 붙이다 실패해 워크트리를 지울 때는 `--delete-branch`를 빼고 워크트리만 지운다. 새 워크트리가 앞 브랜치를 체크아웃하고 있어 브랜치째 지우면 앞 워커가 쌓은 커밋을 잃을 수 있다. 실패 사유에 붙이는 `orca worktree rm` 명령도 같다. 지운 뒤에는 2에서 detach한 앞 워크트리를 다시 그 브랜치로 돌려 둔다. 2나 3에서 멈출 때 붙이는 명령은 새 워크트리가 아직 임시 브랜치를 쓰고 있어서 `--delete-branch`를 붙인다. 임시 브랜치 이름을 모르면 붙이지 않는다.

git 워크트리 워커는 앞 워크트리 경로를 다시 쓰고 그 워크트리가 실제로 체크아웃한 브랜치를 기록한다. detach 상태면 브랜치를 기록하지 않고 경고를 남긴다. 디렉토리가 사라졌으면 남은 앞 브랜치를 `-b` 없이 다시 붙인다.

### 부모 워크트리와 기준 브랜치

기존 워크트리 아래 하위로 워커를 띄우려면 주문에 `--parent-worktree`를 준다. 어느 ref에서 갈라질지는 `--base-branch`로 정한다.

```bash
gestalt conductor order add --repo acme/app --title "쿠폰 목록 하위 작업" \
  --parent-worktree ~/orca/workspaces/app/feat-coupon --base-branch feat-coupon
```

`--parent-worktree`는 경로나 오르카 선택자(`branch:feat-coupon`, `id:...` 같은 것)를 받는다. 선택자면 `orca worktree show`로 경로를 받아 온다. `path:`로 시작하면 접두어를 떼고 로컬 경로로 본다. 접수할 때 워크트리 루트의 절대 경로로 풀고 주문 레포의 워크트리인지 확인한다. `repoPaths`에 그 레포가 있으면 git 공용 디렉토리가 같은지 보고 없으면 `origin` 주소가 `owner/name`과 맞는지 본다. 경로가 없거나 git 워크트리가 아니거나 레포가 다르면 주문을 받지 않는다. `origin`으로 맞출 때는 호스트를 안 본다. SSH 별칭(`git@github-work:acme/app.git`)도 받으려는 것이고 호스트가 다른 동명 레포를 가려야 하면 `repoPaths`에 그 레포 경로를 적는다.

`--base-branch`는 브랜치 이름이나 `origin/main` 같은 ref를 받는다. `-`로 시작하거나 `..`, `@{`, 공백이 있거나 `/`로 나눈 조각이 비었거나 `.`으로 시작하거나 `.lock`으로 끝나면 거절한다. 부모 없이 단독으로 줘도 된다.

외부 큐는 `baseBranch`만 받고 `parentWorktree`는 확인 자리로 올린다. 부모 경로는 이 머신에서 확인한 값이어야 해서 `order add`로 넣은 주문만 받는다. 말로 받은 주문이 아닌데 기준 브랜치가 있으면 새 워크트리의 셋업을 건너뛴다(`--setup skip`). 바깥에서 고른 브랜치의 셋업 스크립트를 이 호스트에서 돌리지 않으려는 것이다.

| 워커            | `--parent-worktree`                                                                                                             | `--base-branch`                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `orca-worktree` | `orca worktree create --parent-worktree`로 그 아래 하위 워크트리를 먼저 만들고 `worker-start --worktree`로 그 워크트리에 띄운다 | 하위 워크트리나 `new-top-level` 워크트리를 그 ref에서 갈라낸다                                |
| `git-worktree`  | 무시하고 tick 보고의 `warnings`에 남긴다                                                                                        | 워커 브랜치를 새로 만들 때 그 ref에서 갈라낸다. 재개 때 남은 브랜치를 다시 붙이면 쓰지 않는다 |
| `subagent`      | 무시하고 `warnings`에 남긴다                                                                                                    | 무시하고 `warnings`에 남긴다                                                                  |

`worker-start --worktree new-child`는 호출한 쪽(컨덕터) 워크스페이스 아래에 붙어서 임의 부모를 고를 수 없다. 그래서 워크트리를 먼저 만드는 두 단계로 띄운다. 워크트리를 만든 뒤 워커가 못 뜨면 오르카가 아무것도 바꾸기 전에 거절했거나(`selector_not_found`) `failed`와 함께 남은 자원이 비었다고 답했을 때만 만든 워크트리를 지운다. 시간 초과나 `outcome_unknown`, 남은 자원을 안 밝힌 실패처럼 워커가 떴는지 모르면 지우지 않는다. 그때나 지우기가 실패했을 때, `worktree create` 자체가 실패했을 때는 남은 워크트리와 `orca worktree rm` 명령을 실패 사유에 붙여 확인 자리로 올린다. 실패한 띄우기는 회차를 안 올리므로 남은 워크트리를 지우기 전에는 같은 이름으로 다시 만들다 실패한다. 부모만 주고 기준 브랜치를 비우면 어디서 갈라질지는 오르카 기본값을 따른다. 부모 브랜치에서 이어 가려면 `--base-branch`에 그 브랜치를 같이 준다.

재개와 정리는 부모가 없는 오르카 워커와 같다. 재개하면 같은 부모 아래 `<주문 id>-<회차>` 이름으로 하위 워크트리를 새로 만든다. 정리도 [워커 정리](#워커-정리)를 그대로 따른다. 기본은 `worker-release`로 워커 터미널만 거두고 워크트리는 남긴다. 워크트리를 지울 때도 부모 워크트리는 건드리지 않는다.

## 워커 정리

tick 마지막 단계는 `finished`나 `failed` 워커를 거두고 `released`로 바꾼다. 멈춘(`stopped`) 워커는 재개가 그 dispatch id나 워크트리를 다시 쓸 수 있어 남긴다.

주문이 끝 상태(`done`, `failed`, `cancelled`)면 멈춘 워커도 같은 tick에 거둔다. 재개될 일이 없고 남겨 두면 `order remove`가 계속 거절해서다. 거두는 방식은 아래 표대로 `finished` 워커와 같다. 오르카 워커는 터미널만 거두고 워크트리는 남긴다. `removeMergedOrcaWorktrees`를 켠 머지된 주문이면 주문 상태와 상관없이 워크트리까지 지운다. `removeDoneOrcaWorktrees`를 켠 머지 없는 `done` 주문도 워크트리까지 지운다. 그 밖의 `parked` 주문은 사람이 PR과 워크트리를 쥐고 있을 수 있어 멈춘 워커를 거두지 않는다. 취소하면 그때 거둔다. `finished`나 `failed` 워커는 `parked` 주문이어도 그대로 거둔다.

| 워커            | 거두는 범위                                                                               |
| --------------- | ----------------------------------------------------------------------------------------- |
| `git-worktree`  | `git worktree remove`로 워크트리를 지운다. 브랜치는 남는다. 같은 레포끼리는 차례로 지운다 |
| `orca-worktree` | `orca orchestration worker-release`로 워커 터미널만 거둔다. 워크트리는 남는다             |
| `subagent`      | 할 일 없음                                                                                |

오르카는 settled 워커만 `worker-release`를 받는다. 워커가 컨덕터에만 보고하고 오르카에 `worker_done` 없이 나가면 dispatch가 `ready`로 남아 `dispatch_inactive`로 거절된다. 그때 `worker-show`의 `liveness`가 `exited`나 `gone`이면 `worker-stop`으로 dispatch를 끝난 상태(state `stopped`)로 바꾸고 `worker-release`를 다시 부른다. 워커가 살아 있으면 다음 tick에 release를 다시 시도한다. `retained` 응답 뒤에도 워커가 살아 있으면 같은 규칙을 쓴다. 첫 거절부터 `orcaReleaseRetryMaxSec`(기본 2시간) 동안 거절이 이어지면 정리 실패 게이트를 연다. 생존 여부를 확인할 수 없으면 바로 게이트를 연다.

오르카 워크트리가 계속 쌓이는 게 싫으면 `~/.gestalt/conductor.json`에 `"removeMergedOrcaWorktrees": true`를 적는다. 레포 `gestalt.json`의 값은 받지 않는다. 켜면 머지된 주문(`mergedAt`이 있는 주문)의 오르카 워커는 다음처럼 정리한다.

1. `orca orchestration worker-show`로 워커의 워크스페이스(`<레포 id>::<경로>`)를 읽는다.
2. `worker-release`로 터미널을 거둔다.
3. `orca worktree show`로 오르카가 아는 워크트리 정보를 한 번 더 확인한다.
4. `orca worktree rm --worktree id:<레포 id>::<경로> --delete-branch`로 워크트리를 지운다. `--force`는 안 붙인다.

- 재개로 회차가 여러 개 생긴 주문이면 `stopped`로 남은 앞 회차 워커도 같이 거둬서 `<주문 id>-<회차>` 워크트리를 빠짐없이 지운다.
- 머지 안 된 주문의 워크트리는 켜도 남긴다. 그중 `done` 주문은 아래 `removeDoneOrcaWorktrees`로 따로 켠다.
- 아래 중 하나라도 걸리면 지우지 않고 정리 실패로 올린다.
  - 지울 경로의 마지막 조각이 `<주문 id>-<회차>`와 다르다
  - 주문의 부모 워크트리이거나 그 위 경로다
  - `worktree show`가 메인 워크트리라고 하거나 메인 여부를 안 알려 준다
  - `worktree show`의 레포 id가 워크스페이스의 레포 id와 다르다
  - 주문에 부모 워크트리가 있는데 `worktree show`의 `parentWorktreeId`가 그 부모를 가리키지 않는다
- 같은 레포의 워크트리 삭제는 git 잠금이 겹치지 않게 차례로 돌리고 다른 레포끼리는 함께 돌린다.
- `--delete-branch`는 오르카가 머지됐다고 확인한 브랜치만 지운다. 스쿼시 머지처럼 확인 못 하는 브랜치는 오르카가 남긴다.
- 이미 없는 워크트리(`selector_not_found`)는 지운 것으로 본다.

머지 없이 `done`으로 끝난 주문(리뷰 답글, 읽기만 하는 주문 등)의 워크트리도 지우려면 `~/.gestalt/conductor.json`에 `"removeDoneOrcaWorktrees": true`를 적는다. 이것도 레포 `gestalt.json`의 값은 받지 않는다. 순서와 지우지 않는 조건은 위 머지 경로와 같고 `worktree rm`에 `--delete-branch`를 붙이지 않는 것만 다르다. 머지를 확인하지 못한 주문이라 브랜치에만 남은 커밋이 있을 수 있어서다. `failed`, `cancelled`, `parked` 주문은 켜도 워크트리를 남긴다. 두 옵션은 따로 움직여서 이 옵션만 켜면 머지된 주문의 워크트리는 남는다.

이미 `released`로 바뀐 워커는 다시 보지 않는다. 옵션을 켜기 전에 끝난 주문의 워크트리는 사람이 `orca worktree rm`으로 지운다.

커밋 안 한 변경이 있어 오르카가 거절하거나 다른 이유로 정리가 실패하면 강제로 지우지 않는다. 주문 없는 `cleanup-failed` 게이트를 열고 그 게이트가 열린 동안은 다시 시도하지 않는다. 사람이 직접 정리하고 승인하면 `released`로 두고 거절하면 다음 tick에 다시 시도한다.

## 동시 상한과 큐

`maxConcurrentWorkers`(기본 10)를 넘는 주문은 `queued`로 남았다가 슬롯이 나면 뜬다. 슬롯은 `starting`과 `running` 워커만 차지한다. 상한은 tick마다 설정을 다시 읽어서 도는 중에 바꿔도 다음 tick부터 적용된다.

## 주문 범위와 사람 확인

| 범위              | 머지 승인       | 인터뷰 답              |
| ----------------- | --------------- | ---------------------- |
| `merge-through`   | 컨덕터가 넘긴다 | 워커가 맥락에서 정한다 |
| `approval` (기본) | 사람에게 묻는다 | 워커가 맥락에서 정한다 |
| `interview-first` | 사람에게 묻는다 | 사람에게 묻는다        |

워커가 혼자 못 넘는 자리를 만나면 `needs`로 보고한다. 컨덕터는 아래처럼 나눈다.

| 요청                             | 처리                                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| `merge-approval`                 | 위 표대로                                                                                    |
| `interview-answer`               | 위 표대로                                                                                    |
| `slack-post`                     | 늘 사람에게                                                                                  |
| `review-manual-switch`           | 늘 사람에게. 리뷰 스킬의 라운드 상한과 수동 전환 지침을 그대로 따른다                        |
| `simple-approval`                | ship 체인 주문이 `--need-step`을 실었으면 승인하고 기록한다. 없으면 사람에게(`no-procedure`) |
| `manual-verification`, `cleanup` | 워커가 직접 하고 다음 보고에 남기라고 돌려준다                                               |
| `auth`, `account-switch`         | `~/.gestalt/conductor.json`의 `accounts`에 적힌 레포만 그 계정으로 맞춘다. 없으면 사람에게   |
| `other`                          | 사람에게 (`no-procedure`)                                                                    |

사람에게 가는 자리는 확인 자리(gate)로 열리고 그 주문은 `waiting-gate`가 된다. `gestalt conductor gate resolve`로 종료하면 결정이 그 워커에 바로 전달된다. bypass로 넘긴 일은 저장소에 기록만 남고 컨덕터가 모아서 사후 보고한다. `gestalt conductor status`가 주문마다 bypass 내역을 붙여 보여 주고 주문에 묶이지 않은 것은 `unassignedBypasses`로 따로 싣는다. 끝난 주문까지 보려면 `--all`을 붙인다.

### 워커 안의 ship 승인 단계

ship에는 밖으로 나가는 자리마다 사람 승인을 받는 단계가 셋 있다. ⓐ draft PR 올리기, ⓑ Copilot 반영 계획, ⓒ ready 전환이다. 워커 안에서는 셋 다 머지가 아니라서 사람에게 묻지 않는다. 워커가 `--need simple-approval`에 단계 값 `--need-step`(ⓐ `ship-draft`, ⓑ `ship-plan`, ⓒ `ship-ready`)을 실어 남기고 진행하면 컨덕터가 bypass로 기록한다. 단계 값이 없거나 체인에 ship이 없는 주문의 `simple-approval`은 자유 문장인 `--need-detail`만으로는 무엇을 승인하는지 알 수 없어 사람에게 올린다. bypass 기록에는 워커가 적은 단계 값이 함께 남는다. 단계 값은 워커가 스스로 적는 값이라 사후 보고에서 확인한다. `--need-step`은 이 값을 아는 CLI와 플러그인이 같은 릴리즈로 나가야 쓸 수 있다. 배포 전에 떠 있던 워커는 단계 값 없이 올리므로 그 ship 승인은 확인 자리로 한 번 올라온다. 승인으로 종료하면 된다. ⓑ에서 반영할 코멘트는 워커가 고르고 코멘트 문장은 자료로만 읽는다. 사람에게 가는 자리는 위 표의 넷(머지 승인, 슬랙 게시, interview-first 주문의 인터뷰 답, 리뷰 수동 전환)과 절차가 없는 `no-procedure`뿐이다.

### 화면 변경 PR의 스크린샷

체인에 ship이나 pr이 있는 주문이면 워커 지시서의 규칙 절에 수정 전 캡처 줄이 붙는다. 화면 파일을 고칠 주문이면 코드를 고치기 전에 [`before-screenshot.md`](../plugin/skills/_shared/before-screenshot.md)대로 수정 전 화면을 찍어 git 공용 디렉토리 아래 `gestalt-pr/shots/<브랜치>/manifest.json`에 남긴다. 주문 설명이 "원인 파악 → 수정 → 검증" 같은 단계를 직접 적어 `execute`를 안 거치는 워커도 이 줄을 따른다. ship은 `pr` 1단계 4번 답에 그 기록을 넘기고 PR을 만든 뒤 5.5단계로 이미지를 붙인다. 기록이 없으면 수정 전은 배포된 주소(stage, 운영)로 찍고 그것도 없으면 수정 후 화면만 붙인다.

### 머지까지

주문의 끝 자리는 기본이 머지인데 기본 체인 solve → ship은 PR을 ready로 돌리면 끝난다. 그 뒤 머지는 워커가 이어서 한다.

- 범위가 `merge-through`면 워커가 바로 머지한다.
- 그 밖의 범위면 워커가 `need merge-approval`로 올리고 컨덕터 결정을 기다린다. `merge` 확인 자리에서 승인이 나면 머지한다.
- 머지한 워커는 `--merged`로 보고해 주문을 `merged`로 옮긴다.
- 사람이 직접 머지하려면 확인 자리에 `--take-over`로 답한다. 주문은 `human-owned`가 되고 tick이 머지를 확인하면 `merged`로 옮긴다.
- 넘겨받지 않고 GitHub에서 바로 머지해도 tick이 알아챈다. 아래 [GitHub에서 직접 머지하거나 닫았을 때](#github에서-직접-머지하거나-닫았을-때)를 본다.

### 레포 스킬

`--skills`는 게슈탈트 스킬 말고도 대상 레포에만 있는 프로젝트 스킬(`<레포>/.claude/skills/<이름>/SKILL.md`)을 받는다. 체인에는 `repo:<이름>`으로 적는다.

```bash
gestalt conductor order add --repo acme/app --title "v1.2.0 릴리즈" --skills repo:release --json
```

- **`repo:` 접두를 붙이는 까닭**: 게슈탈트 스킬과 이름이 겹치면 어느 쪽을 돌릴지 정할 수 없다. 레포 스킬 이름이 `ship`이면 ship 승인 단계(`--need-step`) 판정과 수정 전 캡처 줄도 그 스킬에 붙는다. 접두가 붙은 이름은 `KNOWN_SKILLS`에 없어서 바깥 출처를 거르는 기존 검사에 그대로 걸린다.
- **이름 꼴**: 접두 뒤는 영문 소문자나 숫자로 시작하고 영문 소문자와 숫자, `-`만 쓴 64자 이하다. 경로 한 칸으로 붙으므로 `/`, `\`, `..`가 들어갈 수 없다.
- **존재 확인**: 주문을 넣을 때 워커 워크트리가 갈라질 로컬 체크아웃에 스킬 문서가 있는지 본다. `--worker-kind git-worktree`면 부모를 무시하고 띄우므로 `~/.gestalt/conductor.json`의 `repoPaths[레포]`만 본다. `orca-worktree`이거나 종류를 안 정했으면 오르카가 없을 때 git 워크트리로 떨어지므로 부모 경로와 `repoPaths[레포]` 가운데 아는 경로를 다 본다. 경로를 하나도 모르거나 파일이 없으면 이유와 함께 거절하고 주문을 만들지 않는다. 스킬 문서나 그 디렉토리가 레포 밖을 가리키는 링크여도 거절한다. 같은 `--source-ref`로 다시 넣은 주문은 확인 전에 기존 주문을 돌려준다. 오르카에 등록된 레포 경로는 보지 않는다. 접수는 오르카를 부르지 않기 때문이다. 접수가 보는 건 그 체크아웃의 작업 트리 파일이고 워커 워크트리는 `--base-branch` 커밋에서 갈라진다. 이 값이 없으면 git 워크트리 워커는 그 체크아웃의 HEAD에서, 오르카 워커는 오르카가 정한 기준에서 갈라진다. 스킬 문서가 커밋되지 않았거나 기준 브랜치에 없으면 접수는 통과해도 워커에는 그 문서가 없다. 그러면 워커가 `needs other`로 올린다.
- **받는 출처**: 컨덕터 세션이 `order add`로 넣은 주문과 말로 받은 주문만 받는다. 지라, 외부 큐, PR 감시에서 온 `repo:` 스킬은 체인에서 빠진다. 바깥 글이 레포 안 아무 스킬이나 돌리게 두지 않는다. 봇 채팅의 `order add`는 기본 체인만 받으므로 레포 스킬을 못 넣는다.
- **ship과 함께 넣지 않는다**: 체인에 ship이 있으면 단계 값(`--need-step`)이 붙은 `simple-approval`을 사람 없이 넘긴다. 레포 스킬과 한 체인에 두면 레포 스킬의 푸시 승인도 그렇게 넘어갈 수 있어서 접수에서 거절한다. PR까지 가야 하면 주문을 나눠 넣는다.

워커 지시서에는 레포 스킬마다 "워크트리의 `.claude/skills/<이름>/SKILL.md`를 읽고 그 절차를 따른다"는 줄이 붙는다. 워크트리에 그 파일이 없으면 `need other`로 올린다. 체크포인트의 `--skill`에는 `repo:<이름>`을 그대로 적는다. 재개는 `--done`에 적힌 스킬만 끝낸 것으로 세므로 밖으로 나가는 행동이 성공하면 바로 `--done repo:<이름>`을 붙여 체크포인트를 한 번 더 남긴다. 빠뜨리면 태그를 푸시한 뒤 끊겼을 때 재개한 워커가 그 절차를 처음부터 다시 돈다.

레포 스킬은 PR을 만드는지 읽기만 하는지 알 수 없다. 그래서 지시서에 아래 두 줄이 더 붙는다.

- 레포 밖 상태를 바꾸는 행동 직전에는 `--need simple-approval`을 단계 값 없이 올리고 결정을 기다린다. 기본 브랜치나 태그 푸시, force push, 원격 삭제, GitHub 릴리스 생성, 패키지나 앱 배포, 마이그레이션, 외부 API 호출, 메시지나 PR 코멘트 게시가 모두 여기 든다. 컨덕터 보고와 체크포인트 저장은 빼고 셈한다. 스킬 문서가 확인 없이 진행하라고 적었어도 이 줄이 먼저다. 컨덕터는 `simple-approval`을 체인에 ship이 있고 단계 값이 붙었을 때만 넘긴다. 레포 스킬 체인에는 ship을 못 넣으므로 이 요청은 범위가 `merge-through`여도 확인 자리(`no-procedure`)로 사람에게 간다.
- 체인이 PR 없이 끝나면 머지 승인을 올리지 않고 `--status done`으로 낸다. 주문은 `merged`가 아니라 `done`으로 끝나고 지라는 머지 단계로 옮기지 않는다. 체인이 PR을 남기면 위 [머지까지](#머지까지)를 그대로 탄다.

## 주문 상태

| 상태           | 뜻                                                | 끝 상태 | 슬롯 차지 |
| -------------- | ------------------------------------------------- | ------- | --------- |
| `queued`       | 띄울 차례를 기다린다                              | 아니다  | 아니다    |
| `running`      | 워커가 돌고 있다                                  | 아니다  | 차지한다  |
| `waiting-gate` | 사람 확인을 기다린다. 워커는 살아 있다            | 아니다  | 차지한다  |
| `escalated`    | 사람 결정을 기다리며 슬롯만 비웠다                | 아니다  | 아니다    |
| `human-owned`  | 사람이 넘겨받았다. 워커는 거뒀고 tick이 PR만 본다 | 아니다  | 아니다    |
| `merged`       | 머지됐다. 지라 전환과 배포 확인이 남았다          | 아니다  | 아니다    |
| `parked`       | 넘겨받은 뒤 오래 안 움직여 tick이 더 안 본다      | 그렇다  | 아니다    |
| `done`         | 끝났다                                            | 그렇다  | 아니다    |
| `failed`       | 실패로 끝났다                                     | 그렇다  | 아니다    |
| `cancelled`    | 취소됐다                                          | 그렇다  | 아니다    |

사람이 넘겨받은 뒤의 전이는 아래와 같다.

```
queued, running, waiting-gate, escalated
  ── gate resolve --take-over / order take-over ──▶ human-owned
human-owned ── PR MERGED ──▶ merged ──▶ done
human-owned ── PR CLOSED(머지 없음) ──▶ cancelled
human-owned ── humanOwnedParkAfterSec 경과 ──▶ parked
human-owned, parked ── order mark-merged(gh MERGED 확인) ──▶ merged
끝나지 않은 주문, human-owned, parked ── order cancel ──▶ cancelled
```

- tick은 `human-owned` 주문의 PR을 주문마다 `humanOwnedPollSec`(기본 900초) 간격으로 `gh pr view`로 본다. 계정은 PR 감시와 같은 `accounts` 설정으로 고른다. OPEN이면 아무것도 바꾸지 않고 tick 출력에도 안 싣는다. 상태가 바뀐 주문만 한 줄씩 싣는다.
- 넘겨받은 지 `humanOwnedParkAfterSec`(기본 86400초)가 지나도 머지나 닫힘이 없으면 `parked`로 내린다. `parked`는 끝 상태라 gh 확인을 멈춘다. 나중에 머지했으면 `order mark-merged`로 알린다.
- `human-owned` 주문의 워커는 거둔 워커라 끊김 판정과 재개에서 빠진다. 거둔 뒤 늦게 도착한 워커 보고는 무시한다.
- PR이 없는 주문을 넘겨받으면 머지를 지켜볼 수 없다고 경고하고 기한이 지나면 `parked`로 내린다.
- `status` 기본 목록은 `done`만 숨기므로 `parked` 주문이 계속 보인다.

### GitHub에서 직접 머지하거나 닫았을 때

넘겨받기 없이 사람이 GitHub에서 PR을 바로 머지하거나 닫을 수도 있다. tick은 PR이 있는 `running`, `waiting-gate`, `escalated` 주문도 `human-owned`와 같은 간격(`humanOwnedPollSec`)과 같은 계정 설정으로 본다.

```
running, waiting-gate, escalated ── PR MERGED ──▶ merged ──▶ done
running, waiting-gate, escalated ── PR CLOSED(머지 없음) ──▶ cancelled
```

- MERGED면 열린 확인 자리를 종료하고 워커에 종료를 전한 뒤 `merged`로 넘긴다. 지라 전환과 배포 확인은 워커가 머지했을 때와 같다. 워커는 같은 tick의 [워커 정리](#워커-정리)가 거두므로 `removeMergedOrcaWorktrees`도 그대로 적용된다.
- 머지 없이 CLOSED면 확인 자리를 종료하고 워커를 바로 거둔 뒤 `cancelled`로 넘긴다. 지라는 옮기지 않는다.
- OPEN이면 확인 시각만 남긴다. 컨덕터가 쥔 주문은 하루가 지나도 `parked`로 내리지 않는다. 워커나 확인 자리가 아직 움직이고 있어서다.
- 배포 실패로 올라온 `escalated` 주문은 이미 `mergedAt`이 있어 보지 않는다. 다시 `merged`로 넘기면 정산이 같은 실패를 되풀이한다.
- 바뀐 주문은 tick 출력의 `humanOwned`에 실리고 `from`에 앞 상태가 붙는다.
- 거둔 뒤 늦게 도착한 워커 보고는 주문이 `merged`나 `done`이어도 무시한다. 그래야 `mergedAt`이 덮이거나 지라가 두 번 옮겨지지 않는다.

## 체크포인트와 재개

워커는 스킬이나 단계가 바뀔 때마다 체크포인트를 남긴다. CI 대기처럼 15분 넘게 걸릴 수 있는 대기도 들어가기 전과 끝난 뒤에 남긴다. 그래야 `staleAfterSec`(기본 30분) 안에 소식이 끊기지 않는다. 사람의 답이나 CI, 리뷰처럼 바깥을 기다리기 전에는 `--status waiting --wait-for "<무엇>" [--wait-until <ISO 시각>]`으로 알린다. 그러면 tick이 대기 중에 끊김으로 보지 않는다. 대기는 다음 보고나 체크포인트가 오면 풀리므로 체크포인트를 먼저 남기고 waiting 보고를 맨 마지막에 한다. 오르카 워커는 이 시간이 지나도 터미널을 먼저 확인하므로 출력 중이면 끊김으로 안 바뀐다.

```bash
gestalt conductor checkpoint save --worker <id> --skill solve --next "스펙 확정" --done solve
gestalt conductor checkpoint save --worker <id> --skill ship --next "라운드 2 반영" --ship-dir .ship
gestalt conductor checkpoint save --worker <id> --skill repo:release --next "릴리스 노트 확인" --done repo:release
```

ship 단계는 기존 `gestalt ship checkpoint save`와 `check`를 그대로 쓴다. 컨덕터 체크포인트는 그 자리(`--ship-dir`)만 가리킨다. 재개할 때 ship 체크포인트를 다시 읽어 단계와 라운드를 새 워커 지시에 싣는다. 끝낸 스킬은 다시 돌리지 않고 남은 체인만 이어 간다. git 워크트리 워커는 앞 워커의 워크트리 경로를 다시 써서 워크트리를 새로 만들지 않는다. 오르카 워커는 재개할 때도 새 워크트리로 띄운다. 지라 주문이면 새 워크트리가 앞 워커의 브랜치를 이어받는다([지라 주문의 브랜치와 참조](#지라-주문의-브랜치와-참조)).

아래면 재개하지 않고 원인과 마지막 체크포인트를 붙여 사람에게 올린다.

- 같은 주문을 `maxResumeAttempts`번 재개했는데도 또 멈췄다
- 체크포인트상 체인을 다 끝냈는데 멈췄다
- ship 체크포인트를 읽지 못했다
- 오르카 워커인데 앞 워커 터미널 정리가 기한을 넘기거나 실패했다

### 오르카 워커의 세션 한도

세션 한도에 걸린 오르카 워커는 보고 없이 멈춘다. 이걸 끊김으로 보고 새 워커를 띄우면 한도가 풀린 앞 워커가 다시 움직여서 한 주문을 둘이 진행한다. 그래서 오르카 워커(부모 워크트리 아래 하위 워커 포함)는 `staleAfterSec`이 지나도 바로 끊김으로 바꾸지 않고 `orca orchestration worker-show`와 `worker-read`로 터미널을 먼저 본다.

| 터미널 상태                                  | 처리                                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 에이전트가 아직 출력 중(`activity: working`) | 끊긴 게 아니라 그대로 둔다                                                                                |
| 끝 메시지에 세션 한도나 사용량 한도 표시     | `stopReason: rate-limit`으로 멈춤만 표시하고 재개하지 않는다                                              |
| 터미널이 없거나 프로세스가 끝남              | `disconnected`로 보고 재개한다                                                                            |
| 살아 있지만 조용함                           | `disconnected`로 보고 재개를 시도한다. 앞 터미널이 살아 있으면 새 워커는 대기하고 release를 다시 시도한다 |
| 확인 실패(오르카 응답 없음 등)               | 위와 같이 재개를 시도하고 tick 보고 `warnings`에 남긴다                                                   |

한도는 오르카가 남기는 `failure.kind: "usageLimitReached"` 표식을 먼저 보고 표식이 없으면 출력 문구로 가른다. 문구로 가른 한도는 워커가 다루는 글에 섞인 문구에 잘못 걸렸을 수 있어서 `conductor status`에 `출력 문구로 판단`을 붙여 보인다.

한도로 멈춘 워커가 다시 보고하거나 체크포인트를 남기면 `running`으로 돌아온다. tick마다 `worker-show`로 터미널 상태도 다시 보는데, 다시 출력 중이면 한도가 풀린 것이라 `running`으로 돌리고 터미널이 사라졌으면 `disconnected`로 바꿔 재개한다. 한도 대기 중인 주문은 `gestalt conductor status`와 tick 보고의 `rateLimited`에 처음 본 시각, 오르카가 알려 준 풀리는 시각과 함께 보인다.

멈춘 지 `rateLimitEscalateAfterSec`(기본 6시간)이 지나도 안 풀리면 게이트로 사람에게 올린다. 한도에 걸린 워커는 오르카 기준으로 아직 안 끝난 상태다. 그대로 승인하면 살아 있는 앞 워커의 release를 재시도하다 기한에 재개 게이트를 열 수 있다. 바로 재개하려면 게이트 사유에 적힌 대로 `orca orchestration worker-stop --dispatch=<id>`로 앞 워커를 먼저 멈추고 승인한다. 게이트가 열린 동안에는 터미널을 다시 보지 않는다. 그사이 앞 워커가 보고하면 워커는 `running`으로 돌아오지만 게이트는 사람이 정할 때까지 열려 있다. 승인한 뒤 앞 터미널을 거두면 체크포인트부터 다시 띄운다. 거절하면 주문을 취소하고 앞 터미널은 그대로 남는다. 한도가 풀려 그 워커가 나중에 보고해도 취소된 주문이라 결과를 무시한다. 취소된 주문의 보고를 무시하는 건 워커 종류와 상관없이 똑같다.

오르카 워커를 재개할 때는 새 워커를 띄우기 전에 앞 워커 터미널을 `worker-release`로 거둔다. 워크트리는 지우지 않는다. 앞 워커가 살아 있어 release를 못 하면 새 워커는 대기하고 다음 tick에 release를 다시 시도한다. `orcaReleaseRetryMaxSec`까지 계속 거절되거나 생존 여부를 확인할 수 없으면 재개 게이트를 열어 사람이 `orca orchestration worker-stop --dispatch=<id>`로 멈춘 뒤 승인하게 한다. git 워크트리와 서브에이전트 워커는 들여다볼 터미널이 없어 지금처럼 바로 끊김으로 보고 재개한다.

| 머지 (sub-task)                                           | Done        |
| 배포 성공 (bug, task, sub-bug)                            | In-QA       |

주문에 `jiraStatus`가 있으면 사용자가 정한 값이라 기본 규칙보다 먼저다. 배포는 머지 뒤 파이프라인 성공으로 판단한다. 호스트가 결과를 확인해 `gestalt conductor deploy report`로 남기고 tick이 읽는다. 배포가 실패하면 그 주문만 사람에게 올린다. 배포가 `deployWaitMaxSec`(기본 24시간)까지 대기 중이면 지라 이동 없이 주문을 `done`으로 바꾸고 tick에 경고를 남긴다. 기한은 `mergedAt`부터 센다. 예전 주문에 이 값이 없으면 `updatedAt`부터 센다.

배포 파이프라인이 자동으로 안 도는 브랜치는 "dev, stage 배포" 같은 배포 주문을 따로 넣는다. 이때 `order add --deploys <orderId...>`로 그 배포에 들어가는 주문을 같이 적어 두면 손으로 주문마다 `deploy report`를 남기지 않아도 된다. 접수할 때 대상이 있는 주문인지, 배포 주문과 같은 레포인지 확인하고 틀리면 거절한다. 대상은 `order show --json`과 `status --json`의 `deploys`에 보인다.

배포 워커가 done으로 보고하면 다음 tick이 대상 주문마다 `deploy report --status success`와 같은 신호 파일을 `deploy/`에 쓴다. ref는 워커가 `worker report --deploy-ref <url>`로 실은 배포 실행 주소이고 없으면 배포 주문 id다. 신호를 쓴 뒤에는 같은 tick의 머지 뒤 정산이 평소처럼 지라를 In-QA로 옮기고 주문을 `done`으로 끝낸다. 대상이 이미 `done`이거나 배포를 안 기다리는 유형이면 건너뛰고 tick 결과의 `deployTargets`에 남긴다. 호스트가 이미 배포 실패 신호를 남긴 대상도 성공으로 덮지 않고 건너뛴다. 머지되지 않은 대상은 이 배포에 안 들어간 것이라 기록하지 않고 warnings에 남긴다. 이 배포 주문으로는 그 대상을 다시 안 보므로, 나중에 머지돼 배포됐으면 다음 배포 주문의 `--deploys`에 넣거나 `deploy report`로 남긴다. 배포 주문당 한 번만 돌고 그 시각을 `deploysRecordedAt`에 남긴다. 배포 워커가 실패하거나 주문이 취소되면 대상에는 아무것도 남기지 않고 `deployWaitMaxSec` 기한도 그대로 흐른다.

## PR 감시

`~/.gestalt/conductor.json`의 `prWatchRepos`에 적은 레포만 열린 PR을 gh로 읽는다. 기본은 빈 배열이라 적지 않으면 감시하지 않는다. 본문은 안 싣고 누가 언제 남겼는지만 본다.

```json
{
  "repoPaths": { "acme/app": "/path/to/app", "acme/web": "/path/to/web" },
  "prWatchRepos": ["acme/app"]
}
```

`repoPaths`는 워크트리를 만들 경로를 알려 주는 칸이라 여기 적었다고 감시하지는 않는다. 레포를 추가하자마자 오래된 draft나 사람이 다른 세션에서 직접 맡은 PR까지 주문이 생기는 걸 막으려고 둘을 나눴다.

- gh는 그 레포의 로컬 체크아웃에서 부르므로 `prWatchRepos`에 적은 레포는 `repoPaths`에도 같은 철자의 키로 경로가 있어야 한다. 없으면 그 레포만 감시에서 빠지고 tick 보고의 `errors`에 이유가 남는다.
- `owner/name` 꼴이 아닌 항목(끝 공백이 붙었거나 `/`가 없는 값)도 감시에서 빠지고 `errors`에 그 값이 따옴표로 감싸여 남는다.
- 감시 간격 안이라 건너뛴 tick은 감시를 안 돌므로 위 오류도 남기지 않는다.
- 이번 tick만 감시를 건너뛰려면 `gestalt conductor tick --no-pr-watch`를 쓴다.
- 남이 만든 레포 안에서 세션을 열었다고 감시 대상이 바뀌면 안 되므로 레포 `gestalt.json`의 `prWatchRepos`는 받지 않는다.

감시가 켜진 레포에서는 PR마다 아래처럼 주문을 만든다.

- **내가 올린 PR**: 내가 마지막으로 답한 뒤에 다른 사람 코멘트가 있으면 `review-reply` 주문을 만든다.
- **내가 리뷰한 PR**: 내가 리뷰한 뒤 head가 바뀌었으면 `review-loop` 주문을 만든다. 코드는 그대로인데 답만 달렸으면 `review-manual-switch` 확인 자리로 사람에게 묻고 승인되면 재리뷰 주문을 만든다.

워커는 PR을 다루면 결과 보고에 `--pr owner/name#번호`를 싣는다. PR 감시는 끝나지 않은 주문과 사람이 넘겨받은 주문(`human-owned`, `parked`)에 붙은 이 값으로 이미 처리 중인 PR을 건너뛰므로 빠지면 같은 PR에 주문이 또 생긴다. ship이 draft PR을 만들면 Copilot 리뷰를 요청하기 전에 `--status progress --skill ship --summary "<한 줄 요약>"`으로 바로 보고한다. 끝 보고까지 미루면 그 사이 Copilot 코멘트가 달린 PR을 감시가 새 PR로 보고 `review-reply` 주문을 만든다.

## 외부 큐

다른 시스템이 주문을 넣는 자리는 상태 저장소의 `queue/` 디렉토리다. 파일 하나가 메시지 하나이고 tick이 한 번에 20개까지 이름 순으로 읽는다.

```json
{
  "repo": "acme/app",
  "title": "배너 문구 고치기",
  "description": "메인 배너 문구를 새 캠페인 문구로 바꾼다",
  "scope": "approval",
  "issueKey": "APP-123"
}
```

`repo`(`owner/name`)와 `title`은 꼭 있어야 한다. 나머지 칸은 `description`, `scope`, `issueKey`, `issueType`, `workerKind`, `jiraStatus`, `skillChain`, `baseBranch`이고 전부 빼도 된다.

`parentWorktree`는 큐로 받지 않는다. 이 머신의 경로라 바깥 시스템이 정하게 두면 워커가 엉뚱한 워크트리 아래에서 뜰 수 있다. 이 칸이 든 메시지는 확인 자리로 올라온다. 사람이 보고 `order add --parent-worktree`로 다시 넣는다.

넣는 쪽은 아래 둘 중 하나를 쓴다.

```bash
gestalt conductor queue add --body-file order.json
cat order.json | gestalt conductor queue add --body-file - --id app-123
```

`queue add`는 본문 꼴을 먼저 보고 틀리면 넣지 않는다. `--id`를 비우면 시각과 난수로 새로 만든다. 같은 id 파일이 아직 큐에 있으면 덮지 않고 거절한다. 명령 없이 파일을 직접 둘 때는 점으로 시작하는 이름으로 다 쓴 뒤 `<id>.json`으로 바꾼다. tick은 점으로 시작하는 파일을 건너뛰므로 쓰다 만 파일을 읽지 않는다.

tick은 메시지를 이렇게 처리한다.

- 출처 키는 `queue:<id>`다. 같은 id가 다시 들어와도 주문은 한 번만 생긴다.
- 꼴이 틀린 본문(`repo`나 `title`이 없는 등)은 주문을 만들지 않고 사람 확인 자리를 연다.
- 깨진 JSON, 256KB를 넘는 파일, 심볼릭 링크, id 꼴(영문, 숫자, `-`, `_`, `.`로 128자까지)이 틀린 이름은 `queue/failed/`로 옮기고 tick 보고의 `errors`에 남긴다.
- 처리한 파일은 지운다.
- 큐 본문은 자료로만 읽는다. 범위는 `defaultScope`보다 넓힐 수 없고 `merge-through`는 받지 않는다. `skillChain`은 아는 스킬 이름만 남기고 `repo:` 레포 스킬도 뺀다.

큐를 잠시 건너뛰려면 `gestalt conductor tick --no-queue`로 돌린다.

## 효과 재기

`gestalt conductor metrics --since <날짜>`가 직전 45일 사람 세션 평균과 컨덕터를 쓰기 시작한 뒤 세션을 같은 셈법으로 비교한다. 끼어든 발화는 스킬 호출 뒤 8턴 안의 사용자 발화에서 도구 결과, 메타 메시지, 압축 요약, 작업 알림, 워커 알림을 뺀 수다. 목표는 끼어든 발화 40% 감소이고 토큰은 +10% 안이 목표치다. 토큰이 넘으면 초과분을 보고만 한다.

## 실환경에서 아직 확인하지 않은 것

테스트는 지라, 슬랙, gh, 오르카를 전부 가짜 어댑터로 돌린다. 아래는 실제 환경에서 처음 쓸 때 확인해야 한다.

- 오르카 `worker-start` 응답 JSON에서 dispatch id가 담기는 필드
- 오르카 `agent launch`가 첫 지시의 `/gestalt:conductor`를 스킬 호출로 받는지와 응답 JSON의 세션 id 필드
- 실제 컴팩트 직후 트랜스크립트 마지막 응답의 usage가 줄어든 크기로 바로 잡히는지
- gh `pr list --json`의 `reviews[].commit.oid`와 `comments[].id`
- 지라 전환 이름이 프로젝트마다 다를 때 호스트가 고르는 전환
- 지휘자 탭이 닫힐 때 Claude Code가 백그라운드로 띄운 `conductor wait`를 함께 끝내는지. 안 끝나도 새 wait가 뜨면 `superseded`로 끝나고 인계한 세션의 wait는 tick 거절로 끝난다
