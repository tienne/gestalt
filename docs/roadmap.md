# Gestalt 로드맵

이 문서는 Gestalt가 다음 단계로 나아가기 위한 방향성을 정리한다. 코드 품질은 이미 상위권(타입 안전성·테스트·CI 모두 양호)이므로, 여기서는 "무엇을 더 만들까"가 아니라 **"무엇을 증명하고, 무엇으로 좁히고, 무엇으로 해자를 팔까"**를 다룬다.

한 문장 요약: **기술적으로는 상위권, 전략적으로는 갈림길.** 기능을 늘려 완결성을 높이는 길보다, Interview·Spec·Memory로 좁혀 해자를 파는 길을 택한다. 그 전에 "해상도 0.8이 정말 효과 있다"를 데이터로 증명하는 것이 모든 작업의 선결 조건이다.

---

## 핵심 진단

차별점은 코드 실행이 아니라 **코드를 쓰기 전, 요구사항의 해상도를 정량화하는 것**이다. 코드 실행은 Claude Code·Cursor·Codex가 이미 잘하고 앞으로 더 잘한다. Gestalt가 비집고 들어갈 자리는 인터뷰와 스펙이다.

그런데 현재 구조에는 세 가지 긴장이 있다.

- **증거의 부재** — "해상도를 올리면 드리프트가 준다"는 핵심 약속을 데이터로 보여주지 못한다.
- **기능 과잉** — 차별점이 아닌 영역(Execute·Code Graph 등)이 전체 LOC의 37%를 차지하며 호스트 기능과 중복된다.
- **얇은 해자** — 복제 불가능한 유일 자산인 Memory가 plain JSON 배열 수준에 머물러 있다.

아래 일곱 갈래와 기술 부채 한 갈래로 나눠 각각의 해결 방향을 정리한다.

---

## 1. 효과 증명 — "0.8이 정말 효과 있다"

### 문제

현재 0.8은 LLM이 스스로 매긴 점수가 임계치를 넘었다는 의미일 뿐이다. 그 점수가 재현되는지, 실제 결과를 개선하는지에 대한 증거가 없다. 제품의 핵심 약속인데 검증 장치가 없다.

### 해결 방향 — 3단계 증명 사다리

| 단계 | 증명할 것 | 방법 |
|------|-----------|------|
| ① 재현성 | 같은 입력 → 같은 점수 | 모호한 요구사항 20개 고정 세트, 각 5회 반복, 점수 분산(σ) 측정 |
| ② 단조성 | 점수가 오르면 결과 품질도 오른다 | 같은 과제를 해상도 0.5 / 0.65 / 0.8 스펙으로 실행하고 산출물 채점 |
| ③ 인과성 | Gestalt를 쓸 때와 안 쓸 때의 차이 | 같은 과제를 "바로 구현" vs "인터뷰 후 구현"으로 나눠 드리프트·재작업률 비교 |

### 첫 액션

`benchmarks/`에 이미 인프라가 있다. 고정 요구사항 세트(golden set) 20개와 평가 루브릭부터 만든다. 채점은 LLM-as-judge로 자동화하되, 5개는 사람이 직접 라벨링해 judge를 보정한다.

### 성공 기준

"해상도 0.8 스펙은 0.5 스펙 대비 재작업률 X% 감소"라는 한 문장을 README 최상단에 박을 수 있으면 성공이다. 이 문장은 마케팅 자산이자 회귀 테스트가 된다.

> ⚠️ ③이 "효과 없음"으로 나올 수도 있다. 그래도 빨리 아는 편이 낫다. 지금 전체 제품이 이 가정 위에 서 있다.

## 2. 게슈탈트 메타포 — 두 레이어로 분리

### 문제

5원리가 전체를 관통하는 일관성은 이 프로젝트의 정체성이자 미학이다. 동시에 신규 사용자에게는 인지 부담이다. "왜 goalClarity가 Closure인가"는 내부적으로는 우아하지만, 처음 쓰는 사람이 배울 이유가 없는 어휘다. 우아함이 진입장벽으로 작동할 위험이 있다.

### 해결 방향 — 표면과 심층 분리

- **표면(사용자 노출)**: "목표 명확도 0.4 → 0.8, 미해결 모순 2건"처럼 평범한 언어
- **심층(아키텍처·문서·브랜딩)**: 게슈탈트 원리를 그대로 유지
- 둘 사이는 매핑 테이블 하나로 연결한다. README에 이미 있는 표가 그 씨앗이다.

### 첫 액션

인터뷰 응답에서 사용자에게 보이는 필드(`label`, `improvementHint`)를 게슈탈트 용어 없이 다시 쓴다. 코드 내부 식별자(`gestaltPrinciple`)는 건드리지 않는다. 표면 문자열만 교체하므로 리스크가 낮고 효과는 즉시 나타난다.

### 성공 기준

게슈탈트를 한 번도 들어본 적 없는 사람이 인터뷰 출력만 보고 "다음에 뭘 명확히 해야 하는지" 이해하면 성공이다. 메타포는 "더 알고 싶은 사람을 위한 깊이"로 내려간다.

## 3. 기능 과잉 — 핵심으로 좁히기

### 문제

차별점이 아닌 영역이 호스트 기능과 중복되며 유지보수 부담만 키운다. LOC 분포가 이를 보여준다. `execute` 4,546줄 + `code-graph` 3,040줄로 전체의 37%가 차별점 바깥에 있다. 정작 차별점인 `interview`는 1,254줄이다.

### 해결 방향 — 기능을 3구역으로 분류

| 구역 | 정의 | 해당 기능 | 방침 |
|------|------|-----------|------|
| **Core (사수)** | 우리만의 차별점 | Interview, Spec, Resolution Scorer, Memory | 투자 집중 |
| **Bridge (얇게)** | 차별점과 실행을 잇는 상태 관리 | Execute 상태머신, Evaluate·Evolve 루프 | 로직 최소화, 실행은 호스트에 위임 |
| **Commodity (재검토)** | 호스트·외부 도구와 중복 | Code Graph, Role Agent 13개, Graph Viz, KB 검색 | "정말 우리가 들고 있어야 하나" 개별 판단 |

### 첫 액션

바로 삭제하지 않는다. 사용 데이터부터 모은다. EventStore에 이벤트가 쌓이고 있으니 각 기능의 실제 호출 빈도를 집계한다. 안 쓰는 기능부터 deprecate 후보로 둔다. 데이터 없이 애착으로 자르면 반발과 후회가 생긴다.

### 성공 기준

"Gestalt는 X를 한다"를 한 문장으로 말할 수 있게 되면 성공이다. 지금은 그 문장이 너무 길다.

## 4. Memory — 진짜 해자 키우기

### 문제

Passthrough 모드(API 키 불필요)는 진입장벽을 낮추는 좋은 선택이다. 동시에 이 선택은 Gestalt를 "상태 관리자 + 프롬프트 생성기"로 만든다. 프롬프트와 게슈탈트 프레임워크는 복제할 수 있다. 복제 불가능한 자산은 누적된 Memory 하나뿐인데, 지금은 plain JSON 배열로 너무 얇다.

### 해결 방향 — "검색 가능한 결정 이력"으로 격상

1. **연결** — KB의 임베딩 인프라를 Memory에 붙여 "예전 비슷한 스펙"을 시맨틱 검색한다. 인프라를 재사용하므로 신규 개발이 적다.
2. **심화** — 결정의 이유·결과·회고까지 스키마를 확장한다. `architectureDecisions: string[]`을 구조화된 레코드로 바꾼다.
3. **공유** — 팀 단위 누적을 강화하고, commit 시 충돌 머지 전략을 정의한다.

4. **회수** — human escalation을 종료가 아니라 해소 가능한 게이트로 바꿔 사람의 판단을 Memory로 회수한다.

지금은 `EVOLVE_HUMAN_ESCALATION`이 오면 세션이 `status='failed'`, `terminationReason='human_escalation'`으로 끝난다(`src/execute/repository.ts`). 사람이 판단해서 답을 줘도 그 답이 어디에도 남지 않고 세션도 재개되지 않는다. 막힌 지점과 사람이 내린 결정은 `architectureDecisions`에 들어갈 가장 값진 재료인데 실패와 함께 버려지는 셈이다.

Orca는 이걸 `gate-create` / `gate-resolve` / `gate-list`로 레코드화해서, 질문과 선택지와 해소 내용을 저장하고 답이 오면 흐름을 이어간다. 워커가 막혀서 던지는 블로킹 질문(`ask`)과 코디네이터가 DAG 결정을 위해 만드는 게이트를 구분해 둔 것도 참고할 만하다.

### 첫 액션

②부터 시작한다. `architectureDecisions`를 `{ decision, rationale, outcome?, specId, timestamp }` 구조로 바꾼다. 인터뷰 주입 시 "과거 결정과 그 결과"를 함께 넣어 "인터뷰가 점점 똑똑해진다"를 실체화한다. ④의 게이트 레코드가 이 구조를 그대로 채우는 입력이 되므로 스키마를 함께 설계한다.

### 성공 기준

같은 팀이 두 번째 비슷한 과제를 할 때, 인터뷰 라운드 수가 측정 가능하게 줄어들면 성공이다. 1번에서 만든 벤치마크로 측정할 수 있다.

> 📝 3번에서 "재검토" 대상으로 둔 KB 검색 인프라가 여기서 핵심 부품으로 재활용된다. 버리는 게 아니라 핵심으로 끌어오는 것이다.

## 5. 플랫폼 종속 리스크

### 문제

Claude Code에 강하게 결합돼 있다. 좋은 단기 전략이지만, Claude Code가 plan mode·skill·subagent를 계속 강화 중이다. 호스트가 "요구사항 명확화"를 기본 탑재하면 차별점이 증발한다.

### 해결 방향 — "세션"이 아닌 "프로젝트 역사"로 포지셔닝 이동

- 호스트가 잘하는 것: 지금 이 세션의 추론과 실행
- Gestalt가 잡을 것: 프로젝트 전체에 걸친 요구사항의 역사와 일관성 (다시 Memory로 귀결)
- 전술: MCP 표준에만 의존하고, 호스트 전용 기능 의존을 최소화한다. Codex·Gemini 지원은 이미 옳은 방향이다.

### 첫 액션

호스트별 기능 의존을 추상화 레이어 하나로 격리한다. 지금의 `client` 설정(claude-code / codex / both)이 그 씨앗이다. 여기에 호스트 차이를 모두 흡수시켜 코어가 호스트를 모르게 만든다.

### 성공 기준

새 호스트를 추가하는 일이 "어댑터 한 개 작성"으로 끝나면 성공이다. 코어 코드에 호스트 분기가 없어야 한다.

## 6. 스킬 배포 — 하이브리드 스텁으로 전환

### 문제

스킬 가이드와 그 가이드대로 실행할 MCP 서버가 따로 배포된다. skills/ 15개는 npm 패키지(`package.json`의 `files`)와 플러그인(`plugin.json`의 `"skills": "./skills/"`) 두 경로로 나가는데, 플러그인이 서버를 찾는 경로는 `.mcp.json`이 따로 들고 있다. 설치된 SKILL.md의 액션 설명과 실제로 그 액션을 처리할 서버 버전이 묶여 있지 않다는 뜻이다.

`ges_execute` 액션이 25개까지 늘어난 만큼 시그니처가 바뀔 여지도 크다. 지금은 그 위험을 릴리즈 절차로 막고 있어서, 버전을 올릴 때마다 플러그인 매니페스트 범프 커밋을 따로 만들고 스킬 문서가 최신인지 사람이 확인해야 한다.

### 해결 방향 — 가이드를 실행 주체가 서빙

Orca CLI가 쓰는 하이브리드 스텁 패턴을 따른다.

- SKILL.md에는 디스커버리 정보(트리거 조건, 언제 이 스킬을 쓰는지)만 남긴다
- 상세 가이드는 설치된 패키지가 런타임에 서빙한다 — `gestalt skills get <name>` CLI 서브커맨드 또는 MCP 리소스
- 가이드를 주는 주체가 곧 액션을 실행할 패키지이므로 버전 드리프트가 원천적으로 사라진다

부수 효과로 5번(호스트 추상화)을 돕는다. 스텁은 호스트 중립적이라 Claude Code든 Codex든 같은 파일로 배포할 수 있다.

### 첫 액션

액션 시그니처가 가장 자주 바뀌는 스킬 하나(execute)로 파일럿한다. CLI에 `skills get` 서브커맨드를 추가하고, 해당 SKILL.md 본문을 스텁으로 교체한 뒤 스킬 발동 시 가이드를 받아오게 한다.

### 성공 기준

스킬 가이드의 버전이 항상 설치된 패키지 버전과 일치하면 성공이다. 릴리즈 때 스킬 문서 갱신을 사람이 확인할 필요가 없어진다.

## 7. 병렬 에이전트 환경 대응

### 문제

에이전트를 워크트리마다 띄워 병렬로 돌리는 환경(Orca 같은 도구)에서 게슈탈트의 상태가 끊긴다. 저장 위치가 셋으로 갈라져 있고 각각 다르게 동작한다.

| 상태 | 저장 위치 | 워크트리에서 |
|------|----------|-------------|
| 이벤트 DB | `~/.gestalt/events.db` (홈 글로벌) | 세션이 워크트리를 넘어 이어짐 |
| 코드 그래프 | `<repoRoot>/.gestalt/code-graph.db` | 워크트리마다 비어 있어 매번 풀 리빌드 |
| 프로젝트 메모리 | `<repoRoot>/.gestalt/memory.json` | 빈 상태로 시작하고, 워크트리를 지우면 함께 사라짐 |

`ProjectMemoryStore`의 `detectRepoRoot`가 첫 `.git`에서 멈추는데 링크드 워크트리는 `.git`이 파일이어도 잡히므로 repoRoot가 워크트리 디렉토리가 된다. blast-radius를 쓰려면 워크트리마다 그래프를 새로 빌드해야 하고, 4번에서 키우려는 Memory 피드백 루프는 사실상 무력화된다.

### 해결 방향

1. **병렬은 워크트리가 아니라 터미널로** — 같은 워크트리에 에이전트 터미널을 여럿 띄우면 `.gestalt/`를 공유하므로 위 표의 문제가 애초에 생기지 않는다. Orca 자체 가이드도 같은 말을 한다 — 병렬 실행이나 편의는 워크트리 분리의 사유가 아니고, 같은 체크아웃을 공유하면 안 되는 파일 충돌이 있을 때만 워크트리를 만든다. **디스패치의 기본값을 같은 워크트리 안 터미널로 두면 2번이 1번에 의존하지 않는다.**
2. **상태 공유는 워크트리를 실제로 나눌 때만 필요하다** — 파일 충돌로 워크트리를 분리해야 하는 경우에 한해, `git rev-parse --git-common-dir`로 메인 리포를 찾아 코드 그래프와 memory를 거기에 둔다. 그래프는 SQLite WAL이라 동시 읽기가 안전하지만 memory.json은 plain JSON이라 동시에 쓰면 깨진다 — 공유하는 순간 쓰기 직렬화를 함께 해결해야 한다. 부담이 크면 워크트리 생성 시 메인 그래프를 복사하고 diff로 증분 갱신하는 부트스트랩만으로도 체감이 크다.
3. **디스패치 스킬** — ready 집합(`nextTaskIds`, 완료)을 읽어 태스크당 에이전트 터미널 하나에 넣고, `worker_done`을 기다렸다가 새로 가능해진 태스크를 다시 뿌린다. 게슈탈트가 플래닝을, 외부 도구가 실행 인프라를 맡는 분담이 된다.
4. **상태를 사람 눈에 보이게** — escalation과 파이프라인 단계를 워크트리 카드 코멘트로 미러링한다. 지금은 그 터미널을 열어봐야만 보인다.

### 외부 도구가 없는 환경이 기본값이다

디스패치 스킬은 **opt-in 대안 백엔드**다. Orca 같은 도구가 없는 사용자에게는 지금 동작이 그대로 유지된다 — execute 스킬이 이미 `parallelGroups`를 읽어 호스트의 Agent 도구로 병렬 실행하고 있고, 그 경로가 계속 기본값이다.

- **게슈탈트 코어는 외부 도구를 모른다.** 현재 `src/` 어디에도 Orca 참조가 없고, 그 상태를 유지한다. 의존은 스킬 층에만 둔다.
- **감지 실패는 조용히 넘기지 않는다.** CLI가 없거나 런타임이 안 붙으면 어느 경로로 돌았는지 밝히고 기본 경로로 내려간다. `skills/_shared/tool-availability.md`의 규칙이 그대로 적용된다.
- **존재 여부만으로 판단하지 않는다.** 리눅스에서 `orca`는 GNOME 스크린리더 이름이라 `which orca`로 찾으면 엉뚱한 프로그램에 명령을 보내게 된다. `orca status --json` 응답을 검증하고, 리눅스에서는 `orca-ide`를 쓴다.
- 외부 도구를 경유해 얻는 것은 병렬 자체가 아니라 **에이전트 다양성(워커별로 다른 CLI), 사람이 들여다볼 수 있는 터미널, `worker_done` 생애주기 추적**이다. 이게 필요 없으면 기본 경로가 더 가볍다.

### 첫 액션

이벤트 DB에 `busy_timeout`을 넣는다. `src/events/store.ts`가 `journal_mode = WAL`과 `foreign_keys = ON`만 설정해서, 프로세스가 둘 이상 같은 `~/.gestalt/events.db`에 쓰면 기다리지 않고 `SQLITE_BUSY`로 즉시 실패한다. 워커를 여럿 띄우기 전에 해결해야 하고, **외부 도구와 무관하게 같은 레포에서 세션 두 개만 띄워도 발생한다.**

그다음 디스패치 스킬을 만든다. 워커는 캐시된 세션 상태를 믿지 말고 매번 다시 읽어야 한다 — 서버 프로세스마다 인메모리 `sessions` Map을 따로 들고 있어서, 이벤트는 append-only로 수렴하지만 다른 프로세스의 파생 상태(`nextTaskIds`)는 낡는다. ready 집합을 앞으로 굴리는 것은 코디네이터 한 명만 한다.

### 성공 기준

워크트리 다섯 개에서 같은 코드 그래프를 재빌드 없이 쓰고, 한 워크트리에서 쌓인 결정이 다음 워크트리 인터뷰에 주입되면 성공이다.

## 기술 부채

방향성 작업을 떠받치는 토대다. 우선순위는 방향성보다 낮지만, `core/` 테스트는 모든 변경의 안전망이라 먼저 처리한다.

| 항목 | 방향 | 트리거 시점 |
|------|------|-------------|
| `core/` 테스트 0% | Result 모나드와 config 로딩부터 테스트한다. 모든 것의 기반인데 테스트가 없다 | 지금 |
| 태스크 단위 서킷브레이커 없음 | 재시도가 LLM 어댑터(`maxAttempts=3`)와 리뷰 fix 루프에만 있다. 한 태스크가 연속 실패할 때 끊어주는 장치가 없어 호스트가 같은 태스크를 무한히 물고 있을 수 있다. Orca는 3회 연속 실패 시 dispatch를 끊고 failed로 마킹한다 | Stagnation Detector 손댈 때 |
| MCP 응답에 절삭 개념 없음 | 플랜과 스펙 전문이 그대로 나가 긴 세션에서 컨텍스트를 누른다. Orca `task-list --brief`처럼 요약 옵션과 `spec_truncated` 같은 절삭 표시를 둔다 — 잘랐다는 사실을 응답이 알려주지 않으면 호스트가 전체를 봤다고 착각한다 | 3번 사용 데이터 집계와 함께 |
| 실행 완료를 확인 없이 신뢰 | Passthrough라 실제 실행 주체가 호스트인데, 파일이 정말 바뀌었는지 확인하지 않고 완료로 넘어갈 여지가 있다. Orca 스킬은 "했다고 주장하기 전에 상태를 조회하라, 밖에서 돌았으면 솔직히 말하라"를 본문에 박아둔다 | 6번 스텁 전환 때 함께 |
| `.mcp.json` 절대경로 하드코딩 | `/Users/kwon-david/dev/gestalt/dist/bin/gestalt.js`가 커밋돼 있어 다른 사람이 플러그인을 설치하면 서버가 붙지 않는다. 배포 대상을 정하고 경로 해석 방식을 결정한다 | 6번과 함께 |
| 거대 파일 분해 | `evolution.ts`(583줄), `server.ts`(665줄), `code-graph/engine.ts`(562줄)를 해당 기능을 손댈 때 함께 쪼갠다 | 3번 진행 중 |
| KB 검색 O(n) | `search.ts`가 전체 엔트리를 선형 스캔한다. 4번에서 Memory에 붙일 때 함께 개선한다 | 4번과 동시 |
| 프롬프트·파일 IO 추상화 | `prompts.ts`(636줄), `readFileSync` 19개 파일 산재. `PromptBuilder`·`FileStore`로 통합한다 | 후순위 |

> ⚠️ `core/` 테스트 부재는 모순적이다. 자주 바뀌는 `execute`는 123% 커버리지인데, 잘 안 바뀌지만 모두가 의존하는 `core`는 0%다.

## 실행 순서

순서가 중요하다. **증명 → 좁히기 → 키우기** 흐름이다.

```
[0] core/ 테스트 보강 ─────────────── 안전망 (모든 작업의 전제)
      │
[1] 효과 벤치마크 (golden set) ─────── "무엇이 효과 있는지" 측정 도구 확보
      │         │
      │         └──> 이 측정 도구가 3·4번의 판단 근거가 된다
      ▼
[3] 기능 사용 데이터 집계 ──────────── "무엇을 줄일지" 데이터 확보
      │
      ▼
[2] 메타포 표면 분리 ──────────────── 저리스크·즉효, 병렬 진행 가능
      │
      ▼
[4] Memory 격상 (KB 인프라 재활용) ─── 진짜 해자 구축
      │
      ▼
[5] 호스트 추상화 ─────────────────── 방어선
      │
      ▼
[6] 스킬 하이브리드 스텁 ───────────── 배포 드리프트 제거, [2]처럼 언제든 병렬 가능
      │
      ▼
[7] 병렬 에이전트 환경 대응 ────────── 상태 공유가 [4] Memory의 전제조건
```

### 세 가지 핵심 통찰

1. **벤치마크(1)가 모든 판단의 기준점이다.** 이것 없이 3·4번을 하면 감으로 하는 셈이다.
2. **메타포 분리(2)는 리스크가 가장 낮고 효과는 즉시 나타난다.** 언제든 병렬로 끼울 수 있어 워밍업으로 좋다.
3. **3번에서 줄이려던 KB 인프라가 4번의 핵심 부품이 된다.** 축소와 강화가 한 흐름이다.
