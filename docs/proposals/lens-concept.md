# 읽기 렌즈 컨셉 다시 잡기

## 배경

### 컨셉

렌즈는 리포트를 한 장 더 만드는 기능이 아니다. 원문을 해석하고 검증해서 읽는 사람에게 **쉽고 정확하게** 설명하는 기능이다. 다 읽은 사람이 "나 천재인가? 쉽게 이해되네?" 하고 느끼면 성공이다.

출처 칩과 의심 표시, 원문 표 대조는 "정확하게"를 맡는다. 목적이 아니라 쉬운 설명이 틀리지 않게 받치는 장치다. 지금 렌즈는 이 장치를 앞에 내세우고 "쉽게" 쪽은 옵션으로 뒀다. 이 문서는 그 무게를 뒤집는다.

[`reading-lens.md`](./reading-lens.md)의 "천재의 눈" 표에 동작 하나를 더한다.

| 동작           | 지금                                                            | 새로 필요한 것                                                                  |
| -------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 쉽게 풀어 준다 | 쉬운 리포트(opt-in, 보통 리포트에 없는 내용은 못 더함), 위젯 넷 | 비유와 예시를 원문 내용과 구분해 싣기, 개념에 맞는 그림을 고를 만큼 다양한 위젯 |

### 같은 원문으로 견준 결과

Confluence의「캐치테이블 FE 배포 프로세스」 한 편을 두 가지로 만들어 견줬다.

| 표현              | 손으로 만든 풀이 문서                                                                       | 렌즈(`difficulty=easy`, `templates=quiz`)                                |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 비유 표           | 배포를 택배 출고에 빗댄 5줄 표                                                              | 없음. 쉬운 리포트가 보통 리포트에 없는 내용을 못 더한다                  |
| 외울 세 줄        | 병합 방향별 규칙 세 줄을 카드로                                                             | 한눈에 보기가 주장, 근거, 한계로 고정이라 규칙 카드 자리가 없다          |
| 용어              | 용어 표에 예시(`feat/CT-1234-…`)까지                                                        | `keywords`와 원문 표로 됨                                                |
| 내 PR의 여정      | 되돌아가는 화살표가 있는 단계 카드                                                          | `flow` 도식. 되돌아가는 길을 못 그린다                                   |
| 배포 건이 겹칠 때 | 브랜치 이름이 붙은 커밋 그래프를 11단계로 넘겨 본다. 버려진 커밋은 점선, 단계마다 환경 상태 | 위젯 0개. B는 원문 이름과 숫자를 못 쓰고 원문 그림이 안 잡혀 C도 못 쓴다 |
| 주간 일정         | 요일 달력                                                                                   | `timeline` 도식과 원문 표                                                |
| 확인 퀴즈         | 문제 셋                                                                                     | 확장 리포트 퀴즈로 됨                                                    |
| 서술 모순         | 없음                                                                                        | 원문 문단 18과 19의 순서 모순을 잡았지만 한계 단락으로만 갔다            |

렌즈가 못 따라간 자리는 거의 다 "원문에 없는 설명 장치를 못 쓴다"와 "그림 종류가 모자란다" 둘로 모인다. 정확성 쪽은 오히려 렌즈가 앞섰다.

## P0-1 그림 표현 늘리기

### 모델은 계속 구조 JSON만 쓴다

지시서가 이 원칙을 바꿀지 판단해 달라고 했다. **유지한다.** 다양성은 종류를 늘리고 종류끼리 같은 단계 모델을 쓰게 해서 얻는다.

유지하는 근거는 이렇다.

- **참고 서비스의 그림 결함이 전부 모델이 HTML을 직접 쓴 자리에서 났다.** 난수로 만든 점수, 원문에 없는 설정, 정답으로 깔끔하게 모이는 재구성이 다 그랬다([`reading-lens.md`](./reading-lens.md) "못한 것").
- **lint가 볼 수 있는 건 JSON 칸뿐이다.** SVG를 받으면 글자 노드는 뽑아 대조할 수 있어도 막대 높이, 점 위치, 선 연결처럼 모양으로 전하는 정보는 대조할 길이 없다. 커밋 그래프에서 "선이 이어져 있다"는 것 자체가 주장인데 그걸 검사할 수 없게 된다.
- **원문에 섞인 지시문이 스크립트로 실행될 길이 생긴다.** Confluence처럼 여러 사람이 쓰는 문서를 읽으면 더 그렇다.
- **값 사이를 보간하거나 난수로 채울 자리가 다시 생긴다.** 지금은 렌더러가 상태마다 미리 그려 두고 뷰어는 어느 상태를 보일지만 바꾼다.
- **다크 모드, 마크다운 출력, 윤문이 다 JSON 칸 단위로 돈다.** 모델 SVG는 셋 다 따로 처리해야 한다.

손으로 만든 커밋 그래프 시뮬레이터도 스크립트를 열어 보면 커밋 목록(`lane`, `from`, `show`, `gone`)과 단계 목록(`t`, `c`, `qa`, `prod`, `op`)이라는 데이터 두 개와 그걸 그리는 코드로 나뉜다. 데이터 쪽이 모델이 쓸 몫이고 그리는 코드는 렌더러에 한 번 두면 된다.

P0와 P1을 넣은 뒤에도 그리지 못하는 표현이 계속 나오면 그때 "SVG 틀 + 글자 노드 대조" 같은 다음 단계를 다시 검토한다. 그 판단 근거로 쓰려고 P1에 범용 `scene` 위젯을 둔다.

### 구분 D 원문 서술 그림

지금 구분은 셋이다. A는 원문 표 숫자, B는 원문과 무관한 장난감 예시, C는 원문 그림 재구성이다. 배포 프로세스 문서처럼 **원문이 글로 설명한 절차나 사례**를 그림으로 옮기는 자리가 비어 있다. B는 원문 이름을 못 쓰고 C는 원문 그림이 있어야 한다.

| 구분  | 무엇                                                       | 배지                          | 원문 이름          | 원문 숫자            |
| ----- | ---------------------------------------------------------- | ----------------------------- | ------------------ | -------------------- |
| A     | 원문 표 숫자로 만든 그림                                   | 원문 표 데이터                | 표에 있는 것       | 칸과 대조            |
| B     | 원문과 무관한 장난감 예시                                  | 설명용, 원문 데이터 아님      | 못 씀              | 못 씀                |
| C     | 원문 그림을 다시 그린 것                                   | AI가 이해한 대로 다시 그림    | 원문에 있는 것     | 원문 글자와 대조     |
| **D** | **원문이 글로 설명한 절차, 사례, 구조를 그림으로 옮긴 것** | **원문 설명을 그림으로 옮김** | **원문에 있는 것** | **출처 문단과 대조** |

D의 규칙은 이렇다.

- 원문 그림(`figure`)을 달면 C로 만들라고 막는다(`D_FIGURE_REF`). 원문 그림이 있는데 글로도 설명된 사례면 C가 우선이다.
- 단계마다 `cite`를 단다(`D_STEP_NO_CITE`). 단계 하나가 원문의 어느 문장을 옮긴 건지 출처 칩으로 바로 열린다.
- 그림 속 이름은 원문에 있어야 한다(`D_NAME_UNKNOWN`). 대상은 영문자와 숫자가 섞인 토큰, `/`나 `-`, `_`, `.`이 든 토큰, 두 글자 이상 영단어다. `release/20260728`, `main`, `alpha`, `force push` 같은 것이다. 한국어 설명 말("브랜치 생성", "버그 발견")은 대조하지 않는다. 이름은 원문 어디에 있든 된다. 이름은 한 번 정의되고 여러 문단에서 가리키기 때문이다.
- 그림 속 숫자는 그 요소나 단계의 출처 문단, 위젯 `cite` 범위 안에 있어야 한다(`D_NUMBER_UNKNOWN`). 이름 속 숫자는 이름으로 대조하므로 여기서 세지 않는다.
- 지표 말은 A와 같이 원문에 나온 것만 쓴다(`WIDGET_METRIC_UNKNOWN`을 그대로 쓴다).
- 원문에 없는 요소를 끼워야 이해가 쉬우면 그 요소에 `illustrative: true`를 단다. 렌더러가 점선 테두리와 "예시" 꼬리표로 그리고 그 요소 라벨은 B 규칙(`B_HAS_NUMBER`, `B_METRIC_LABEL`)을 받는다. 예를 들어 "내 수정 커밋"처럼 원문에 없는 커밋 하나를 더 그릴 때 쓴다.
- `differences`는 선택이다. 원문 설명을 단순하게 옮긴 자리가 있으면 적는다. 손으로 만든 문서의 "원문 그림과 조금 다르게 그렸어요" 단락이 이 칸이다.

### 공통 단계 모델

지금 `stepSlider`만 단계가 있고 단계마다 노드와 간선을 통째로 다시 적는다. 새 위젯은 **요소 목록은 한 번 적고 단계는 그 위의 변화만 적는다.** 모든 단계형 위젯이 같은 `steps` 꼴을 쓴다.

```jsonc
"steps": [
  {
    "label": "0721이 먼저 production에 나간다",
    "note": "release/20260721을 main으로 rebase 머지했다. 커밋 두 개가 main 위에 새로 생긴다",
    "cite": { "key": 19, "from": 19, "to": 19 },
    "show": ["m1", "m2"],   // 이 단계에서 처음 보이는 요소
    "gone": ["a1", "a2"],   // 이 단계에서 점선으로 그리고 다음 단계부터 숨긴다
    "focus": ["m1", "m2"],  // 강조할 요소
    "state": [              // 그림 옆 상태 칸. 손으로 만든 문서의 "alpha/beta에 올라간 것" 같은 칸
      { "key": "production", "value": "release/20260721" },
      { "key": "git 동작", "value": "rebase 머지" }
    ]
  }
]
```

- 어느 단계의 `show`에도 안 나온 요소는 처음부터 보인다.
- 렌더러는 단계마다 그림을 미리 그리고 뷰어는 보일 단계만 바꾼다. 지금 위젯과 같다. 단계 사이를 보간하지 않는다.
- 단계는 2~16개다. 이전, 다음 버튼과 키보드 좌우 화살표, "단계 3 / 11" 표시는 렌더러가 붙인다. 그래서 모델이 라벨에 "1단계"를 쓸 이유가 없다.
- `show`, `gone`, `focus`의 id는 그 위젯 요소에 있어야 한다(`STEP_REF_UNKNOWN`). `gone`으로 숨긴 요소를 뒤에서 다시 `show`하지 않는다(`STEP_REVIVES_GONE`).
- `state`의 `key`는 위젯 안에서 같은 목록을 쓴다. 키가 단계마다 달라지면 상태 칸이 흔들려서 첫 단계에 나온 키만 받는다(`STEP_STATE_KEY_UNKNOWN`).
- 기존 `stepSlider`는 그대로 둔다. 새 꼴로 옮기는 건 하위 호환 변환을 붙여 P1에서 정한다.

P0는 손으로 만든 문서가 쓴 표현부터 넣고 그다음 절차 문서에 자주 나오는 그림을 넣는다.

지금 있는 넷의 구분도 D를 받게 넓힌다. `stepSlider`와 `beforeAfter`는 D를 받는다. `toggleBars`와 `heatmap`은 값이 핵심이라 A와 C만 그대로 둔다.

#### laneGraph

```jsonc
{
  "id": "w-overlap",
  "class": "D",
  "kind": "laneGraph",
  "title": "release/20260728이 QA하는 동안 main이 두 번 앞으로 간다",
  "cite": { "key": 18, "from": 17, "to": 21 },
  "lanes": [
    { "id": "main", "label": "main" },
    { "id": "r21", "label": "release/20260721" },
    { "id": "r28", "label": "release/20260728" },
    { "id": "r23", "label": "release/20260723" },
  ],
  "nodes": [
    { "id": "m0", "lane": "main", "label": "main" },
    { "id": "a1", "lane": "r21", "label": "PR 병합", "parents": ["m0"] },
    { "id": "a2", "lane": "r21", "label": "QA 수정", "parents": ["a1"] },
    { "id": "m1", "lane": "main", "label": "PR 병합", "parents": ["m0"], "copyOf": "a1" },
    { "id": "m2", "lane": "main", "label": "QA 수정", "parents": ["m1"], "copyOf": "a2" },
    {
      "id": "b1",
      "lane": "r28",
      "label": "기능 A 병합",
      "parents": ["m2"],
      "cite": { "key": 21, "from": 21, "to": 21 },
    },
  ],
  "steps": [/* 공통 단계 모델 */],
  "differences": [
    "원문 그래프의 \"main 반영\" 점 대신 옛 커밋이 점선으로 사라지고 새 커밋이 생기는 모습으로 그렸다",
  ],
}
```

- 가로 순서는 `nodes` 배열 순서다. 렌더러가 줄과 칸 격자에 놓는다.
- `parents`는 실선, `copyOf`는 같은 색 점과 가는 점선으로 그린다. rebase가 "합치기가 아니라 복사해 새로 쌓기"라는 걸 모양으로 보여 주는 칸이다.
- 점 색은 `copyOf`를 따라 올라간 원래 줄의 색이다. 범례는 렌더러가 줄 이름으로 만든다.
- 줄 6개, 점 40개까지다. `parents`와 `copyOf`가 가리키는 id가 없거나 자기보다 뒤에 있으면 막는다(`LANE_PARENT_UNKNOWN`, `LANE_PARENT_ORDER`).

### 기존 B 규칙은 그대로 둔다

B는 원문과 무관한 장난감 예시라 지금 규칙(`B_BORROWS_NAME`, `B_HAS_NUMBER` 등)이 맞다. 원문 이름을 써야 하는 그림이 B로 막히던 건 B가 엄격해서가 아니라 D 자리가 없어서였다. 렌더러가 단계 번호를 붙이니 "1단계"를 막는 규칙도 그대로 둔다.

### 개수와 배치

- 소섹션당 위젯 0~3개는 그대로 둔다. 쉬운 리포트는 대섹션 머리의 `primer`(아래 P0-2)에 하나를 더 둘 수 있다.
- 새 위젯 렌더러는 `src/digest/render-widgets.ts`에 종류별 함수로 둔다. 마크다운 출력은 위젯마다 표나 목록으로 떨어뜨린다(`laneGraph`는 단계별 표, `calendar`는 칸 표, `analogyMap`은 두 칸 표).
- 위젯은 렌즈 전용이고 영상 리포트에서는 `LENS_FIELD_ON_VIDEO`로 막힌다. 공용 도식(`diagram-schema.ts`, `svg.ts`)은 P0에서 건드리지 않아서 video-digest 회귀 범위가 생기지 않는다. 뷰어 스크립트(`viewer-js.ts`)를 고치면 video-digest 뷰어 테스트를 같이 돌린다.

## P0-2 비유와 예시 허용

### 지금 막는 규칙

쉬운 리포트 규칙 "보통 리포트에 없는 내용을 더하지 않고 있는 내용을 빼지도 않는다"(lens-reader AGENT.md)가 비유와 예시까지 막는다. 이 규칙의 원래 뜻은 **원문 주장을 더하거나 빼지 않는다**였다. 설명 장치를 막으려던 게 아니다.

### 바꾸는 규칙

"주장"과 "설명 장치"를 나눈다.

|                 | 주장                                                      | 설명 장치                                  |
| --------------- | --------------------------------------------------------- | ------------------------------------------ |
| 무엇            | 원문이 한 말을 옮긴 불릿, 한눈에 보기, 의심 표시, 한계 줄 | 비유, 지어낸 예시, 설명용 그림             |
| 출처            | 원문 문단, 표 칸                                          | 무엇을 설명하는지 가리키는 원문 문단       |
| 숫자            | 출처와 대조                                               | 예시에서만 쓸 수 있고 "예시" 배지가 붙는다 |
| 쉬운 리포트에서 | 더하거나 빼지 않는다(지금 그대로)                         | 더할 수 있다                               |
| 화면            | 그대로                                                    | 배지와 다른 바탕색                         |

### 불릿의 `aside`

```jsonc
{
  "text": "release 브랜치는 **그날 출고분만 담은 상자**라고 생각하면 쉬워요",
  "cite": { "key": 4, "from": 4, "to": 5 },
  "aside": "analogy",
}
```

```jsonc
{
  "text": "커밋 15개짜리 PR도 release에는 커밋 하나로 들어가요",
  "cite": { "key": 27, "from": 27, "to": 27 },
  "aside": "example",
}
```

- `aside`는 `analogy`(비유)나 `example`(지어낸 예시)이다. 렌더러가 "비유", "예시" 배지를 붙이고 바탕색을 바꾼다. 모델이 끌 수 없다.
- `cite`는 이 장치가 설명하는 원문 자리다. 출처 칩도 그 자리를 연다.
- `example`의 숫자는 원문 대조에서 뺀다. 대신 지표 말(점수, 정확도, `%` 등)은 못 쓴다(`ASIDE_METRIC_LABEL`). 지어낸 결과처럼 읽히는 걸 막는다.
- `analogy`는 숫자를 못 쓴다(`ASIDE_HAS_NUMBER`).
- `aside` 불릿에는 `doubt`를 못 단다(`ASIDE_HAS_DOUBT`). 1단 불릿 가운데 `aside`가 절반을 넘으면 경고한다(`ASIDE_TOO_MANY`). 설명 장치가 주장을 밀어내지 않게 한다.
- 한눈에 보기, 도입 세 문장, 한계 단락, 의심 표시에는 설명 장치를 못 쓴다. 그 칸에는 `aside`가 없어서 스키마에서 막힌다.

### 먼저 보기(`primer`)

손으로 만든 문서가 "먼저 비유로", "외울 건 세 줄"로 시작한 효과를 뼈대를 깨지 않고 낸다. 쉬운 리포트 `lead`에 `primer`를 더한다.

```jsonc
"primer": {
  "analogy": { /* analogyMap 위젯 하나 */ },
  "rules": [
    { "text": "내 PR → release 브랜치는 **squash 머지**", "cite": { "table": "table-3", "row": 1, "col": 1 } },
    { "text": "release 브랜치 → main은 **rebase 머지**", "cite": { "table": "table-3", "row": 2, "col": 1 } },
    { "text": "최신 main → QA 중인 release는 **rebase + force push**", "cite": { "table": "table-3", "row": 3, "col": 1 } }
  ]
}
```

- `rules`는 원문 주장이다. 출처를 달고 숫자 대조를 받는다. 2~4줄이다.
- `analogy`는 선택이다. 위 analogyMap 규칙을 그대로 받는다.
- 뷰어는 한눈에 보기 바로 아래에 먼저 보기를 둔다.

### 쉬운 리포트에서 더할 수 있는 것

지금 쉬운 리포트는 위젯을 통째로 옮기기만 한다. 아래를 더할 수 있게 바꾼다.

- `aside` 불릿
- `primer`
- B, D 위젯과 analogyMap. A와 C는 원문 대조가 무거워 보통 리포트에서 확인된 것만 옮긴다.

보통 리포트에서도 D 위젯은 쓸 수 있다. 원문에 대조되는 그림이기 때문이다. `aside`와 `primer`는 쉬운 리포트에만 연다(결정 1). 보통 리포트는 "원문 가까이 보기"라 설명 장치가 섞이면 두 리포트의 차이가 흐려진다. 보통 리포트에 넣으면 merge가 `ASIDE_ON_NORMAL`로 막는다.

## P0-3 컨셉과 소개 문구

### 슬로건

| 후보                                    | 담는 것                                 |
| --------------------------------------- | --------------------------------------- |
| 어려운 글도 내가 똑똑해진 것처럼 읽히게 | 컨셉 문장("나 천재인가?")에 가장 가깝다 |
| 쉽게, 그런데 틀리지 않게                | 쉬움과 정확함 둘을 다 앞에 둔다         |
| 그 분야 선배가 옆에서 풀어 주는 읽기    | 옆에서 같이 읽는 경험을 앞에 둔다       |

두 번째로 정했다(결정 4). 첫 번째는 목표 느낌은 살지만 정확성 쪽이 빠져서 렌즈가 참고 서비스와 갈리는 자리가 안 보인다. 두 번째는 "쉽게"가 주인이고 "틀리지 않게"가 받치는 지금 컨셉의 순서와 같다.

### description 초안

```
논문 PDF나 웹 글, 사내 문서, 팟캐스트를 읽는 사람이 쉽게 이해하도록 풀어 주는 읽기 뷰어를 만든다. 비유와 예시, 단계별로 넘겨 보는 그림으로 설명하고 문장마다 원문 출처를 달아 틀리지 않게 받친다. 원문 숫자가 어긋나는 자리는 의심 표시로 짚는다("이 문서 쉽게 설명해줘", "이 논문 같이 읽어줘", "주니어도 이해하게 풀어줘"). 유튜브 영상이면 video-digest로 넘긴다. 코드나 diff, 개념 하나를 설명하는 일은 explain을 쓴다.
```

### 트리거에 더할 말

- 이 문서 쉽게 설명해줘
- 주니어도 이해하게 풀어줘
- 이 컨플루언스 문서 풀어서 보여줘
- 이 글 비유로 설명해줘

explain 스킬과 헷갈릴 수 있다. explain은 레포 코드나 diff, 개념을 대상 독자에게 글로 설명하고 lens는 **바깥 원문 한 편**을 출처가 달린 뷰어로 만든다. description 끝에 그 경계를 적었고 `pnpm verify:skill-confusion`이 걸리면 임계값이 아니라 문구를 고친다.

### 고칠 자리

- `plugin/skills/lens/SKILL.md` frontmatter와 첫 단락
- `plugin/role-agents/lens-reader/AGENT.md` 첫 단락. 목표 문장을 "쉽고 정확하게"로 바꾸고 의심 표시가 그 수단이라고 적는다
- `docs/lens.md` 첫 단락
- `README.md`에 렌즈 소개가 있으면 같이
- `pnpm build:routing`, `pnpm build:agents`로 생성물을 다시 뽑는다
- [`reading-lens.md`](./reading-lens.md)의 슬로건 결정은 지우지 않고 이 문서로 바뀌었다는 줄을 단다. CHANGELOG의 지난 항목은 고치지 않는다

## P0-4 이름 속 숫자

`numbersIn`(`src/digest/lint-lens.ts`)은 영문자 뒤 `-`나 `/`에 붙은 숫자를 세지 않는다. `ResNet-34`를 모델 이름으로 보려고 넣은 규칙이다. 그런데 이 규칙이 원문 쪽에도 똑같이 걸린다. 원문에 `release/20260721`만 있으면 허용 숫자 목록에 20260721이 안 들어가서 리포트가 "20260721에 나간 배포"처럼 숫자만 떼어 쓰면 `DOUBT_NUMBER_UNKNOWN`으로 막힌다.

- **원문 쪽은 이름 속 숫자도 모은다.** 리포트 쪽은 지금처럼 이름 속 숫자를 안 센다. 비대칭으로 둔다. 원문에 있는 숫자를 더 넓게 인정할 뿐이라 없는 숫자가 통과할 길은 안 생긴다.
- **줄임 꼴은 받지 않는다.** 원문이 `release/20260721`만 쓰고 리포트가 "0721"로 줄이면 막는다. 이번 원문은 문단 19가 "0721"을 직접 써서 통과한다. 줄임 꼴을 접미 일치로 받으면 `2026`이 `20262026` 안에 들었다고 통과하는 식의 구멍이 생긴다.
- D 위젯의 숫자 대조와 이름 대조도 같은 함수를 쓴다.

## P1

### 한눈에 보기 틀 고르기 (지시서 3)

`lead.frame`을 더하고 틀마다 필수 칸을 정한다. 자료 종류는 기본 틀만 정하고 다른 틀도 고를 수 있다. 매뉴얼 PDF는 `procedure`를 쓸 수 있어야 해서다.

| 틀          | 칸                                               | 기본으로 쓰는 자료 |
| ----------- | ------------------------------------------------ | ------------------ |
| `paper`     | problem, method, result, limit                   | pdf                |
| `argument`  | claim, evidence, limit                           | web                |
| `procedure` | what 무엇, why 왜, how 어떻게, caution 주의할 점 | 없음(고른다)       |
| `talk`      | topic, claim, limit                              | podcast            |

- `procedure`에는 `limit` 칸이 없다. 절차 문서에서 한계 칸은 억지로 채우게 되고 이번 렌즈 결과처럼 서술 모순이 그 칸으로 들어간다. 대신 "force push는 정해진 절차대로만" 같은 주의 사항이 `caution`으로 간다. 한계 단락(`limits`)은 그대로 필수다.
- 틀이 비었으면 자료 종류의 기본 틀로 본다. 지금 리포트는 그대로 통과한다.

### 웹 글 그림 수집 (지시서 7)

원인은 둘이다. `web-extract-py.ts`가 trafilatura를 `include_images=False`로 부르고 Orca 탭에서 꺼낸 HTML의 Confluence 첨부 이미지는 로그인 쿠키가 있어야 받히는 주소다.

1. Orca 탭에서 HTML을 꺼내기 전에 본문 `<img>`를 data URL로 바꾸는 스크립트를 탭 안에서 돌린다. 같은 출처 첨부라 `fetch(src, { credentials: 'include' })`로 받힌다. 그림 하나 5MB, 합계 30MB까지다. `orca eval`이 Promise를 기다리는지 먼저 확인한다.
2. web 수집이 본문 그림을 `figures`로 남긴다. 캡션은 `alt`, `title`, 그림 바로 아래 문단 순으로 찾는다. 출처 위치는 그림 앞 문단 번호다.
3. 그림이 잡히면 C 재구성을 웹 글에서도 쓸 수 있다. 이번 원문이라면 커밋 그래프 그림이 C의 원문 그림이 되고 손으로 만든 시뮬레이터가 C의 `differences`에 적은 내용이 그대로 들어간다.
4. 장면 수(`panels`)는 웹 그림에서 못 읽는다. C 단계형 위젯은 `panels`가 없으면 `C_PANELS_UNKNOWN`으로 막히므로 웹 그림은 `panels: 1`로 두고 글로 설명된 단계는 D로 그리게 한다. C와 D를 나란히 두는 배치를 받는다.

### 서술 모순 의심 (지시서 8)

lens-reader가 문단 18과 19의 순서 모순을 잡았는데 `DOUBT_NOT_NUMERIC`에 막혀 한계 단락으로 갔다. 숫자 없는 의심을 막은 이유는 "해석이 갈리는 의심이 틀리면 렌즈 전체를 못 믿게 된다"였다. 원문 문장을 그대로 인용하게 하면 기계로 확인할 수 있는 범위가 생긴다.

```jsonc
"doubt": {
  "kind": "narrative",
  "note": "0721 배포 직후에 갈라졌다면서 0721 때문에 rebase했다고 적어 순서가 맞지 않는다",
  "quotes": [
    { "cite": { "key": 18, "from": 18, "to": 18 }, "text": "그 직후 release/20260728이 main에서 갈라져 나와" },
    { "cite": { "key": 19, "from": 19, "to": 19 }, "text": "main이 0721로 한 번, 0723으로 또 한 번 앞으로 나갈 때마다" }
  ]
}
```

- `quotes`는 서로 다른 문단 둘 이상이다(`DOUBT_NARRATIVE_ONE_SIDE`). `text`는 그 문단에 글자 그대로 있어야 한다(`DOUBT_QUOTE_MISMATCH`). 공백만 정규화한다.
- `note`의 숫자는 인용문 안에 있어야 한다.
- 뷰어는 숫자 의심과 다른 배지("서술이 엇갈림")를 달고 인용 둘을 나란히 펼친다. 읽는 사람이 두 문장을 직접 견줘 판단하게 한다.
- 지금 숫자 의심은 `kind`가 없으면 `numeric`으로 본다.

### 범용 장면 위젯 `scene`

정해진 종류로 안 되는 그림의 출구다. 칸 격자 위에 상자와 점, 글자를 놓고 연결선과 묶음을 두고 공통 단계 모델로 넘긴다. 자유 좌표 대신 격자 칸(`row`, `col`, `span`)만 받아 겹침과 어긋남을 렌더러가 막는다. 넣은 뒤 리포트 몇 편에서 `scene`이 얼마나 쓰이는지 보고 자주 나오는 모양은 정식 종류로 올린다. `scene`조차 모자라다는 기록이 쌓이면 그때 구조 JSON 원칙을 다시 본다.

## P2

- **쉬운 리포트의 가르치는 순서.** 손으로 만든 문서는 원문 순서가 아니라 비유 → 규칙 → 용어 → 여정 → 어려운 사례 순으로 짰다. P0의 `primer`로 앞부분은 낸다. 대섹션 순서까지 바꾸려면 쉬운 리포트 뼈대를 보통 리포트와 다르게 두고 토글이 id 대신 출처 범위로 짝을 지어야 한다. 토글 동작이 크게 바뀌어서 P2로 둔다.

## 정한 것

2026-11-25에 권윤학님이 정했다.

1. **`aside`와 `primer`는 쉬운 리포트에만 연다.** 보통 리포트에 넣으면 merge가 막는다.
2. **쉬운 리포트를 기본으로 만든다.** 리포트가 두 벌 쓰이는 비용을 감수한다.
3. **`audience` 기본값은 `peer`다.**
4. **슬로건은 "쉽게, 그런데 틀리지 않게"다.** 화면 이름 "읽기 렌즈"는 그대로 둔다.
5. **쉬운 리포트 기본화(지시서 1)를 P0로 올린다.** 가르치는 순서 뼈대는 P2로 둔다.

## 남은 열린 질문

1. **자동 배치 품질.** `stateMachine`과 `swimlane`은 렌더러가 자리를 잡는다. 상태 10개를 넘으면 선이 엉킬 수 있어서 상한을 낮게 잡았다. 구현 중에 읽히지 않으면 상한을 더 낮추거나 `pos` 힌트를 필수로 바꾼다.
2. **`D_NAME_UNKNOWN` 범위.** 이름을 원문 어디에서든 찾게 했다. 단계의 출처 문단 안으로 좁히면 더 엄격하지만 "main"처럼 앞에서 정의하고 뒤에서 가리키는 이름이 다 막힌다. 원문 전체로 두는 쪽을 제안한다.
3. **기존 `stepSlider`를 공통 단계 모델로 옮길지.** 지금 꼴(단계마다 노드와 간선 전체)을 하위 호환으로 받고 새 꼴을 더할지, 두 꼴을 그대로 둘지 정한다. P0에서는 손대지 않는다.
